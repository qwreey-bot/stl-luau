## 1. 지금 어디에 있는가

## 2. 예전 과제에서 가져오는 것과 가져오지 않는 것

과제의 구조(다시 풀어 적음):

- **필수 연산만 구현하면 나머지는 인터페이스의 기본 구현이 준다.** 이진 트리 인터페이스가 "루트·왼쪽·오른쪽·부모·값"
  다섯을 요구하고, 잎 판정·높이·전위/중위/후위 순회·출력은 그 다섯으로 인터페이스 안에 한 번만 적혀 있습니다.
- **위치의 타입이 구현마다 다르다.** 노드로 이은 트리에서는 노드가 위치이고, 배열에 담은 완전 이진 트리에서는
  인덱스가 위치입니다 — 같은 기본 구현이 양쪽에서 돕니다(지금 리스트 계약의 `I` 와 같은 생각).
- **노드가 컨테이너 바깥의 층이다.** "읽을 수 있는 노드" → "고칠 수 있는 노드" → 그 노드를 조립한 트리 → 그 위의
  이진 탐색 트리. 트리는 노드의 모양을 다시 정하지 않습니다.

**가져오지 않는 것**(사용자): 과제에서는 구현 클래스가 자기가 만족하는 인터페이스를 **전부 자기 선언에 나열**했습니다.
그러면 새 인터페이스를 더할 때마다 이미 있는 구현을 전부 고쳐야 합니다. 여기서는 **트레이트가 자기에게 필요한 것을
알고**, 그걸 갖춘 종류는 등록 없이 따라옵니다(Rust 의 `impl<T: List + Build> Seq for T`).

## 3. 모양 (시제품 `Trait2.luau`·`Traits.luau`)

> ⚠️ 아래 코드는 **시제품의 서명**입니다. `src/Trait.luau` 에 들인 것은 `defaults = function(ops, deps)` 이고
> 프리미티브를 만들 때 붙잡지 않고 **부를 때 `ops` 에서 꺼냅니다**(8절 3번의 답). 표의 "얼려 둠" 도 시제품 —
> 들인 것은 제자리 재정의 때문에 완성 표를 얼리지 않습니다.

```lua
-- 트레이트: 필수 함수 + 기본 구현 + 의존
local List = Trait.New("List", {
	required = { "Get", "FirstIndex", "LastIndex", "NextIndex", "PrevIndex" },
	defaults = function(impl, full)
		const get, first, nextIndex = impl.Get, impl.FirstIndex, impl.NextIndex   -- upvalue 로 잡음
		return {
			Fold = function(self, init, fn) … end,
			IndexOf = function(self, item) … end,
			Contains = function(self, item) return full.IndexOf(self, item) ~= nil end,  -- 재정의된 판을 씀
		}
	end,
})
local Build = Trait.New("Build", { required = { "New", "PushBack" } })
local Seq = Trait.New("Seq", {                     -- Map·Filter: 같은 종류를 돌려줌
	required = {},
	requires = { List, Build },                    -- ← 의존 (Rust 의 where)
	defaults = function(_impl, _full, deps) … deps[List].Get … deps[Build].PushBack … end,
})
```

| 성질 | 어떻게 |
|---|---|
| **기본 구현** | 구현이 필수 함수만 주면 나머지는 트레이트가 채움. 같은 이름을 주면 그것이 이김(재정의) |
| **등록 때 한 번 합침** | `Trait.Impl` 이 "기본 구현 + 구현이 준 것" 으로 완성 표를 만들어 얼려 둠 → 호출 비용은 지금의 조회와 같음 |
| **의존** | `requires` 의 트레이트를 구현하지 않은 종류는 등록이 거절됨. 기본 구현은 의존 트레이트의 완성 표를 받음 |
| ⭐ **저절로 따라옴** | 필수 함수가 없는 트레이트(`Seq`)는 **등록이 필요 없음** — 의존을 다 갖춘 종류면 처음 쓸 때 만들어 캐시. 컨테이너는 자기가 아는 것만 등록 |
| **바깥에서 더하기** | 새 트레이트를 정의하면 이미 있는 컨테이너 전부에 적용됨(시제품의 `Stats` — `Arr`·`Deque`·`LinkedList` 를 고치지 않음) |
| **빠른 판** | 재정의하고 싶은 종류만 따로 등록(`Arr` 는 `Seq` 를 자기 `Map`·`Filter` 로) |

지금 저장소와의 관계: `Trait.Impl(Trait.List, TOKEN, ArrModule)` 처럼 **모듈 테이블을 그대로** 넘기는 지금 방식이면,
모듈에 같은 이름의 함수(`Arr.Fold`, `Arr.IndexOf`)가 있는 것만으로 재정의가 됩니다 — `Arr` 쪽은 고칠 것이 없고,
`Deque` 는 프리미티브만으로 나머지를 받습니다. 10-12 에 넣은 "필수 함수 목록 검사" 는 이 모양의 `required` 입니다.

- **재정의한 종류는 잃는 것이 없습니다** — 진입점 경유 비용(호출당 ~60ns)뿐.
- **기본 구현은 직접 구현의 1.1~3.8배.** 원소마다 프리미티브를 간접 호출하기 때문입니다(설계 노트의 2.5~2.8배와
  같은 크기). "없는 것" 과 비교할 자리이고, 빨라야 하면 재정의합니다.
- 기본 구현을 종류마다 클로저로 특수화하는 것(upvalue)과 구현 표를 인자로 받는 일반형의 차이는 5% 안팎 —
  특수화는 속도보다 "완성 표에 그대로 들어간다" 는 모양 때문에 고릅니다.
- **저절로 따라오는 구현의 조회**: 처음 3.3us(만들기), 그 뒤 호출당 33ns(표를 직접 조회하면 15ns).

## 5. 타입 — 서는 것과 안 서는 것 (`Algo.luau`·`types.luau`)

- **합쳐진 표는 타입 검사기가 모릅니다**(런타임에 만들어짐). 그래서 타입은 지금의 `Algorithm` 처럼 **진입점 한 곳**에
  적습니다. 종류를 아는 코드는 `Arr.Fold`, 모르는 코드는 `Algorithm.Fold` — 트레이트 마커에서 원소 타입을 추론.
  시제품의 대조: POS 8줄 0건, NEG 6줄 전부 에러(반환 타입, 원소 타입, 맵을 리스트 자리에, 빌린 참조에 쓰기).
- **"같은 종류인데 원소 타입만 다른 컨테이너" 를 적을 수 없습니다**(고차 종류 없음). 그래서
  - 원소 타입이 **그대로**인 것(`Filter`)은 넣은 타입 그대로: `<C, E, I>(list: C & ListMarker<E, I>, pred): C` ✅
  - 원소 타입이 **바뀌는** 것(`Map`)은 결과를 담을 **목적지 인스턴스**를 받음:
    `MapInto(list, fn, into: D & ListMarkerMut<G, J>): D` ✅ — 질문 AR(묶기의 결과 컨테이너)과 같은 모양입니다.
    즉 "모을 곳을 호출자가 정한다" 가 묶기만의 규칙이 아니라 이 구조 전체의 규칙이 됩니다.
- 기본 구현의 **안쪽**은 `any` 입니다(완성 표가 `any` 를 거침). 타입 안전은 진입점의 서명까지 — 지금 트레이트와 같습니다.
- 새 솔버의 한계(제네릭 함수를 든 테이블을 인자로 넘기면 추론 실패)는 이 모양에서 밟지 않습니다 — 구현은 인자가
  아니라 토큰으로 찾습니다.

## 6. 노드와 트리 (`Node.luau`·`Containers.luau`)

- **노드는 평범한 테이블 + 서비스 함수**: `ListNode = { value, prev, next }`, `TreeNode = { value, left, right, parent }`,
  잇기·끊기는 `Node.LinkAfter`/`Unlink`/`SetLeft`/`SetRight`. "데이터는 엔티티, 함수는 서비스" 그대로입니다.
- **`LinkedList`**: 노드를 조립. 위치(`I`)가 **노드** — `Get(list, 3)` 은 타입 에러. 프리미티브 다섯 + `New`·`PushBack` 만
  구현하고 `Fold`·`Find`·`Contains`·`Map`·`Filter` 를 받습니다(`Count` 는 크기를 아니까 재정의).
- **`Tree` 트레이트**: 필수 넷(`Root`·`Left`·`Right`·`Value`) → `IsLeaf`·`Height`·`Size`·전위/중위/후위 순회.
  구현 둘이 같은 순회 결과를 냅니다: 노드 트리(그 위에 이진 탐색 트리의 `Insert` 하나)와 배열에 담은 완전 이진 트리
  (위치가 인덱스, `Height` 는 계산으로 재정의).
- 시제품은 이진 트리까지입니다. 자식이 여럿인 일반 트리는 필수 연산이 달라(`Children`) 트레이트를 따로 둡니다 — 미시제품.

> **[2026-10-13 사용자 — 노드의 모양]** *"노드는 Assignment9 와 자료구조에서 짠것 처럼 read node 와 mut node 가 있고,
> 그것을 래핑하거나 해서 사용하는 식이 링크드 리스트가 되면 될지도. 다만 더블릭/싱글은 좀 애매한것 같은 느낌. 나는
> 노드는 다수의 연결이 있어도 된다 봐. 루아우니까, 그냥 arr 로써 링크하면 될것 같은 느낌. 더블릭 링크의 경우 일반
> 노드에 대해서 더블릭으로 양 방향으로 만들고, 그 방법은 1번과 2번을 쓰는것, 트리에서는 일반 노드에 1,2,3,4 를 써도
> 되고, 바이너리면 왼 오를 1 2 할당 하는식이지."*
>
> 즉 시제품처럼 `ListNode { prev, next }` 와 `TreeNode { left, right, parent }` 를 따로 두지 않고 **일반 노드 하나**:
> 연결을 **번호 칸**(배열 부분)에 둡니다 — `node[1]`, `node[2]`, …. 양방향 리스트는 1·2 를 앞·뒤로, 이진 트리는
> 1·2 를 왼쪽·오른쪽으로, 일반 트리는 1·2·3·4… 를 자식으로. 타입은 읽기 노드(`read` 필드)와 고칠 수 있는 노드 둘
> (지금의 `ArrRead`/`ArrData` 와 같은 결). 4단계에서 이 모양으로 다시 시제품을 만들고 잴 것: 값 필드(해시 부분)와
> 번호 칸(배열 부분)을 함께 가진 테이블의 생성·접근 비용 대 이름 붙은 필드만 가진 노드, 부모 연결을 어느 칸에 둘지,
> 단방향 리스트가 따로 필요한지. 과제(`Assignment9`)의 읽기/쓰기 노드 층도 그때 다시 읽습니다.
>
> **[같은 날 — 트리 구현의 자리]** *"btree 구현은 TreeMap 에 놓지 말고, 과제처럼 바깥에 있고 재사용성 있긴 해야하지
> 않을까 싶네. 바이너리 노드와 그걸 돕는 도구? 로써 말이야. Trait 으로 두어도 좋고. 이것도 List 와 유사한 방향으로
> 가는게 내 목표였었어."* — 즉 노드 기반 `TreeMap` 은 **이진 트리 조각을 조립**해 만듭니다: 이진 노드, 그 노드를
> 다루는 도구(잇기·회전·교체·순회 — `Tree` 트레이트의 기본 구현), 그 위의 탐색·균형. `TreeMap` 모듈에는 키-값
> 계약과 조립만 남깁니다(과제의 노드 → 읽기 트리 → 트리 → 이진 탐색 트리 층과 같은 결, 리스트의 "프리미티브만
> 주면 알고리즘이 따라온다" 와 같은 방향).
> *"물론 완전이진트리에 대한 배열 구현도 배제하는건 아니란거 알아둬줘."* — `Tree` 트레이트의 **위치는 제네릭**으로
> 둡니다(노드든 배열 인덱스든). 시제품의 `ArrayTree`(완전 이진 트리, 위치 = 인덱스)가 그 모양이고, 지금의 `Heap` 도
> 배열에 담은 완전 이진 트리라 같은 트레이트의 구현이 될 수 있습니다.

## 7. 들이는 순서(제안)

| 단계 | 무엇 | 지금 코드에 미치는 것 |
|---|---|---|
| 1 | `Trait` 에 기본 구현·의존·저절로 따라오기 | 트레이트 넷은 그대로 동작. 10-12 의 `required` 를 이 모양으로 합침 |
| 2 | 리스트 알고리즘을 `List` 의 기본 구현으로 + `Algorithm` 진입점 | `Arr` 는 모듈을 그대로 등록해 전부 재정의(변화 없음), `Deque` 가 알고리즘을 얻음 |
| 3 | `Build`(같은 종류 만들기)와 묶기(질문 AR) | `GroupBy`·`CountBy`·`KeyBy` 의 결과 컨테이너. 누적 방식은 별도 의견을 받는 중 |
| 4 | 노드 조각, `LinkedList`, `Tree` 트레이트와 노드 트리 | 새 모듈. `TreeMap`(정렬 배열)은 그대로 두고 같은 `Map` 트레이트의 다른 구현으로 |

각 단계는 지금까지처럼 구현 → 테스트 → 음성 대조군 → 리뷰 소진으로 닫습니다.

## 8. 정해야 할 것 — 2026-10-13 답

> 1. **들임, 전부 이 방향으로.** 2. `Algorithm` 은 **작게 시작해 점점 늘림**.
> 3. **덮어써도 됨** — 사용자: *"어차피 정의가 다 끝나야 리턴받지 않음? 따라온 것도 덮어쓰는건 문제 없지 않나. 기본
>    함수들이 똑같은 방법으로 impl 을 찾아내려 할거니까, 온 디멘드로?"* → 저절로 따라온 구현 위에 재정의를 등록하는
>    것은 허용. 그러려면 구현 방식이 따라야 합니다: 완성 표를 **새로 만들어 갈아 끼우지 않고 같은 표를 제자리에서
>    고치고**, 기본 구현은 의존 표의 함수를 등록 때 붙잡아 두지 않고 **부를 때 표에서 꺼냅니다**(호출당 테이블 조회
>    하나 — 원소마다가 아님). 시제품은 등록 때 붙잡는 판이라 이 부분을 바꿔 들입니다. (명시적으로 등록한 구현을 또
>    등록하는 것은 지금처럼 에러 — 내장 구현이 조용히 바뀌지 않게, 10-06 결정.)
> 4. **다른 이름 허용** — *"함수의 네임스페이스 자체가 다른거니까."* 트레이트마다 자기 어휘를 씁니다.
> 5. `TreeMap` — 정렬 배열이 "보통의 정의" 가 아니라는 지적. 실측(perf 30절): 무작위로 넣기는 ~수천 개까지만
>    배열이 빠르고 10만 개에선 5배 느림, 조회는 지금 구현이 노드 트리의 절반. → **[결정] `TreeMap`/`TreeSet` 은
>    노드 기반 균형 트리로(이 페이퍼의 노드 조각·`Tree` 트레이트 위에), 지금의 정렬 배열 판은 `FlatMap`/`FlatSet`
>    으로 이름을 바꿔 남김.** 둘 다 같은 `Map`/`Set` 트레이트를 구현.
> 6. 일반 트리·연결 리스트의 표면은 **조금 더 보고**. 노드의 모양은 방향을 주심 — 6절 끝의 인용(연결을 번호 칸에
>    둔 일반 노드 하나).

**들인 것**: 1단계(`src/Trait.luau` — 기본 구현·의존·저절로 따라오기, `spec.contracts` 12절, `spikes/55`) 2026-10-13.
2단계의 읽기 알고리즘 일곱(`Trait.List` 의 기본 구현 + `Algorithm` 진입점, `spec.contracts` 13절, `spikes/64`,
perf 31절) 같은 날. ⚠️ 3절의 코드는 시제품의 서명(`defaults(impl, full, deps)`, 등록 때 프리미티브를 붙잡음)이고,
들인 것은 **`defaults(ops, deps)` — 부를 때 `ops` 에서 꺼냄**입니다(8절 3번의 답).

1. **이 방향으로 들일지**, 들인다면 위 순서와 범위(전부 / 1~2단계만 먼저).
2. **`Algorithm` 을 어디까지 넓힐지.** 순회만으로 되는 `Arr` 연산은 수십 개입니다. 설계 노트 10절의 교훈("안 쓴 것은
   안 만든 것보다 나쁘다")과 "프리미티브만 주면 다 된다" 사이의 선을 어디에 그을지 — 제 생각은 읽기(접기·찾기·세기)와
   거르기·옮기기 정도의 작은 묶음에서 시작.
3. **재정의의 시점.** 저절로 따라온 구현을 이미 쓴 뒤에 그 종류가 재정의를 등록하면 — 에러로 할지, 갈아 끼울지.
   (제 생각은 에러: 같은 호출이 등록 순서에 따라 다른 함수를 부르면 안 됨.)
4. **한 종류가 두 트레이트에서 같은 이름을 가질 때**(예: `List.Count` 와 `Collection.Len` 은 같은 뜻의 다른 이름).
   이름 어휘를 트레이트끼리 맞추는 규칙이 필요합니다.
5. **`TreeMap` 의 이름.** 정렬 배열 판을 그대로 `TreeMap` 이라 부를지(Java 계보 이름), 노드 트리 판이 생기면 가를지.
6. **일반 트리**(자식 여럿)·양방향 연결 리스트의 표면을 어디까지 — 과제에서 중요했던 순회·삽입·삭제 기준으로.

## 9. 2026-10-13 오후에 더 받은 방향과 그에 대한 설계 초안

사용자 말(원문)과 **제 초안**을 갈라 적습니다. 초안은 결정이 아닙니다 — 4단계를 시작할 때 실측과 함께 확인받습니다.

### 9-1. 최종 목표의 범위

*"게임 만들면서 서치에 필요해서 트라이(Trie) 나 블룸필터나 여러가지 데이터타입을 넣기도 해. 우린 그런것도 최종
목표에 껴있음."* — 컨테이너가 계속 늘어난다는 뜻이라, **새 종류를 더할 때 고칠 파일이 그 종류의 파일 하나**여야
합니다. 같은 날의 구조 재배치(토큰을 종류의 모듈이 만듦, 트레이트는 파일 하나씩, 저절로 따라오는 구현)가 그
바탕입니다.

### 9-2. Deque 는 둘로 — 원형과 연결

*"데큐 구현체 … 보통 써큘러 큐라 하면 이 구현이 맞는데. 데큐 구현은 보통 링크드로 하는경우가 많거든. 노드면 삽입
삭제가 중간 아닌 헤드 테일을 유지한다 하면 공짜로 구현되니까. 링크드 데큐와 써큘러 데큐를 나눠야하고. 이것도
Trait 으로 몰라도 접근 가능한 구조여야할듯. 더블릭으로 원형으로 연결해서 앞 뒤 아는 상황에서 쉽게 처리도 가능한데.
그냥 헤드 테일 놓고 직접 관리하는 싱글릭 링크노드로도 구현 가능하지. … 싱글릭을 쓸 때 뒷면을 제거한다던가
추가한다던가 하면 뒤따라 자기 자신도 고쳐야한다는건데. 이건 그냥 그렇게 하는게 맞는것 같아보임. 모듈화 하기엔 별로
이유가 없을듯."*

초안:
- **`Deque` 는 트레이트 이름이 됩니다**(`src/Traits/Deque.luau`): 필수 `PushFront`·`PushBack`·`PopFront`·`PopBack`·
  `Front`·`Back`. 종류를 모르는 코드는 `Deque.PushBack(d, v)`.
- 지금의 링 버퍼 모듈은 **`CircularDeque`** 로 이름을 바꾸고, 노드로 이은 **`LinkedDeque`** 를 더합니다. 둘 다
  `Deque`·`List`·`Collection` 을 구현합니다(`LinkedDeque` 의 `List` 위치는 노드).
- 한쪽 끝만 쓰는 좁은 계약(**`Stack`**: `Push`·`Pop`·`Peek`, **`Queue`**: `Push`·`Pop`·`Peek`)은 **`Deque` 에 의존하는,
  필수 함수 없는 트레이트**로 둘 수 있습니다 — 그러면 `Deque` 를 구현한 종류는 등록 없이 스택·큐가 됩니다(1단계의
  "저절로 따라오는 구현" 이 정확히 이 쓰임). `Arr` 은 `Stack` 만 직접 구현.
- 단방향으로 이은 리스트는 꼬리 쪽을 지울 때 앞 노드를 찾아 꼬리 포인터를 고쳐야 합니다(O(n)) — 사용자 말대로 **그
  구현 안에서 직접** 합니다(공용 조각으로 빼지 않음). 그래서 양끝 큐는 양방향(연결 칸 1 = 앞, 2 = 뒤)으로 하고,
  단방향 리스트를 따로 둘지는 부르는 곳이 보일 때.
- 잴 것: 길이별 `PushBack`/`PopFront` 에서 원형 대 연결(perf 24절이 원형 대 `Arr` 만 쟀음), 노드 할당 비용.

### 9-3. 트리 — 부분을 떼어 트리로, 균형 방식의 공유 구현

*"btree 구현은 TreeMap 에 놓지 말고, 과제처럼 바깥에 있고 재사용성 있긴 해야 … 바이너리 노드와 그걸 돕는 도구?
로써 말이야. Trait 으로 두어도 좋고."*, *"완전이진트리에 대한 배열 구현도 배제하는건 아니란거"*, 그리고
*"이진 트리 자료형 같은 경우 부분형으로 뭐보다 크거나 작은 영역을 때어 트리로 놓는것도 가능하잖아. 그것도 가능하게
할 길을 만들 수 있을지 궁금해. 또 트리 구조 제어법도 RB트리나 다양한 방법이 있잖아. 이것도 구현을 도와야하고. 이
공유 구현도 어떻게 둬야할지 고민되더라고"*

초안 — **두 질문의 답이 같은 조각입니다: `Join`.**

균형 이진 탐색 트리의 연산은 전부 "왼쪽 트리 + 가운데 키 + 오른쪽 트리를 균형 맞춰 하나로" 하는 **`Join(left, key,
right)` 하나** 위에 세울 수 있습니다(Blelloch·Ferizovic·Sun 의 join-based 구성 — AVL·레드블랙·무게 균형·트립 넷 다
`Join` 만 다르고 나머지는 같은 코드).

| 층 | 무엇 | 어디 |
|---|---|---|
| 노드 | 연결을 번호 칸에 둔 일반 노드(이진이면 1 = 왼쪽, 2 = 오른쪽), 읽기 노드/고칠 수 있는 노드 타입 | 노드 조각(컨테이너 밖) |
| 노드 도구 | 잇기·떼기, 회전, 자식 바꾸기 — 균형 방식들이 `Join` 을 쓸 때 쓰는 재료 | 같은 곳 |
| `Tree` 트레이트 | 필수: 뿌리·자식·값(위치는 제네릭 — 노드든 배열 인덱스든). 기본 구현: 전위·중위·후위·층별 순회, 높이, 세기 | `Traits/Tree` |
| **`SearchTree` 트레이트**(이름 잠정) | **필수: `Join` 하나**(+ 노드에 균형 정보 한 칸 — 높이·색·크기·우선순위). 기본 구현: `Split(tree, key) → (작은 쪽, 찾은 값, 큰 쪽)`, 넣기·지우기, 합집합·교집합·차집합, 구간 떼어내기 | `Traits/SearchTree` |
| 균형 방식 | `Join` 의 구현 하나씩(AVL 부터, 레드블랙·트립은 같은 틀로 추가) — 빠른 넣기/지우기가 필요하면 같은 이름으로 재정의(리스트에서 `Arr` 가 기본 구현을 재정의하는 것과 같음) | 방식마다 파일 하나 |
| `TreeMap`/`TreeSet` | 키-값 계약과 조립만 | `Collections/` |

- **"뭐보다 크거나 작은 영역을 떼어 트리로"** 는 `Split` 그 자체입니다(O(log n), 결과 둘 다 같은 종류의 온전한 트리).
  `[lo, hi]` 구간은 `Split` 두 번. Rust `BTreeMap::split_off` 와 같은 결(원본에서 떼어 냄).
- 떼어 내지 않고 **보기만** 하는 길도 값쌉니다: 구간을 든 읽기 뷰(O(1) 로 만들고, 순회·조회만 — Java 의 `subMap`).
  읽기 트레이트(`Tree`·`Map` 의 읽는 쪽)를 구현하면 종류를 모르는 코드가 그대로 받습니다. 지금 `TreeMap` 의 구간
  함수들은 새 목록을 만들어 돌려주는데, 그 사이의 선택지입니다.
- **공유 구현을 두는 자리**가 `SearchTree` 의 기본 구현입니다 — 균형 방식을 새로 만드는 사람은 `Join` 만 쓰면 나머지를
  받습니다("프리미티브만 주면 알고리즘이 따라온다" 의 트리 판).
- ⚠️ 대가: `Join` 위의 넣기는 직접 회전하는 넣기보다 상수 배 느립니다(내려가며 쪼개고 올라오며 잇기). 얼마나인지는
  재야 합니다 — 4절의 "기본 구현은 1.1~3.8배" 와 같은 종류의 질문이고, 느리면 방식이 `Insert` 를 재정의합니다.
- 배열에 담은 완전 이진 트리(`Heap`)는 `Tree`(읽기·순회)는 구현하지만 `SearchTree` 는 아닙니다(잇기가 없음).
- 다진 트리(B-트리)·트라이는 이진이 아니라 같은 노드(번호 칸이 여럿)를 쓰되 `SearchTree` 와는 다른 계약입니다 —
  트라이는 9-1 의 목표라 그때 따로 봅니다.

**[같은 날 잰 것]** ① 노드 모양 — perf 34절(값 필드 + 번호 칸이 이름 필드만 쓰는 노드보다 순회 0.55~0.67배, 메모리
0.64배). ②·③ `Join` 시제품 — perf 36절, `.claude/research/tree-join/`: **`Split` 은 크기와 무관하게 약 2μs**(정렬 배열을
두 조각으로 복사하면 1만 개에 22μs, 10만 개에 300μs 이상), `Join` 위의 넣기는 직접 회전의 **2.0~2.2배**이지만 10만
개에서 지금의 정렬 배열보다 3.5배 빠름. 즉 "떼어 내기" 와 "균형 방식의 공유 구현" 은 같은 조각으로 되고, 값은 넣기
2배(느리면 그 방식이 `Insert` 를 재정의). ⚠️ 조회 숫자가 perf 30절과 어긋나 같은 표면으로 다시 재야 함(36절).
남은 확인: 이 모양으로 갈지(트레이트 이름·층), 레드블랙을 같은 틀로 하나 더 써 보고 `Join` 만 다르다는 것을 확인.

### 9-4. 사용자 답 — 층은 이렇게 (2026-10-13)

*"AVL 이 좀 그렇네. 구현체로 때어 두는건 좋은데 실제 제품에서는 RB 가 들어가긴 해야겠다 싶음. 노드단 도구와(읽기
read, 쓰기 mut, single/double/binary 같은것) 노드에 구현된 next/prev/insertnext/insertprev, ... 등을 사용해 벨런싱
자료 등을 구현하는 트리부, 여기에 AVL/RB등이 있고. 아마 완전이진 같은 경우는 배열식, 노드식 둘을 제공하는 방향이
되어야할듯 해보임. 그런걸 가지고 다시 조립해 원하는 자료형을 만드는걸 넣는, 아마 너가 생각한것과 유사한 층이 될것
같아."*

정해진 층(아래에서 위로):

| 층 | 무엇 | 어디(이름은 잠정) |
|---|---|---|
| 1. **노드단 도구** | 일반 노드(값 필드 + 번호 칸)와 타입 둘(읽기 `NodeRead`, 쓰기 `Node`). 연결 방식별 도구: **단방향**(다음), **양방향**(앞·뒤 — `InsertNext`·`InsertPrev`·`Unlink`), **이진**(왼쪽·오른쪽 — 회전, 자식 바꾸기, 중위 다음/이전, 처음/끝) | `src/Node.luau`(`Node.Single`·`Node.Double`·`Node.Binary`) |
| 2. **트리부** | 노드 도구로 짠 균형 방식 — **AVL, 레드블랙**. 방식마다 파일 하나. 완전 이진 트리는 **배열식·노드식 둘** | `src/Trees/` |
| 3. **조립** | 그 조각들로 만든 자료형 — `TreeMap`/`TreeSet`(**제품의 균형 방식은 레드블랙**), `LinkedDeque`, `Heap`(완전 이진의 배열식) | `src/Collections/` |

- AVL 은 구현체로 남기되 `TreeMap` 은 **레드블랙**으로 조립합니다(넣기·지우기의 회전 수가 적음 — 넣고 빼기가 잦은
  게임 쪽 쓰임에 맞음. 숫자는 들일 때 AVL 과 나란히 잼).
- 9-3 의 `Join` 공유 구현은 **트리부 안의 공유 조각**으로 둡니다: 균형 방식이 `Join` 을 주면 `Split`·합집합 등은 한
  번만 씀. 넣기·지우기는 방식이 직접 회전으로 가질 수 있음(시제품에서 `Join` 위의 넣기는 직접의 2배 — perf 36절).
- 노드 도구는 **컨테이너의 뜨거운 자리에서 꼭 거치지 않아도 됩니다**(생성자를 직접 쓰는 것과 같은 이유 — perf 34절).
  위치 연산처럼 드문 자리와 바깥 구현자를 위한 것. 어디까지 도구를 거칠지는 자리마다 재서 정합니다.

**[같은 날 이어서 받은 것]** *"Node 는 한 파일에 있는게 좀 그렇네 … Trees 처럼, Node 폴더 만들고 분리"* → `src/Node/`.
*"AVL 도 있어도 되긴 해. 버리진 말고 추출해서 Trees 안에"* → `src/Trees/Avl.luau`(레드블랙과 같은 표면).
*"트리 순회자 그런것도 Trees 폴더에 … 자가균형 같은 경우는 Insert, Remove 를 계약으로 하나의 추상화를 둘 수 있을법
한데. 트리 쓰는 곳에서 자가균형을 뭘로 할 지 default 가 있고, 직접 선택도 가능한 구조"* → 계약 `Search.Balance`
(두 모듈이 그대로 그 모양), 조립하는 쪽이 기본값(레드블랙)과 선택 인자를 가짐. 실측은 perf 37절.
