## 1. 지금 어디에 있는가

| 원래 구상(`container-design-notes.md` 2·11절) | 지금 |
|---|---|
| 리스트는 위치 프리미티브 다섯만 구현하고, 순회만으로 되는 알고리즘은 소스에 한 번만 | `Arr` 가 연산 103개를 직접 구현. `Deque` 는 `Map`·`Filter`·`Fold` 가 없음. `Algorithm` 은 함수 일곱 |
| 위치 타입 `I` 가 제네릭 — 연결 기반이면 노드가 곧 위치 | `I = number` 인 구현 둘뿐(`Arr`, `Deque`). 노드 기반 구조가 없음 |
| "두 번째 구현체가 생기면 공용 알고리즘을 다시 본다" | `Deque` 가 들어온 뒤(10-07) 다시 보지 않음 |
| — | `TreeMap` 은 이름만 트리(정렬 배열 + 이분 탐색). 트리 노드·순회 없음 |
| — | `Trait` 는 `[토큰] = 구현` 표까지. 기본 구현도 트레이트 사이의 관계도 없음 |

성능을 이유로 "각 컨테이너가 자기 표현으로 직접" 을 계속 골랐고(선택마다 실측 근거는 있었음), 공용 구조 쪽은
"부르는 곳이 보이면" 에 걸려 자라지 않았습니다. 11절이 걱정하던 타입 제약(체이닝이 죽음)은 M0 에서 콜론 메소드를
없애며 사라졌는데, 그 뒤에도 돌아보지 않았습니다.

## 2. 예전 과제에서 가져오는 것과 가져오지 않는 것

과제의 구조(다시 풀어 적음):

- **필수 연산만 구현하면 나머지는 인터페이스의 기본 구현이 준다.** 이진 트리 인터페이스가 "루트·왼쪽·오른쪽·부모·값"
  다섯을 요구하고, 잎 판정·높이·전위/중위/후위 순회·출력은 그 다섯으로 인터페이스 안에 한 번만 적혀 있습니다.
- **위치의 타입이 구현마다 다르다.** 노드로 이은 트리에서는 노드가 위치이고, 배열에 담은 완전 이진 트리에서는
  인덱스가 위치입니다 — 같은 기본 구현이 양쪽에서 돕니다(지금 리스트 계약의 `I` 와 같은 생각).
- **노드가 컨테이너 바깥의 층이다.** "읽을 수 있는 노드" → "고칠 수 있는 노드" → 그 노드를 조립한 트리 → 그 위의
  이진 탐색 트리. 트리는 노드의 모양을 다시 정하지 않습니다.

**가져오지 않는 것**(사용자): 과제에서는 구현 클래스가 자기가 만족하는 인터페이스를 **전부 자기 선언에 나열**했습니다.
그러면 새 인터페이스를 더할 때마다 이미 있는 구현을 전부 고쳐야 합니다. 여기서는 **트레이트가 자기에게 필요한 것을
알고**, 그걸 갖춘 종류는 등록 없이 따라옵니다(Rust 의 `impl<T: List + Build> Seq for T`).

## 3. 모양 (시제품 `Trait2.luau`·`Traits.luau`)

```lua
-- 트레이트: 필수 함수 + 기본 구현 + 의존
local List = Trait.New("List", {
	required = { "Get", "FirstIndex", "LastIndex", "NextIndex", "PrevIndex" },
	defaults = function(impl, full)
		const get, first, nextIndex = impl.Get, impl.FirstIndex, impl.NextIndex   -- upvalue 로 잡음
		return {
			Fold = function(self, init, fn) … end,
			IndexOf = function(self, item) … end,
			Contains = function(self, item) return full.IndexOf(self, item) ~= nil end,  -- 재정의된 판을 씀
		}
	end,
})
local Build = Trait.New("Build", { required = { "New", "PushBack" } })
local Seq = Trait.New("Seq", {                     -- Map·Filter: 같은 종류를 돌려줌
	required = {},
	requires = { List, Build },                    -- ← 의존 (Rust 의 where)
	defaults = function(_impl, _full, deps) … deps[List].Get … deps[Build].PushBack … end,
})
```

| 성질 | 어떻게 |
|---|---|
| **기본 구현** | 구현이 필수 함수만 주면 나머지는 트레이트가 채움. 같은 이름을 주면 그것이 이김(재정의) |
| **등록 때 한 번 합침** | `Trait.Impl` 이 "기본 구현 + 구현이 준 것" 으로 완성 표를 만들어 얼려 둠 → 호출 비용은 지금의 조회와 같음 |
| **의존** | `requires` 의 트레이트를 구현하지 않은 종류는 등록이 거절됨. 기본 구현은 의존 트레이트의 완성 표를 받음 |
| ⭐ **저절로 따라옴** | 필수 함수가 없는 트레이트(`Seq`)는 **등록이 필요 없음** — 의존을 다 갖춘 종류면 처음 쓸 때 만들어 캐시. 컨테이너는 자기가 아는 것만 등록 |
| **바깥에서 더하기** | 새 트레이트를 정의하면 이미 있는 컨테이너 전부에 적용됨(시제품의 `Stats` — `Arr`·`Deque`·`LinkedList` 를 고치지 않음) |
| **빠른 판** | 재정의하고 싶은 종류만 따로 등록(`Arr` 는 `Seq` 를 자기 `Map`·`Filter` 로) |

지금 저장소와의 관계: `Trait.Impl(Trait.List, TOKEN, ArrModule)` 처럼 **모듈 테이블을 그대로** 넘기는 지금 방식이면,
모듈에 같은 이름의 함수(`Arr.Fold`, `Arr.IndexOf`)가 있는 것만으로 재정의가 됩니다 — `Arr` 쪽은 고칠 것이 없고,
`Deque` 는 프리미티브만으로 나머지를 받습니다. 10-12 에 넣은 "필수 함수 목록 검사" 는 이 모양의 `required` 입니다.

## 4. 실측 (`bench.luau`, `-O2`, 21회 최소)

| 일 | N=10 | N=1000 | N=100000 |
|---|---|---|---|
| `Fold` — `Arr.Fold` 직접 | 0.16us | 13.9us | 1.37ms |
| 종류를 모르는 진입점 경유, `Arr` 는 재정의(= 직접 구현) | 1.35배 | 1.05배 | 1.04배 |
| `Arr` 가 **기본 구현**을 쓴다면(프리미티브 경유) | 2.47배 | 2.66배 | 2.62배 |
| `Deque` 기본 구현 대 손으로 쓴 `Deque.Iter` 루프 | 1.65배 | 1.72배 | 1.72배 |
| `LinkedList` 기본 구현 대 손으로 쓴 노드 루프 | 3.74배 | 3.81배 | 3.46배 |
| `Map` — `Arr` 기본 구현 대 `Arr.Map` 직접 | 1.73배 | 3.13배 | 2.98배 |
| `Map` — `Deque` 기본 구현 대 손으로 쓴 루프 | 1.12배 | 1.15배 | 1.33배 |

- **재정의한 종류는 잃는 것이 없습니다** — 진입점 경유 비용(호출당 ~60ns)뿐.
- **기본 구현은 직접 구현의 1.1~3.8배.** 원소마다 프리미티브를 간접 호출하기 때문입니다(설계 노트의 2.5~2.8배와
  같은 크기). "없는 것" 과 비교할 자리이고, 빨라야 하면 재정의합니다.
- 기본 구현을 종류마다 클로저로 특수화하는 것(upvalue)과 구현 표를 인자로 받는 일반형의 차이는 5% 안팎 —
  특수화는 속도보다 "완성 표에 그대로 들어간다" 는 모양 때문에 고릅니다.
- **저절로 따라오는 구현의 조회**: 처음 3.3us(만들기), 그 뒤 호출당 33ns(표를 직접 조회하면 15ns).

## 5. 타입 — 서는 것과 안 서는 것 (`Algo.luau`·`types.luau`)

- **합쳐진 표는 타입 검사기가 모릅니다**(런타임에 만들어짐). 그래서 타입은 지금의 `Algorithm` 처럼 **진입점 한 곳**에
  적습니다. 종류를 아는 코드는 `Arr.Fold`, 모르는 코드는 `Algorithm.Fold` — 트레이트 마커에서 원소 타입을 추론.
  시제품의 대조: POS 8줄 0건, NEG 6줄 전부 에러(반환 타입, 원소 타입, 맵을 리스트 자리에, 빌린 참조에 쓰기).
- **"같은 종류인데 원소 타입만 다른 컨테이너" 를 적을 수 없습니다**(고차 종류 없음). 그래서
  - 원소 타입이 **그대로**인 것(`Filter`)은 넣은 타입 그대로: `<C, E, I>(list: C & ListMarker<E, I>, pred): C` ✅
  - 원소 타입이 **바뀌는** 것(`Map`)은 결과를 담을 **목적지 인스턴스**를 받음:
    `MapInto(list, fn, into: D & ListMarkerMut<G, J>): D` ✅ — 질문 AR(묶기의 결과 컨테이너)과 같은 모양입니다.
    즉 "모을 곳을 호출자가 정한다" 가 묶기만의 규칙이 아니라 이 구조 전체의 규칙이 됩니다.
- 기본 구현의 **안쪽**은 `any` 입니다(완성 표가 `any` 를 거침). 타입 안전은 진입점의 서명까지 — 지금 트레이트와 같습니다.
- 새 솔버의 한계(제네릭 함수를 든 테이블을 인자로 넘기면 추론 실패)는 이 모양에서 밟지 않습니다 — 구현은 인자가
  아니라 토큰으로 찾습니다.

## 6. 노드와 트리 (`Node.luau`·`Containers.luau`)

- **노드는 평범한 테이블 + 서비스 함수**: `ListNode = { value, prev, next }`, `TreeNode = { value, left, right, parent }`,
  잇기·끊기는 `Node.LinkAfter`/`Unlink`/`SetLeft`/`SetRight`. "데이터는 엔티티, 함수는 서비스" 그대로입니다.
- **`LinkedList`**: 노드를 조립. 위치(`I`)가 **노드** — `Get(list, 3)` 은 타입 에러. 프리미티브 다섯 + `New`·`PushBack` 만
  구현하고 `Fold`·`Find`·`Contains`·`Map`·`Filter` 를 받습니다(`Count` 는 크기를 아니까 재정의).
- **`Tree` 트레이트**: 필수 넷(`Root`·`Left`·`Right`·`Value`) → `IsLeaf`·`Height`·`Size`·전위/중위/후위 순회.
  구현 둘이 같은 순회 결과를 냅니다: 노드 트리(그 위에 이진 탐색 트리의 `Insert` 하나)와 배열에 담은 완전 이진 트리
  (위치가 인덱스, `Height` 는 계산으로 재정의).
- 시제품은 이진 트리까지입니다. 자식이 여럿인 일반 트리는 필수 연산이 달라(`Children`) 트레이트를 따로 둡니다 — 미시제품.

## 7. 들이는 순서(제안)

| 단계 | 무엇 | 지금 코드에 미치는 것 |
|---|---|---|
| 1 | `Trait` 에 기본 구현·의존·저절로 따라오기 | 트레이트 넷은 그대로 동작. 10-12 의 `required` 를 이 모양으로 합침 |
| 2 | 리스트 알고리즘을 `List` 의 기본 구현으로 + `Algorithm` 진입점 | `Arr` 는 모듈을 그대로 등록해 전부 재정의(변화 없음), `Deque` 가 알고리즘을 얻음 |
| 3 | `Build`(같은 종류 만들기)와 묶기(질문 AR) | `GroupBy`·`CountBy`·`KeyBy` 의 결과 컨테이너. 누적 방식은 별도 의견을 받는 중 |
| 4 | 노드 조각, `LinkedList`, `Tree` 트레이트와 노드 트리 | 새 모듈. `TreeMap`(정렬 배열)은 그대로 두고 같은 `Map` 트레이트의 다른 구현으로 |

각 단계는 지금까지처럼 구현 → 테스트 → 음성 대조군 → 리뷰 소진으로 닫습니다.

## 8. 정해야 할 것 — 2026-10-13 답

> 1. **들임, 전부 이 방향으로.** 2. `Algorithm` 은 **작게 시작해 점점 늘림**.
> 3. **덮어써도 됨** — 사용자: *"어차피 정의가 다 끝나야 리턴받지 않음? 따라온 것도 덮어쓰는건 문제 없지 않나. 기본
>    함수들이 똑같은 방법으로 impl 을 찾아내려 할거니까, 온 디멘드로?"* → 저절로 따라온 구현 위에 재정의를 등록하는
>    것은 허용. 그러려면 구현 방식이 따라야 합니다: 완성 표를 **새로 만들어 갈아 끼우지 않고 같은 표를 제자리에서
>    고치고**, 기본 구현은 의존 표의 함수를 등록 때 붙잡아 두지 않고 **부를 때 표에서 꺼냅니다**(호출당 테이블 조회
>    하나 — 원소마다가 아님). 시제품은 등록 때 붙잡는 판이라 이 부분을 바꿔 들입니다. (명시적으로 등록한 구현을 또
>    등록하는 것은 지금처럼 에러 — 내장 구현이 조용히 바뀌지 않게, 10-06 결정.)
> 4. **다른 이름 허용** — *"함수의 네임스페이스 자체가 다른거니까."* 트레이트마다 자기 어휘를 씁니다.
> 5. `TreeMap` — 정렬 배열이 "보통의 정의" 가 아니라는 지적. 실측(perf 30절): 무작위로 넣기는 ~수천 개까지만
>    배열이 빠르고 10만 개에선 5배 느림, 조회는 지금 구현이 노드 트리의 절반. **이름·구현을 어떻게 할지 여쭘.**
> 6. 일반 트리·연결 리스트의 표면은 **조금 더 보고**.

1. **이 방향으로 들일지**, 들인다면 위 순서와 범위(전부 / 1~2단계만 먼저).
2. **`Algorithm` 을 어디까지 넓힐지.** 순회만으로 되는 `Arr` 연산은 수십 개입니다. 설계 노트 10절의 교훈("안 쓴 것은
   안 만든 것보다 나쁘다")과 "프리미티브만 주면 다 된다" 사이의 선을 어디에 그을지 — 제 생각은 읽기(접기·찾기·세기)와
   거르기·옮기기 정도의 작은 묶음에서 시작.
3. **재정의의 시점.** 저절로 따라온 구현을 이미 쓴 뒤에 그 종류가 재정의를 등록하면 — 에러로 할지, 갈아 끼울지.
   (제 생각은 에러: 같은 호출이 등록 순서에 따라 다른 함수를 부르면 안 됨.)
4. **한 종류가 두 트레이트에서 같은 이름을 가질 때**(예: `List.Count` 와 `Collection.Len` 은 같은 뜻의 다른 이름).
   이름 어휘를 트레이트끼리 맞추는 규칙이 필요합니다.
5. **`TreeMap` 의 이름.** 정렬 배열 판을 그대로 `TreeMap` 이라 부를지(Java 계보 이름), 노드 트리 판이 생기면 가를지.
6. **일반 트리**(자식 여럿)·양방향 연결 리스트의 표면을 어디까지 — 과제에서 중요했던 순회·삽입·삭제 기준으로.

## 9. 한계

- 기본 구현은 느립니다(4절). 컨테이너를 만든 사람이 "되긴 하는데 느리다" 를 모르고 넘어갈 수 있어, 재정의할 가치가
  큰 함수(접기·옮기기)는 문서에 표시합니다.
- 타입은 진입점까지입니다(5절). 기본 구현을 쓰는 사람이 서명을 잘못 적어도 검사기가 잡지 못합니다 — 테스트(구현을
  바꿔 끼워 같은 답이 나오는지)로 지킵니다. 지금 `spec.contracts` 가 하는 일의 확장입니다.
- 시제품은 에러 규약(`Common.raise`)·구멍(`nil` 원소)·읽기 전용 마커와의 세부 맞춤을 다루지 않았습니다.
