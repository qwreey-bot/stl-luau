## 1. 확정 — `type function` 을 쓰지 않습니다

**이 저장소에서 `type function` 기반 설계를 더 밀지 않습니다.** quad 이
같은 길을 가서 부작용으로 대부분 폐기했습니다.

이미 기록돼 있던 함정들(`.claude/conventions.md`):

- `type function` 안에서 같은 파일의 바깥 로컬을 참조하면 **컴파일 실패**
- `error()` 대신 `print()` + `types.never` 를 써야 진단이 노출됨
- 어떤 타입이 `type function` 을 **한 번 통과하면**(그냥 `return t` 라도)
  그 뒤 제네릭 `self` 메소드 체이닝이 **조용히 깨짐**

마지막 항목이 특히 이 저장소와 정면으로 부딪힙니다 — 여기는 **체이닝이
공개 표면의 핵심**입니다(`Arr:Map():Filter():Sort()`).

## 3. 튜플이 필요하기는 한가 — 아마 아닙니다

사용자: *"지금은 필요하다고 안 보이고, 안 만들어도 되지 않을까 생각함."*

Luau 에는 이미 다중 반환이 있고, 이 저장소에는 **`Arr` 가 있습니다.**
튜플이 주는 것 중 `Arr` 로 안 되는 것:

| 튜플이 주는 것 | `Arr` 로 되는가 |
|---|---|
| 길이가 타입에 박힘 | ❌ (그게 type function 이 필요했던 이유) |
| 원소마다 타입이 다름 | ❌ |
| 다중 반환을 값으로 담기 | ✅ `Arr.Pack` … 이었는데 `Of` 와 같아서 뺐습니다 |
| 다중 반환으로 풀기 | ✅ `:Unpack()` |

**타입 수준 이득 둘은 `type function` 없이는 못 얻습니다.** 그걸 포기하기로
한 이상, 남는 것은 `Arr` 가 이미 하는 일입니다.

### B. `select` 를 쓰는 형식

사용자 언급: *"`select(Tup:all(), 1)` 같은 형식으로 선택하는게 나을지도."*

읽으면, 튜플이 **다중 반환을 돌려주는 객체**이고 선택은 Lua 기본
`select` 에 맡기는 모양입니다. 타입 수준 길이 추적을 포기하는 대신
**런타임이 단순하고 Lua 관례와 맞습니다** — 이 저장소가 구간 규약에서
이미 택한 것과 같은 태도입니다(*"호스트 언어와 어긋나는 게 더 큰 비용"*).

인자 순서는 확인이 필요합니다. Lua 의 `select` 는 `select(n, ...)` 라
`select(1, Tup:All())` 이 자연스러워 보입니다.
