## 1. 개요 및 핵심 요약

Luau 표준 라이브러리 `stl-luau`의 트레이트(인터페이스) 타입 설계를 둘러싸고, 세 자리(**정의하는 사람**, **등록하는 사람**, **쓰는 사람**)의 관점에서 후보 A(v6), B(v8 인라인), B'(v8 모드 명시), C(표 분리)를 다각도로 평가했습니다.

사용자는 v5를 검토하며 다음과 같이 토로했습니다:
> *"다시 DX가 나빠진다는게 좀 흠이네. Trait() 밖 까지 나가버리니까 뭔가뭔가가 되었음 mut 이란것도 조금 그렇게 보이는 느낌.. 타입을 맞추다가 DX가 나빠진것같아. 내가 원하는 방향도 있겠지만 객관적으로 원해지는 방향도 중요."*

DX 팀은 **"정의자의 작성 편의"**뿐만 아니라 **"외부 생태계 컨테이너 작성자(등록자)의 하위 호환성과 등록 간결성"**, 그리고 **"소비자(쓰는 사람)가 누려야 할 오류 없는 안전성"**을 객관적 지표로 삼아 분석했습니다.

### 핵심 결론 및 순위 요약

| 순위 | 후보 | 정의자 DX | 등록자 DX (외부 생태계) | 쓰는 사람 DX / 견고함 | 종합 평가 |

| 2위 | **B'** (v8 모드 명시) | 보통 (정의가 밖으로 나감) | 우수 (2줄 등록, 기본 구현 생략 가능) | **최상 (같은 모듈 구멍 없음)** | 견고하나 등록에 2줄 필요 |

### 대발견: `table.freeze`를 통한 "한 줄 등록" 실현 (변형 D)
Luau 소스 분석에서 밝혀진 *"받는 타입의 필드가 `read`이면 표 리터럴을 인자 자리에 직접 넘겨도 서브타입 검사가 통과하고 NEG가 잡힌다"*는 원리를 바탕으로 실측을 진행한 결과, **`table.freeze({ ... })`로 반환된 테이블의 모든 프로퍼티가 Luau 검사기에서 자동으로 `read` 프로퍼티로 추론**된다는 사실을 실측으로 입증했습니다.

이를 통해 외부 컨테이너 작성자는 중간 지역 변수 없이 **단 한 줄**로 등록할 수 있습니다:
```lua
Stack.ImplFor<<Arr<A>, A>>(ARR, {
    Push = Arr.PushBack,
    Pop = Arr.PopBack,
    Peek = arrPeek,
})
```
필수 메서드 누락, 시그니처 불일치, 잘못된 재정의 모두 `luau-analyze`에서 완벽하게 차단됩니다 (실측 입증).

## 2. 세 자리 관점의 후보별 심층 평가 (A · B · B' · C)

### 2.1 정의하는 사람 (Trait Author / Core Library)
- **후보 A (v6)**:
  - `const List = Trait.Trait("List", function<Self, E, I>(of: ...) return { Get = Fn...(), IndexOf = Default(...) } end)`
  - 장점: `mode` 매개변수 없음, 2중 람다 없음, `Trait()` 안에서 인라인 완결. 정의자 관점에서는 가장 아름답고 직관적임.
- **후보 B (v8 인라인)**:
  - `const List = Trait.Trait("List", function<M>(mode: M) return function<Self, E, I>(of: ...) return { ..., IndexOf = Default(mode, ...) } end end)`
  - 머리 한 겹(`function<M>(mode: M)`)과 `Default(mode, ...)`가 추가되지만 여전히 `Trait()` 안에서 완결됨.
  - 단점: 같은 모듈 안에서 기본 구현 반환 타입이 `never`가 되는 치명적 구멍이 잠복함.
- **후보 B' (v8 모드 명시)**:
  - `local function listDef<M>(mode: M) return ... end`
  - `const List = Trait.Trait("List", listDef<<"full">>, listDef<<"impl">>)`
  - 단점: 정의 함수가 `Trait()` 밖으로 분리됨. 사용자가 "DX가 나빠졌다"고 지적한 형태.
  - 실질적 평가: 임시 함수 선언 1개와 모드 명시 2개가 추가되지만, 어차피 모듈 레벨에서 `export type List`, `export type ListImpl`을 선언하므로 모듈 단위 코드 배치상 큰 이질감은 아님.
- **후보 C (표 분리)**:
  - `listReq()`, `listDefaults()` 두 개로 함수를 쪼개고, 타입 정의에서 기본 구현 필드 이름들을 일일이 `IndexOf: typeof(...)?, Fold: typeof(...)?, ...`로 나열해야 함. 상용구 최악.

### 2.2 등록하는 사람 (Container Author / External Ecosystem)
트레이트 시스템에서 가장 많은 코드가 작성되는 자리이자, 서드파티 개발자가 직접 마주하는 접점입니다.

- **후보 A (v6)**: **최악 (Unacceptable)**
  - 등록 표에 기본 구현 칸을 전부 수동으로 채워 넣어야 함: `IndexOf = Trait.Inherit, Contains = Trait.Inherit, Fold = Trait.Inherit`.
  - 실수로 필수 칸에 `Inherit`을 넣어도 타입 레벨에서 0건으로 통과하고 런타임에서만 터짐.
  - ⭐ **치명적 하위 호환성 파괴 (Breaking Changes on Extension)**:
    만약 `stl-luau` 1.1에서 `List` 트레이트에 기본 구현 `Count`를 추가하면, 기존의 모든 사용자 컨테이너 코드가 `missing field 'Count'`로 타입 에러를 내며 컴파일이 깨집니다. 라이브러리의 건강한 성장을 가로막는 치명적 결함입니다.
- **후보 B / B'**: **우수 (Good)**
  - 기본 구현 칸은 안 적으면 기본 구현 사용, 적으면 재정의(override).
  - 트레이트가 확장되어 기본 구현이 추가되어도 기존 컨테이너 코드가 전혀 깨지지 않음.
  - 단, 기존 B/B'는 `const arrStack: StackImpl<Arr<A>, A> = { ... }`, `Stack.ImplFor(ARR, arrStack)`로 반드시 2줄에 걸쳐 중간 변수를 만들어야 했음.
- **후보 C**:
  - 기본 구현 생략 가능하나 타입 정의가 복잡함.

### 2.3 쓰는 사람 (End User / Consumer)
- **후보 A & B'**:
  - `List.Of(d).IndexOf(d, 2)` 형태로 호출하며, 같은 모듈이든 다른 모듈이든 반환 타입과 매개변수 타입이 100% 견고하게 검사됨.
- **후보 B (인라인)**: **치명적 구멍 (Soundness Hole)**
  - 다른 모듈에서 임포트할 때는 정상 동작하지만, **트레이트를 정의한 같은 모듈** 안에서 `Stack.Of(a).IsEmpty(a)`를 호출하면 반환 타입이 `never`가 됨.
  - 서브타이핑에서 `never <: T`가 성립하므로, `local s: string = Stack.Of(a).IsEmpty(a)` 처럼 완전히 틀린 타입에 대입해도 타입 검사기가 0건으로 통과함 (`main-v8-same-module-hole.luau` 실측).
  - 라이브러리 내부 테스트나 단일 파일 스크립트 작성 시 버그를 숨김.
- **후보 C**:
  - 타입 에러 발생 시 노출되는 타입 메시지가 거대한 교집합 타입(`{ Get: ... } & { IndexOf: ... }`)으로 오염되어 가독성이 심각하게 저하됨.

## 3. ⭐ 변형 D 제안: "한 줄 등록"과 "완전한 견고함"의 결합

### 3.1 발상의 전환과 핵심 기제

사용자가 느낀 "타입을 맞추다가 DX가 나빠졌다"는 아쉬움을 해소하기 위해, DX 팀은 두 가지 핵심 메커니즘을 결합한 **변형 D**를 제안합니다:

1. **`table.freeze`를 통한 `read` 프로퍼티 자동 생성 [실측 대발견]**:
   - Luau 0.742 소스 분석에 따르면 표 리터럴 인자 전달 실패의 근본 원인은 invariant(읽기쓰기) 필드 비교 실패 및 캐시 오염 때문이었습니다.
   - 팩토리 함수에서 `return table.freeze({ Push = ..., Pop = ..., IsEmpty = Default(...) })`로 반환하면, **반환 타입의 모든 프로퍼티가 자동으로 `read` 프로퍼티로 추론**됩니다.
   - 따라서 수동으로 복잡한 유틸리티 타입을 만들 필요 없이, 표 리터럴을 인자 자리에 직접 넘길 수 있게 됩니다!
2. **트레이트 객체에 특화된 `ImplFor` 바인딩 [실측 확인]**:
   - 트레이트 정의 모듈에서 `rawStack.ImplFor :: StackImplFor`로 바인딩하여 트레이트 객체 `Stack`을 노출합니다.
   - 외부 컨테이너 작성자는 중간 변수 없이 **단 1줄**로 컨테이너를 등록할 수 있습니다:
     `Stack.ImplFor<<Arr<A>, A>>(ARR, { Push = Arr.PushBack, Pop = Arr.PopBack })`
3. **모드 명시를 통한 `never` 구멍 박멸 (B'의 견고함 계승)**:
   - 인라인 람다의 제네릭 `M`이 오버로드 매칭 시 풀리지 않는 상류 솔버 결함을 우회하기 위해, 정의 함수를 모드 명시(`stackDef<<"full">>, stackDef<<"impl">>`)로 전달하여 같은 모듈에서도 100% 안전성을 확보합니다.

### 3.2 변형 D 실물 코드 구조

#### (1) 트레이트 정의 모듈 (`src/Traits/Stack.luau` 예시)
```lua
--!strict
local Trait = require("../Trait")

type Item<T> = Trait.Item<T>
type Token = Trait.AnyToken
const Fn, Default = Trait.Fn, Trait.Default

-- [1] 정의 팩토리: table.freeze로 감싸 모든 필드를 read 프로퍼티로 생성!
local function stackDef<M>(mode: M)
	return function<Self, T>(of: (Self & Item<T>) | Token)
		return table.freeze({
			Push = Fn<<(stack: Self, item: T) -> Self>>(),
			Pop = Fn<<(stack: Self) -> T?>>(),
			Peek = Fn<<(stack: Self) -> T?>>(),
			IsEmpty = Default(mode, function(ops: any)
				return function(s: Self): boolean
					return ops.Peek(s) == nil
				end
			end),
		})
	end
end

-- [2] 시스템 트레이트 생성 (모드 명시로 never 구멍 원천 차단)
const rawStack = Trait.Trait("Stack", stackDef<<"full">>, stackDef<<"impl">>)

-- [3] 외부 노출 타입 선언
export type Stack<Self, T> = typeof(rawStack.Of<<Self, T>>(nil :: any))
export type StackImpl<Self, T> = typeof(rawStack.ImplOf<<Self, T>>(nil :: any))

-- [4] 1줄 등록용 특화 ImplFor 바인딩
type StackImplFor = <Self, T>(token: Token, impl: StackImpl<Self, T>) -> ()

const Stack = table.freeze({
	Of = rawStack.Of,
	ImplOf = rawStack.ImplOf,
	ImplFor = rawStack.ImplFor :: StackImplFor,
	ImplWhere = rawStack.ImplWhere,
})

return Stack
```

#### (2) 컨테이너 등록 자리 (외부 사용자 컨테이너 또는 `src/Collections/Arr.luau`)
```lua
-- ⭐ 등록이 단 한 줄로 완결! 중간 변수 불필요!
Stack.ImplFor<<Arr<A>, A>>(ARR, {
	Push = Arr.PushBack,
	Pop = Arr.PopBack,
	Peek = arrPeek,
	-- IsEmpty는 생략(기본 구현 사용)하거나 원하는 경우 재정의!
})
```

#### (3) 쓰는 자리
```lua
Stack.Of(arr).Push(arr, 100)
local empty: boolean = Stack.Of(arr).IsEmpty(arr) -- 반환 타입 boolean 완벽 검사!
```

## 5. 상대 팀(타입 안전·견고함 팀)의 예상 반론에 대한 답

### 반론 1. "정의가 `Trait()` 밖으로 나가는 것은 여전히 DX 저하가 아닌가? 인라인으로 적는 B가 더 낫지 않은가?"
**DX 팀의 답변**:
- 우리는 B의 인라인 형태가 시각적으로 매력적이라는 점을 인정합니다.
- 그러나 소프트웨어 공학에서 **"타입 검사가 조용히 사라지는 구멍(`never` 추락)"**이 존재하는 문법은 아무리 겉보기가 예뻐도 라이브러리 코어에 채택될 수 없습니다.
- 트레이트를 정의하는 파일은 라이브러리 전체를 통틀어 불과 10여 개 내외입니다. 반면 그 트레이트를 등록하고 사용하는 코드는 수백~수천 군데에 달합니다.
- 정의자에게 2~3줄의 상용구(함수 분리 및 `ImplFor` 바인딩)를 요구하는 대신, **등록자에게 단 1줄 등록을 선물하고 소비자에게 100% 안전한 타입 검사를 보장하는 것**이 소프트웨어 전체 생태계 관점에서 압도적으로 우월한 DX입니다.

### 반론 2. "후보 A는 정의가 가장 깔끔하고 타입 함수 `index<>`도 안 쓰는데, 바깥 사람이 `Inherit`을 좀 쓰면 안 되나?"
**DX 팀의 답변**:
- 이것은 단순한 타이핑 수고의 문제가 아니라 **라이브러리의 진화 가능성(하위 호환성)**을 파괴하는 문제입니다.
- 표준 라이브러리가 버전 1.1, 1.2로 판올림되면서 트레이트에 유용한 기본 구현 메서드를 추가하는 것은 극히 자연스러운 발전입니다.
- 후보 A에서는 라이브러리가 기본 메서드를 하나 추가하는 순간, 전 세계 모든 외부 사용자 컨테이너 코드가 컴파일 에러(`missing field`)를 뿜으며 깨집니다.
- 또한 필수 칸에 실수로 `Inherit`을 적어도 컴파일러가 침묵하므로, 런타임 크래시가 런타임에 가서야 터집니다. 등록자 DX 관점에서 A는 지속 불가능합니다.

### 반론 3. "변형 D에서 `table.freeze`를 팩토리에 쓰는 것이 런타임 오버헤드가 되지 않는가?"
**DX 팀의 답변**:
- `table.freeze`는 트레이트 정의 시 단 한 번(모듈 로드 시) 실행됩니다.
- Luau에서 `table.freeze`는 VM 최적화에 오히려 도움이 되며, 런타임 루프 안이 아닌 초기화 경로이므로 비용은 0에 수렴합니다.
- 런타임 비용 0으로 컴파일러에게 `read` 프로퍼티라는 완벽한 공변 서브타이핑 힌트를 제공하여 "표 리터럴 1줄 등록"을 가능하게 만드는 것은 극히 효율적인 공학적 선택입니다.

## 6. 결론 및 제안 (사용자 결정을 위한 권고)

- **DX 팀의 최종 추천**: ⭐ **변형 D**
- **근거**:
  1. **등록자 DX의 획기적 개선**: `table.freeze`를 활용하여 중간 변수 없이 **`Stack.ImplFor<<Arr<A>, A>>(ARR, { Push = ..., Pop = ... })`로 1줄 등록 실현**.
  2. **완벽한 하위 호환성**: 기본 구현 칸은 선택적이므로, 트레이트가 성장해도 기존 사용자 코드가 전혀 깨지지 않음.
  3. **견고한 안전성**: 모드 명시(`<<"full">>, <<"impl">>`)를 통해 B의 같은 모듈 `never` 구멍을 완벽히 박멸.
  4. **합리적인 정의자 비용**: 트레이트 정의 모듈에 추가되는 코드는 단 3줄(`StackImplFor` 타입 및 객체 조립)에 불과함.

> 본 보고서의 결론과 변형 D의 도입은 사용자님의 최종 판단을 위한 "제안"입니다.
