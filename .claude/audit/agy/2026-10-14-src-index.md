## 1. 개요 및 요약

stl-luau의 트레이트 시스템 시제품 v5(`.claude/research/trait-v5/`)는 한 번의 정의로부터 완성 표(`Of`)와 등록 표(`ImplOf`)라는 두 보기를 얻기 위해 내장 타입 함수 `index<{ full: F, impl: F? }, M>`를 도입했습니다. 반면 함수 오버로딩(`&`)을 통한 모드 분기는 제네릭 `M` 호출 시 `ambiguous` 에러로 실패했습니다(`.claude/audit/agy/2026-10-14-tr3-noindex-probes/probe3_overload_ambiguity.luau`).

본 보고서는 Luau 타입 검사기(새 솔버) C++ 소스 코드를 면밀히 분석하고 다수의 정밀 프로브를 통해 다음 두 핵심 질문을 검증했습니다:
1. **내장 타입 함수 `index<>`**: 소스 수준의 축약(reduction) 조건, 제네릭/막힌 타입과의 상호작용, `never` 추락 메커니즘, 그리고 트레이트 규모 확장 시 발생하는 잠재적 결함 지점을 규명했습니다.
2. **오버로드 해석의 Ambiguity**: 제네릭 인자 `M`이 전달될 때 왜 두 오버로드가 모두 매칭되는지 소스 수준의 근본 원인(`Subtyping.cpp:830-836`의 임시 `never` 대체 코드)을 규명하고, 오버로드 구문만으로 이를 회피하는 적는 법이 존재하는지 분석했습니다.

### 핵심 결론 요약
- **오버로드 해석 (질문 2)**: 제네릭 `M`을 인자로 넘길 때 모호성 에러가 나는 것은 Luau 서브타이핑 엔진(`Subtyping.cpp:833`)에서 외부 제네릭 `subTy`를 **무조건 `neverType`으로 취급**하기 때문입니다. `never`는 모든 타입의 서브타입이므로(`never <: "full"`, `never <: "impl"`) 인자 개수(arity)가 같으면 **모든 오버로드 분기가 적합 판정**을 받아 `ok.size() > 1`로 모호해집니다. 따라서 동일 인자 개수 환경에서 제네릭 인자만으로 오버로드를 단일 선택하게 만드는 적는 법은 **원천적으로 불가능**합니다 (소스 확정).
- **내장 타입 함수 `index<>` (질문 1)**: `index<{ full: F, impl: F? }, M>`는 제네릭 `M` 상태로 서브타이핑에 진입하면 축약에 실패하여 **`never`** 로 떨어집니다 (`the reduced type is 'never'`). 그러나 시제품 v5의 `Trait.Trait("Name", def, def)` 패턴은 `def`를 호출하는 것이 아니라 **시그니처 레벨에서 `M = "full"`과 `M = "impl"`로 즉시 인스턴스화(Instantiation)** 시킵니다. 인스턴스화 즉시 solver가 `ReduceConstraint`를 디스패치하여 완전히 레코드 타입으로 치환하므로, 외부에 노출되는 완성 표/등록 표에는 `index<>`가 0개로 소멸합니다.
- **스케일 확장 시 발견된 치명적 경계 (실측 대발견)**: 쓰기 함수(`Mut<Self, T, M>`)와 기본 구현(`Default(mode, ...)`)이 **한 트레이트 정의 안에 공존**할 경우, 기존의 `Trait("Name", def, def)`처럼 모드를 생략하면 Luau의 양방향 타입 추론(Bidirectional Type Inference)이 깨지면서 `stackDef`의 반환 타입이 축약되지 않은 `index<>` 채로 남아 거대한 타입 불일치 에러를 냅니다. 이를 방지하려면 **`Trait("Name", def<<"full">>, def<<"impl">>)`처럼 명시적 타입 인자를 공급**해야 합니다 (실측 증명: `probes/probe_scale_simulation.luau`).

## 2. [질문 1] 내장 타입 함수 `index<>` 심층 분석

### 2.1 소스 구현과 축약(Reduce) 조건

- **소스 위치**: `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/BuiltinTypeFunctions.cpp:2140-2272` (`indexFunctionImpl`), line 2274 (`indexTypeFunction`)
- **호출 및 제약 디스패치**: `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/ConstraintSolver.cpp:2726` (`tryDispatch(const ReduceConstraint&)`), `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/Subtyping.cpp:2986` (`handleTypeFunctionReductionResult`)

#### (1) `indexeeTy` (첫 번째 인자: 인덱싱 대상 테이블)의 축약 조건
1. `isPending(indexeeTy, ctx->solver)` (line 2149):
   - `indexeeTy`가 아직 미해결된 `TypeFunctionInstanceType`이거나 `BlockedType`, `PendingExpansionType`, 또는 solver에 미해결 제약이 걸려 있는 경우:
   - `{std::nullopt, Reduction::MaybeOk, {indexeeTy}, {}}`를 반환하며 축약을 **보류(Blocked)** 합니다.
2. `normalizer->normalize(indexeeTy)` (line 2152):
   - 정규화 실패 시 `MaybeOk`로 보류.
   - `indexeeNormTy->shouldSuppressErrors()` (`any` 등): 즉시 `anyType`을 반환하며 축약 성공.
3. 타입 검증 (line 2163-2170):
   - 테이블 또는 extern type(class)이어야 함 (`hasTables() != hasExternTypes()`).
   - `hasTyvars()`(제네릭 변수 포함)이거나, primitive(number, string, boolean 등)가 섞여 있으면:
     `return {std::nullopt, Reduction::Erroneous, {}, {}};` -> **즉시 에러(축약 불가)**.

> **시제품 v5의 쓰임 평가**: `{ full: F, impl: F? }`는 프로퍼티 타입 `F`가 제네릭 변수일지라도 테이블 자체는 구체적인 `TableType`이므로 정규화 시 `hasTables()`가 참이고 `hasTyvars()`는 거짓입니다. 따라서 `indexee` 검증을 완벽히 통과합니다 (실측).

#### (2) `indexerTy` (두 번째 인자: 프로퍼티 키)의 축약 조건
1. `isPending(indexerTy, ctx->solver)` (line 2174):
   - 키가 막혀 있으면 `Reduction::MaybeOk`로 보류.
2. `searchPropsAndIndexer` (`BuiltinTypeFunctions.cpp:1980`):
   - `indexerTy`를 순회하며 `StringSingleton`인지 검사 (line 1987).
   - 테이블의 `tblProps`에서 일치하는 이름의 프로퍼티(`prop.readTy` 또는 `prop.writeTy`)를 탐색.
   - `tblIndexer`가 있는 경우 `isSubtype(indexerTy, tblIndexer->indexType)`를 검사.
3. **축약 실패 판정** (line 2262):
   - `StringSingleton` 키를 찾지 못하고 테이블 인덱서도 없는 경우:
   - `isRaw == false`(즉 내장 `index<>`)이면 **`return {std::nullopt, Reduction::Erroneous, {}, {}};`** 반환!

> **제네릭 `M`이 전달되었을 때의 거동**:
> - 만약 `M`이 제네릭 변수(`GenericType`)인 상태로 축약을 시도하면:
> - `isPending(M)`은 false (제네릭 변수 자체는 pending/blocked 상태가 아님).
> - `M`은 `StringSingleton`이 아니며 인덱서도 없으므로 `searchPropsAndIndexer`가 false 반환.
> - 결과적으로 **`Reduction::Erroneous`** 로 즉시 실패합니다 (실측).

### 2.2 줄어든 결과의 일반화(Generalization) 및 인스턴스화(Instantiation) 상호작용

#### (1) 축약 성공 시 즉시 치환 (Bound Mutation)
- **소스 위치**: `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/TypeFunction.cpp:369`
  ```cpp
  asMutable(subject)->ty.template emplace<Unifiable::Bound<T>>(replacement);
  ```
- 축약이 완료되면 `TypeFunctionInstanceType` 객체 내부가 즉시 `Bound<TypeId>`로 변경됩니다. 이후 `follow(ty)`를 거치는 모든 타입 연산은 타입 함수 인스턴스를 거치지 않고 직접 결과 타입(`replacement`)을 보게 됩니다.

#### (2) 인스턴스화(Instantiation) 시 재생성 메커니즘
- **소스 위치**: `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/ConstraintSolver.cpp:3823-3827` (`reproduceConstraints`)
  ```cpp
  for (auto [_, newTy] : subst.newTypes)
  {
      if (get<TypeFunctionInstanceType>(newTy))
          pushConstraint(scope, location, ReduceConstraint{newTy}, moduleName);
  }
  ```
- 제네릭 함수를 인스턴스화할 때 반환 타입 등에 포함된 `TypeFunctionInstanceType`이 치환 맵(`subst.newTypes`)에 존재하면, 솔버는 **해당 인스턴스화된 타입에 대해 새로운 `ReduceConstraint`를 즉시 큐에 삽입**합니다.
- 따라서 제네릭 `M`이 구체 싱글톤 `"full"` 또는 `"impl"`로 바인딩되는 순간, 지체 없이 `index<>`가 축약되어 레코드 타입으로 바뀝니다.

#### (3) 서브타이핑 중 미축약 타입 함수의 `never` 추락
- **소스 위치**: `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/Subtyping.cpp:2956-3001` (`handleTypeFunctionReductionResult`)
  ```cpp
  std::pair<TypeId, ErrorVec> Subtyping::handleTypeFunctionReductionResult(const TypeFunctionInstanceType* functionInstance, NotNull<Scope> scope)
  {
      TypeFunctionContext context{...};
      TypeId function = arena->addType(*functionInstance);
      FunctionGraphReductionResult result = reduceTypeFunctions(function, {}, NotNull{&context}, /*force=*/true);
      ErrorVec errors;
      if (result.blockedTypes.size() != 0 || result.blockedPacks.size() != 0)
      {
          errors.emplace_back(Location{}, UninhabitedTypeFunction{function});
          return {builtinTypes->neverType, errors};
      }
      if (result.reducedTypes.contains(function))
          return {function, errors};
      return {builtinTypes->neverType, errors};
  }
  ```
- 서브타이핑 검사 도중 아직 축약되지 않은 `TypeFunctionInstanceType`을 만나면, `force = true`로 강제 축약을 시도합니다.
- 만약 제네릭 변수 등이 남아 있어 축약되지 않으면, 솔버는 이를 **`neverType`** 으로 강제 축약합니다!
- **실측 프로브**: `probes/probe_index_never_direction.luau`
  ```lua

  local function testAssign<M>(mode: M)
      local function helper(): index<TargetTable, M> return nil :: any end
      local n: number = helper() -- 통과! (never <: number 성립)
      local val: index<TargetTable, M> = 123 -- FAIL! (number <: never 불성립)

  ```
  실행 결과:
  ```

  the reduced type is `never`, and `number` is not a subtype of `never`
  ```
  - `subTy` 위치에 오면 `never <: T`가 성립하여 아무 타입에나 대입되어 버리고 (타입 안전성 구멍),
  - `superTy` 위치에 오면 `T <: never`가 되어 어떤 값도 대입할 수 없는 모순이 발생합니다.

### 2.3 알려진 실패 모양 및 사용자 타입 함수(UDTF)와의 차이

| 구분 | 내장 타입 함수 `index<>` | 사용자 정의 타입 함수 (`type function`) |
|---|---|---|
| **실행 엔진** | Luau C++ 검사기 내부 네이티브 실행 (`BuiltinTypeFunctions.cpp`) | Luau VM 바이트코드 인터프리터 샌드박스 실행 |
| **제약 결합도** | `ConstraintSolver`의 `ReduceConstraint` 루프에 완전 결합 | `UserDefinedTypeFunction` 제약으로 격리 |
| **미축약 인자 처리** | 다른 `TypeFunctionInstanceType`이 오면 `isPending`으로 대기 | **지원 불가**: `"Type functions do not currently support types of the form 'index<D, L>'"` 에러 (`TypeFunction.user.test.cpp:3205`) |
| **우리 설계 적합성** | **적합**: 순수 타입 축약으로만 쓰이고 최종 표에서 소멸 | **부적합**: 사용자 타입 함수는 stl-luau 원칙상 금지 |

#### 리터럴 widening 함정
- 제네릭 인자에 아무런 제약이 없으면 리터럴 `"full"`을 인자로 넘길 때 `string`으로 widening됩니다 (`probes/probe_generic_index_call.luau`).
- `index<{ full: F, impl: F? }, string>`은 테이블에 `string`이라는 프로퍼티가 없으므로 `Property 'string' does not exist` 에러를 냅니다.
- **해결책**: 시제품 v5처럼 받는 쪽 매개변수를 `(mode: "full") -> F`로 기대 타입을 제시하거나, 제네릭 선언부에 `mode: M & ("full" | "impl")` 교집합 제약을 부여해야 합니다 (실측: `probes/probe_constrained_index.luau` 통과).

### 2.4 위험 평가 및 대규모(`src` 규모) 확장 시 깨지는 지점 실측

#### (1) 안전한 영역: 완성 표(`Of`)와 등록 표(`ImplOf`)
시제품 v5가 완성 표를 꺼내는 방식:
```lua
const Stack = Trait.Trait("Stack", stackDef<<"full">>, stackDef<<"impl">>)
export type Stack<Self, T> = typeof(Stack.Of<<Self, T>>(nil :: any))
export type StackImpl<Self, T> = typeof(Stack.ImplOf<<Self, T>>(nil :: any))
```
- `Stack.Of`는 `(mode: "full") -> F`의 `F`입니다. 이미 `M = "full"`로 인스턴스화되어 `index<>`가 완전히 풀려 있습니다.
- `Stack.ImplOf`는 `(mode: "impl") -> G`의 `G`입니다. 이미 `M = "impl"`로 인스턴스화되어 기본 구현 칸은 `F?`로 완전히 풀려 있습니다.
- 따라서 제네릭 알고리즘이나 컨테이너 구현체 코드에는 `index<>`가 단 1개도 노출되지 않습니다 (`types.luau` 에러 목록에 `index<` 0건).

#### (2) 치명적 위험 지대: 복합 트레이트에서 `def, def` 생략 시의 양방향 추론 붕괴 (실측 대발견)
- **실측 프로브**: `probes/probe_scale_simulation.luau`
  트레이트 안에 쓰기 함수(`Mut<Self, T, M>`)와 기본 구현(`Default(mode, ...)`)이 동시에 존재할 때:
  ```lua
  local function stackDef<M>(mode: M)
      return function<Self, T>(of: (Self & ItemRead<T>) | AnyToken)
          return {
              Push = Fn<<(self: Mut<Self, T, M>, item: T) -> Self>>(),
              Pop = Fn<<(self: Mut<Self, T, M>) -> T?>>(),
              Peek = Fn<<(self: Self) -> T?>>(),
              IsEmpty = Default(mode, function(ops: any) return function(self: Self): boolean return ops.Peek(self) == nil end end),
          }
      end
  end
  ```
  이를 `const Stack = MakeTrait("Stack", stackDef, stackDef)`로 등록하면:
  ```
  TypeError: Expected this to be
      '("full") -> <Self, T>((ItemRead<T> & Self) | AnyToken) -> { IsEmpty: (Self) -> boolean, Peek: (Self) -> T?, Pop: (Item<T> & Self) -> T?, Push: (Item<T> & Self, T) -> Self }'
  but got
      '<M>(M) -> <Self, T>((ItemRead<T> & Self) | AnyToken) -> { IsEmpty: index<{ full: (Self) -> boolean, impl: ((Self) -> boolean)? }, M>, Peek: (Self) -> T?, Pop: (index<{ full: Item<T> & Self, impl: Self }, M>) -> T?, Push: (index<{ full: Item<T> & Self, impl: Self }, M>, T) -> Self }'
  ```
- **원인 분석 (추정 및 소스 근거)**:
  `Mut`과 `Default`가 복합적으로 얽혀 있는 경우, Luau의 양방향 함수 인자 추론이 `stackDef`의 제네릭 `M`을 인자 기대 타입 `(mode: "full")`로부터 즉시 고정하지 못하고, 반환 테이블의 타입 검사를 먼저 수행하다가 미축약 `index<>`와 충돌하여 추론을 포기합니다.
- **해결책 (실측)**:
  `const Stack = MakeTrait("Stack", stackDef<<"full">>, stackDef<<"impl">>)`
  호출 시점에 **명시적 타입 인자 `<<"full">>`, `<<"impl">>`를 명시**하면, `stackDef`가 넘어가기 전에 `M`이 확정되므로 양방향 추론의 모호성이 완전히 제거되어 에러 0건으로 완벽히 통과합니다.

## 3. [질문 2] 오버로드 해석의 Ambiguity 원인과 대안 탐색

### 3.1 제네릭 인자 `M`에서 `ambiguous` 에러가 발생하는 근본 원인

`probe3_overload_ambiguity.luau`에서 관찰된 실패:
```lua
type DefaultOverload =
	(<F>(mode: "full", build: (ops: any) -> F) -> F) &
	(<F>(mode: "impl", build: (ops: any) -> F) -> F?)

local function genericFactory<M>(mode: M & ("full" | "impl"))
	return {
		IsEmpty = Default(mode, dummyBuild) -- FAIL: ambiguous
	}
end
```

#### (1) 오버로드 리졸버의 판정 흐름
- **소스 위치**: `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/OverloadResolver.cpp:500-565` (`testFunction`)
  1. 각 오버로드 후보 `fnTy`에 대해 prospective function `(argsPack) -> any`를 생성.
  2. `subtyping.isSubtype(fnTy, prospectiveFunction, scope)`를 호출.
  3. 함수 인자 위치는 반변(contravariant)이므로, 실제 인자 `argsPack`이 오버로드 매개변수 타입의 서브타입인지 검사:
     - 후보 1 검사: `(mode: M & ("full" | "impl")) <: "full"`
     - 후보 2 검사: `(mode: M & ("full" | "impl")) <: "impl"`

#### (2) 서브타이핑 엔진의 결정적 결함 코드
- **소스 위치**: `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/Subtyping.cpp:830-836`
  ```cpp
  // TODO: These branches are entirely incorrect. We should never consider
  // generic types to "always" be a sub type or super type of another type
  // in a given scope.
  else if (auto subGeneric = get<GenericType>(subTy); subGeneric && subsumes(subGeneric->scope, scope))
      return isCovariantWith(env, builtinTypes->neverType, superTy, scope);
  else if (auto superGeneric = get<GenericType>(superTy); superGeneric && subsumes(superGeneric->scope, scope))
      return isCovariantWith(env, subTy, builtinTypes->unknownType, scope);
  ```
- **해석**:
  - `subsumes(subGeneric->scope, scope)`는 호출 위치(자식 스코프)가 제네릭 함수 정의 스코프(부모 스코프)에 포함되므로 항상 참입니다.
  - Luau 소스 주석에 `// TODO: These branches are entirely incorrect.`라고 명시되어 있듯이, **현재 새 솔버는 외부 제네릭 변수가 `subTy` 자리에 오면 이를 임시로 `neverType`으로 대체**하여 서브타이핑을 수행합니다.
  - `never`는 모든 타입의 서브타입입니다:
    - `never <: "full"` -> **true** (후보 1 viable)
    - `never <: "impl"` -> **true** (후보 2 viable)
    - 심지어 `never <: number` -> **true**, `never <: string` -> **true**!
- **결과**:
  - `OverloadResolver`에서 두 후보 모두 `result.ok`에 추가됩니다 (`ok.size() == 2`).
  - `/code/Projects/stl-luau/refs-ignoreme/luau/Analysis/src/TypeChecker2.cpp:2279-2281`:
    ```cpp
    if (result2.ok.size() > 1)
        reportError(AmbiguousFunctionCall{fnTy, argsPack}, call->location);
    ```
  - 적합한 오버로드가 2개 이상이므로 **`AmbiguousFunctionCall` 에러가 발생**합니다.

#### (3) 실측 확인 프로브
- `probes/probe_generic_subtyping.luau`:
  `((x: number) -> number) & ((x: string) -> string)` 에 `m: M`을 넘기면:
  `TypeError: Calling function ((number) -> number) & ((string) -> string) with argument pack M is ambiguous.`
  완전히 무관한 `number`와 `string` 오버로드조차 제네릭 `M` 앞에서는 둘 다 통과하여 모호해집니다 (실측).
- `probes/probe_overload_variants.luau`:
  `mode: M & "full"` 처럼 제네릭에 `"full"` 싱글톤 교집합을 걸어주어도, `subIntersection` 분해 과정에서 `M`이 포함되어 있는 한 `never` 취급 때문에 후보 2(`"impl"`)가 탈락하지 않고 살아남아 여전히 `ambiguous`가 발생합니다 (실측).

### 3.2 제네릭 인자로도 하나가 골라지게 할 수 있는 적는 법이 있는가?

| 접근 방식 | 실측 결과 | 가능 여부 및 소스 근거 |
|---|---|---|
| **모드에 교집합 제약 부여** (`mode: M & "full"`) | `ambiguous` 에러 | **불가**: `Subtyping.cpp:833`에 의해 `M`이 `never`가 되므로 `"impl"` 분기도 통과 |
| **순수 유니온 인자 전달** (`mode: "full" | "impl"`) | `None of the overloads are compatible` | **불가**: 유니온은 둘 다의 서브타입이 아니므로 둘 다 탈락 |
| **명시적 타입 인자 사용** (`Default<<"full">>(mode, ...)`) | 무시됨 (영향 없음) | **불가**: `ConstraintSolver.cpp:3038`에서 `IntersectionType`은 `instantiateFunctionType`이 미지원하여 그대로 반환 |
| **인자 개수(Arity)를 다르게 분기** | **정상 분기 성공** | **유일하게 가능**: `OverloadResolver.cpp:531`의 `isArityCompatible`이 매개변수 개수 불일치를 사전에 걸러냄 |

> **결론**:
> 동일한 2개의 인자(`mode`, `build`)를 받으면서 `mode`의 타입 값만으로 오버로드를 분기하는 방식은, 호출자가 제네릭 `M`을 들고 있는 한 **Luau의 현재 솔버 구현상 절대로 단일 분기될 수 없습니다**.

## 4. 설계 판단 및 제안 (사용자 결정을 위한 근거)

### 4.1 의도된 동작 vs 상류 결함 구분

1. **오버로드의 Ambiguity (`Subtyping.cpp:833`)**:
   - **상류 결함(Known Defect)**: Luau 소스에 `// TODO: These branches are entirely incorrect.`라고 못박혀 있습니다. 향후 제네릭 바운드 전파 시스템이 완성되면 고쳐질 가능성이 있으나, 현재 Luau 0.742에서는 외부 제네릭이 `never`로 취급되는 동작을 우회할 방법이 없습니다. 따라서 **오버로드 기반 두 보기는 현재 채택 불가능**합니다.
2. **내장 타입 함수 `index<>` (`BuiltinTypeFunctions.cpp:2140`)**:
   - **의도된 동작(Intended Feature)**: Luau 팀이 공식 지원하는 내장 타입 함수이며, 다수의 회귀 테스트(`TypeFunction.test.cpp:1084` 등)로 고정되어 있습니다.
   - 단, 제네릭 `M` 상태로 미축약된 채 서브타이핑에 들어가면 `never`로 추락하므로, 반드시 **선언-인스턴스화 경계에서 싱글톤으로 즉시 축약되도록 유도**해야 합니다.

### 4.2 제안: 시제품 v5 방식을 채택하되, 정의 등록 시 `<<"full">>`, `<<"impl">>`를 표준화할 것

시제품 v5의 `index<>` 접근은 매우 건전하며 `src` 규모로 확장 가능합니다. 다만 이번 조사에서 규명된 결함을 회피하기 위해 다음 규칙을 적용할 것을 제안합니다:

1. **`Trait.Trait` 호출 시 명시적 모드 인자 표준화 (강력 권장)**:
   ```lua
   -- 기존 v5 시도 (단순 트레이트에서는 우연히 되었으나 복합 트레이트에서 실패):
   const Stack = Trait.Trait("Stack", stackDef, stackDef)
   
   -- 권장 제안 (복합 트레이트에서도 100% 안정적 통과):
   const Stack = Trait.Trait("Stack", stackDef<<"full">>, stackDef<<"impl">>)
   ```
   `<<"full">>`, `<<"impl">>`를 명시하면 `Mut`과 `Default`가 복합된 대형 트레이트에서도 양방향 추론 실패가 원천 차단됩니다 (`probe_scale_simulation.luau` 실측).
2. **`Default` 내부의 `:: any` 캡슐화 유지**:
   `Default` 함수 구현체 내부에서 `index<{ full: F, impl: F? }, M>`로의 반환은 `:: any`로 마스킹하여, 몸통 내부에서 미축약 `never` 서브타이핑 에러가 발생하는 것을 방지해야 합니다 (시제품 v5가 이미 준수 중).
3. **외부 노출 타입의 무오염 유지**:
   `Stack<Self, T>`와 `StackImpl<Self, T>`는 각각 `Of`와 `ImplOf`의 `typeof`로 정의되어 `index<>`가 완전히 박멸된 순수 테이블 타입이 되므로, 컨테이너 및 알고리즘 작성자는 `index<>`의 존재를 전혀 의식하지 않고 개발할 수 있습니다.
