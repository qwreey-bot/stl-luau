## 2. 과제 1: `typeof(X<<…>>)` 별칭 인스턴스화 누락 원인 및 해법

### 2.1 현상과 오해의 해소: 2인자 vs 3인자가 아닌 `Fn` vs `Default`

메인 세션의 검증(`.claude/audit/agy/2026-10-14-tr3-entry.md`, 재현 `main-list-of-broken.luau:173`)에서는:
> "2-인자 트레이트(`Stack`)는 `Stack.Of(d).Push(d, 5)`가 잘 되는데, 3-인자 트레이트(`List`)는 `List.Of(d).IndexOf(d, 2)`에서 `ItemIndex<E, I> & Self`가 풀리지 않고 에러가 발생한다."

고 보고되었습니다. 그러나 소스 분석과 프로브 격리 결과, **타입 매개변수 개수(2개 vs 3개)는 원인이 아니었습니다 [실측]**.

#### [실측 대조군] 프로브: `probes/q1_defect_isolation.luau`
```luau
-- probes/q1_defect_isolation.luau
type ItemIndex<E, I> = { read __generics: { read Item: (E) -> E, read Index: (I) -> I } }

local function Fn<F>(): F return nil :: any end
local function Def<F>(build: any): F return nil :: any end
local externalBuildFn = function(ops: any) return nil end

const Entries = {
	FromFn       = Fn<< <Self, E, I>(list: Self & ItemIndex<E, I>, item: E) -> I? >>(),
	FromConst    = Def<< <Self, E, I>(list: Self & ItemIndex<E, I>, item: E) -> I? >>(123),
	FromExternal = Def<< <Self, E, I>(list: Self & ItemIndex<E, I>, item: E) -> I? >>(externalBuildFn),
	FromInline   = Def<< <Self, E, I>(list: Self & ItemIndex<E, I>, item: E) -> I? >>(function(ops: any) return nil end),
}

export type TableWrapper<Self, E, I> = {
	FromFn: typeof(Entries.FromFn<<Self, E, I>>),
	FromConst: typeof(Entries.FromConst<<Self, E, I>>),
	FromExternal: typeof(Entries.FromExternal<<Self, E, I>>),
	FromInline: typeof(Entries.FromInline<<Self, E, I>>),
}

local w: TableWrapper<number, number, number> = nil :: any
local _t1: string = w.FromFn
local _t2: string = w.FromConst
local _t3: string = w.FromExternal
local _t4: string = w.FromInline
```

- **분석 결과**:
  - `Stack`에서 테스트했던 메서드(`Push`, `Pop`)는 인자가 없는 `Fn<<...>>()`, 즉 **FromFn** 케이스였습니다. 따라서 정상적으로 `number`로 치환되었습니다. (만약 Stack에서 `Default`로 선언된 `Peek`을 호출했다면 동일하게 에러가 발생합니다 [실측: `probes/q1_test_stack_peek.luau`]).
  - `List`에서 테스트했던 메서드(`IndexOf`, `Contains`)는 기본 구현 `Default<<...>>(function(ops: any) ... end)`, 즉 **FromInline** 케이스였습니다.
  - 즉, **3-인자라서 깨진 것이 아니라, `Default`에 인라인 람다(함수 리터럴)를 인자로 넘긴 메서드만 치환이 누락된 것**입니다.

### 2.2 Luau 소스 기전 추적: 왜 람다가 끼면 치환이 누락되는가?

Luau 타입 검사기 소스 코드(`Analysis/src`)에서 일어나는 정확한 실행 흐름은 다음과 같습니다:

1. **명시적 인스턴스화와 BlockedType 생성** [근거: `ConstraintGenerator.cpp:3839-3856`]:
   ```cpp
   Inference ConstraintGenerator::check(const ScopePtr& scope, AstExprInstantiate* explicitTypeInstantiation)
   {
       TypeId functionType = check(scope, explicitTypeInstantiation->expr, std::nullopt).ty;
       auto [explicitTypeIds, explicitTypePackIds] = resolveTypeArguments(scope, explicitTypeInstantiation->typeArguments);
       TypeId placeholderType = arena->addType(BlockedType{});

       NotNull<Constraint> constraint = addConstraint(
           scope, explicitTypeInstantiation->location,
           TypeInstantiationConstraint{functionType, placeholderType, std::move(explicitTypeIds), std::move(explicitTypePackIds)}
       );
       getMutable<BlockedType>(placeholderType)->setOwner(constraint);
       return Inference{placeholderType};
   }
   ```
   - `Entries.Method<<Self, E, I>>` 표현식을 타입 검사할 때, 결과 타입은 즉시 확정되지 않고 `BlockedType`(소유자: `TypeInstantiationConstraint`)으로 반환됩니다.

2. **인라인 람다로 인한 `FunctionCheckConstraint` 지연** [근거: `ConstraintGenerator.cpp:3263`, `ConstraintSolver.cpp:1875-1945`]:
   - `Fn<<...>>()` 호출은 인자가 없으므로 즉시 해결됩니다.
   - 하지만 `Default<<...>>(function(ops: any) ... end)`는 인자가 함수 리터럴(람다)이므로, 양방향 타입 추론(bidirectional type checking)을 위해 `FunctionCheckConstraint`와 `FunctionCallConstraint`가 생성되어 나중 큐로 지연(deferred)됩니다.
   - 따라서 `Entries.IndexOf`의 반환 타입 자체가 `BlockedType` 상태로 남게 됩니다.

3. **타입 별칭 확장 시점의 블록 검사 회피** [근거: `ConstraintSolver.cpp:1321-1325`]:
   ```cpp
   // If the type function itself is still blocked, we have to wait for it
   if (FFlag::LuauBlockingTypeAliasExpansion && get<BlockedType>(follow(tf->type)))
       return block(tf->type, constraint);
   ```
   - 단독 별칭 `type Alias<Self, E, I> = typeof(Entries.IndexOf<<Self, E, I>>)`의 경우, `tf->type` 자체가 `BlockedType`이므로 솔버가 확장을 멈추고 기다립니다(`block`).
   - 그러나 테이블로 감싼 `type List<Self, E, I> = { IndexOf: typeof(...) }`의 경우, 최상위 `tf->type`은 `TableType`입니다.
   - `get<BlockedType>(follow(tf->type))`이 `nullptr`이므로, **솔버는 블록 상태가 아니라고 판단하고 즉시 타입 별칭 확장을 진행**합니다!

4. **치환기(`ApplyTypeFunction`)의 `BlockedType` 순회 무시** [근거: `Substitution.cpp:173-200`, `Substitution.cpp:730-736`]:
   - 타입 별칭 인스턴스화는 `ApplyTypeFunction::substitute`가 `Tarjan` 알고리즘을 통해 dirty 타입을 찾아 복제/치환합니다.
   - `Tarjan::visitChildren` 코드를 보면:
     `TableType`의 각 프로퍼티를 방문하지만, 프로퍼티 타입인 `BlockedType`은 자식 노드가 없는 리프 노드로 취급됩니다.
   - 따라서 `BlockedType` 내부에 바인딩된 `Self, E, I` 타입 파라미터는 `Tarjan` 탐색에서 발견되지 않으며, 해당 프로퍼티는 dirty로 마킹되지 않습니다.
   - 결과적으로 `{ IndexOf = BlockedType }` 테이블은 아무런 치환 없이 그대로 반환됩니다.

5. **최종 증상: 인스턴스화 누락** [근거: `ConstraintSolver.cpp:2996-3008`]:
   - 나중에 제약 솔버가 인라인 람다를 풀고 `TypeInstantiationConstraint`를 dispatch할 때, 원래 정의 스코프에 있던 미해결 타입 변수 `Self, E, I`가 그대로 주입됩니다.
   - 하지만 이미 `List<number, number, number>`의 확장은 끝난 뒤이므로, `IndexOf`는 `(ItemIndex<E, I> & Self, E) -> I?`로 굳어버려 맞는 호출 `l.IndexOf(d, 2)`에서 타입 에러가 발생하게 됩니다.

### 2.3 v4 방식(`typeof(List.Of<<...>>(nil::any))`)과의 비교

- **v4 방식**:
  `export type List<Self, E, I> = typeof(List.Of<<Self, E, I>>(nil :: any))`
  - v4에서는 최상위 식이 함수 호출식(`AstExprCall`)입니다.
  - `List.Of` 함수는 팩토리 함수이며, 인자로 전달된 `nil :: any`는 람다가 아니라 상수 캐스트식이므로 제약 해결이 지연되지 않습니다.
  - 또한 반환 타입이 이미 닫혀 있는 모노모픽 레코드(`{ Get: ..., IndexOf: ... }`)이므로 `BlockedType` 누락 문제가 발생하지 않았습니다.
- **원천 뒤집기(Entries-as-Source)의 차이**:
  - 테이블 필드 각각에 `typeof(Entries.Method<<...>>)`를 개별적으로 인스턴스화하여 채우는 구조이기 때문에, 필드 중 하나라도 인라인 람다에 의해 `BlockedType`이 되면 테이블 전체 치환에서 해당 필드가 누락되는 솔버 맹점에 노출됩니다.

### 2.4 동작하는 작성법 및 프로브 실측

이 문제를 완전히 해결하고 100% 정적 검사를 달성하는 방법은 다음 2가지가 있습니다.

#### [해법 A] 기본 구현 빌더 함수 외부 분리 (권장) [실측: `probes/q1_working_solutions.luau`]
인라인 람다 `function(ops: any) ... end` 대신, 모듈 스코프의 사전 바인딩 함수를 `Default`에 넘깁니다. 람다 지연이 사라져 즉시 타입이 확정됩니다.

#### [해법 B] 순수 서명 테이블(Signatures) 분리 [실측: `probes/q1_working_solutions.luau`]
완성 표 타입 `List<Self, E, I>`를 유도하기 위한 서명 테이블은 인자가 없는 순수 마커 `Fn<<...>>()`로만 정의하고, 런타임 객체 등록에는 `Default`를 사용하는 방식입니다.

#### 종합 실측 검증: `probes/q1_working_solutions.luau`
```luau
-- [해법 A: 외부 바인딩 함수 분리]
local defaultIndexOf = function(ops: any) return nil end
local defaultContains = function(ops: any) return nil end

const ListEntriesSol1 = {
	Get = Fn<< <Self, E, I>(list: Self & ItemIndex<E, I>, idx: I) -> E? >>(),
	IndexOf = Default<< <Self, E, I>(list: Self & ItemIndex<E, I>, item: E) -> I? >>(defaultIndexOf),
	Contains = Default<< <Self, E, I>(list: Self & ItemIndex<E, I>, item: E) -> boolean >>(defaultContains),
}
export type ListSol1<Self, E, I> = {
	Get: typeof(ListEntriesSol1.Get<<Self, E, I>>),
	IndexOf: typeof(ListEntriesSol1.IndexOf<<Self, E, I>>),
	Contains: typeof(ListEntriesSol1.Contains<<Self, E, I>>),
}
```

## 3. 과제 2: 솔버 관찰 사실 3가지의 소스 근거 및 설계 영향

### 3.1 사실 (a): 읽기 필드가 `any`/`unknown`이면 필드가 없는 테이블도 만족

#### 소스 근거
- **위치**: `Analysis/src/Subtyping.cpp:2173-2193`
- **구현 기전**:
  ```cpp
  else if (FFlag::LuauSubtypingMissingPropertiesAsNil)
  {
      SubtypingResult result;
      result = isCovariantWith(env, Property::readonly(builtinTypes->nilType), superProp, name, forceCovariantTest, scope);
      result.reasoning.clear();
      record(std::move(result));
  }
  ```
  - 서브타입 대상 테이블에 특정 프로퍼티가 아예 없으면, Luau 새 솔버는 이를 **`Property::readonly(nil)`**로 간주합니다.
  - 그리고 수퍼타입 프로퍼티(`superProp`)와 공변성 검사(`Subtyping.cpp:2677`)를 수행합니다:
    `isCovariantWith(nil, superProp.readTy)`.
  - `superProp.readTy`가 `unknown` 또는 `any`인 경우, `nil <: unknown` 및 `nil <: any`가 참이므로 **서브타입 검사가 통과**합니다!
  - 반면 `superProp`이 `ReadWrite`인 경우(`{ x: unknown }`), `Subtyping.cpp:2684`에서 `subProp.isReadOnly()`와 대조되어 `PropertyModifierMismatch` 에러로 정상 거부됩니다.

#### 의도된 동작인지 결함인지
- **판정: 의도된 동작 (Intentional by Design, 테스트로 영구 고정) [근거: `tests/TypeInfer.tables.test.cpp:562-569`]**
  ```cpp
  // TypeInfer.tables.test.cpp:564-568
  // This does not error because `baz` in the method is being inferred as having the type `unknown`, which is an optional type.
  // Specifically, `T` has the type `{ bar: string, method: ... }` and `method` has the type `function({ read baz: unknown }) -> ()`.
  // In this case, `T` functions as a valid argument type for `method` because it will always read `baz` as `nil` which is a subtype of
  // `unknown.` This is safe because in order to do anything with that value, the function body _must_ do some kind of conditional testing.
  LUAU_REQUIRE_NO_ERRORS(result);
  ```
  Luau 설계팀은 "Lua 테이블에서 없는 키를 읽으면 `nil`이 나오며, `nil`은 `unknown`의 서브타입이므로 읽기 전용 `unknown` 프로퍼티를 요구하는 자리에 해당 필드가 없는 테이블이 들어가는 것은 완전히 건전(sound)하다"고 판단하여 테스트로 고정했습니다.

#### stl-luau 설계 영향 및 회피책
- **영향**: 트레이트 마커나 덕 타이핑 검사에서 `{ read Item: unknown }` 또는 `{ read __marker: any }`를 쓰면, **마커가 아예 없는 빈 테이블도 통과해버리는 심각한 누수**가 발생합니다.
- **회피책**: 마커는 반드시 `nil`의 상한이 될 수 없는 타입이어야 합니다. `(T) -> T` 형태의 불변 팬텀 함수(`{ read __item: (T) -> T }`)를 사용하거나, `ItemMarkerMut`처럼 쓰기 속성을 포함해야 빈 테이블이 통과하는 것을 원천 차단할 수 있습니다 [실측: `probes/q2a_missing_props.luau`].

### 3.2 사실 (b): `[string]: any` 인덱서가 든 타입과 교집합이면 `X.Of<<..>>`를 못 붙임

#### 소스 근거
1. **교집합 프로퍼티 조회의 단순화**:
   - `Analysis/src/ConstraintSolver.cpp:3648-3676` (`lookupTableProp` on `IntersectionType`):
     교집합 `{ read Of: <Self, T>(...) -> ... } & { [string]: any }`에서 `.Of` 프로퍼티를 찾을 때, 브랜치 1은 `FunctionType`, 브랜치 2(인덱서)는 `any`를 반환합니다.
     두 타입에 대해 `simplifyIntersection(FunctionType, any)`가 호출됩니다.
2. **`T & any`의 `UnionType` 변환**:
   - `Analysis/src/Simplify.cpp:1640-1643`:
     ```cpp
     if (get<AnyType>(right))
         return arena->addType(UnionType{{left, builtinTypes->errorType}});
     ```
     `Simplify.cpp`는 `FunctionType & any`를 **`UnionType{{FunctionType, error}}`**로 단순화합니다.
3. **명시적 인스턴스화의 단일 함수 요구**:
   - `Analysis/src/TypeChecker2.cpp:4725-4745`:
     ```cpp
     void TypeChecker2::checkTypeInstantiation(...) {
         const FunctionType* ftv = get<FunctionType>(follow(fnType));
         if (!ftv) {
             reportError(InstantiateGenericsOnNonFunction{InterestingEdgeCase::None}, location);
             return;
         }
     }
     ```
     `.Of`의 타입이 `UnionType`이므로 `get<FunctionType>`이 `nullptr`를 반환하고, 에러 메시지 `Cannot instantiate type parameters on something without type parameters.`가 발생합니다.

#### 의도된 동작인지 결함인지
- **판정: 구현 미지원 / 엣지케이스 결함 (Incomplete Feature) [추정]**
  - 인덱서와의 교집합에서 프로퍼티 타입이 `T | error`로 단순화되는 것은 Luau 타입 시스템의 일반 규칙이지만, 명시적 인스턴스화 문법(`expr<<...>>`)이 이 유니온에서 기저 `FunctionType`을 추출하지 못하고 단순 비함수 에러로 거부하는 것은 솔버의 구현 공백입니다.

#### stl-luau 설계 영향 및 회피책
- **영향**: 트레이트 객체 타입에 편의용 진입점을 위해 `& { [string]: any }`를 교집합으로 붙이면 `Trait.Of<<Self, T>>` 문법이 완전히 파괴됩니다.
- **회피책**: 인덱서가 필요하다면 단일 테이블 리터럴 내부(`{ read Of: ..., [string]: any }`)에 함께 정의해야 합니다. 단일 테이블에서는 `props["Of"]`가 우선 탐색되어 인덱서와 교집합을 이루지 않으므로 `Of<<...>>`가 정상 작동합니다 [실측: `probes/q2b_intersection_indexer.luau`].

### 3.3 사실 (c): 연관 타입에서 앞선 호출의 타입이 합(Union)으로 오염되는 현상

`.claude/research/trait-typing-probes/assocfields.luau`에서 `keyOf(m)` 호출 후 `valueOf(m)`을 호출했을 때 `number`가 아닌 `number | string`이 나오는 현상의 원인입니다.

#### 소스 근거
- **위치**: `Analysis/src/Unifier2.cpp:790-800`
- **문제의 코드**:
  ```cpp
  auto subTypeParamsIter = subTable->instantiatedTypeParams.begin();
  auto superTypeParamsIter = superTable->instantiatedTypeParams.begin();

  while (subTypeParamsIter != subTable->instantiatedTypeParams.end() &&
         superTypeParamsIter != superTable->instantiatedTypeParams.end())
  {
      result &= unify_(*subTypeParamsIter, *superTypeParamsIter);
      subTypeParamsIter++;
      superTypeParamsIter++;
  }
  ```

#### 기전 분석: 위치 기반 단일화(Positional Unification)의 참사
1. `MyMap<K, V>`는 타입 별칭이므로 인스턴스화 시 `subTable->instantiatedTypeParams`에 `[0] = K(string)`, `[1] = V(number)`가 등록됩니다 [근거: `ConstraintSolver.cpp:1266`].
2. `HasKey<K>`는 제네릭 1개짜리 별칭이므로 `superTable->instantiatedTypeParams`의 `[0] = K`입니다.
   - `keyOf(m)` 호출 시 `subTable[0]`(`string`)과 `superTable[0]`(`K`)가 매칭되어 `K = string`이 됩니다. (정상처럼 보임)
3. **문제의 발단**: `HasValue<V>` 역시 제네릭 1개짜리 별칭이므로 `superTable->instantiatedTypeParams`의 **`[0] = V`**입니다!
4. `valueOf(m)`을 호출할 때:
   - `subTable`은 `MyMap<string, number>`이고, `subTable->instantiatedTypeParams[0]`은 **`string`**입니다.
   - `superTable`은 `HasValue<V>`이고, `superTable->instantiatedTypeParams[0]`은 **`V`**입니다.
   - `Unifier2`의 루프 첫 바퀴에서 **`unify_(string, V)`**가 실행됩니다!
   - 동시에 프로퍼티 `read __value: V`로부터 `unify_(number, V)`도 실행됩니다.
   - 결과적으로 제네릭 타입 변수 `V`는 `string`과 `number` 양쪽에 구속(constrained)되어 **`V = number | string`**으로 오염됩니다!

#### 의도된 동작인지 결함인지
- **판정: 명백한 솔버 결함 (Severe Unsoundness Bug) [근거: 소스 코드 구조적 결함]**
  - Luau는 구조적 타입 시스템(structural typing)을 표방합니다. 서로 다른 두 타입 별칭(`MyMap`과 `HasValue`)은 프로퍼티 이름(`__value`)에 의해서만 호환성이 검사되어야 합니다.
  - 그러나 `Unifier2.cpp`는 두 테이블이 **동일한 타입 별칭인지 확인하는 검사(`subTable->name == superTable->name`)가 완전히 누락**된 채, 단순히 제네릭 인자의 배열 인덱스 순서대로 묻지마 단일화를 수행하고 있습니다.
  - 이로 인해 제네릭 타입 별칭으로 인터페이스를 정의하면, 제네릭 매개변수의 선언 순서가 컨테이너와 일치하지 않는 모든 경우에 타입 오염이 발생합니다.

#### stl-luau 설계 영향 및 회피책
- **영향**: 인터페이스나 트레이트 연관 타입을 `type HasItem<T> = { ... }`처럼 제네릭 타입 별칭으로 만들어 `Self & HasItem<T>`로 받으면 안 됩니다.
- **회피책 [실측: `probes/q2c_positional_unify.luau`]**:
  1. **인라인 테이블 리터럴 사용**: 함수 매개변수 타입을 별칭이 아닌 `<Self, T>(x: Self & { read __item: T })`처럼 직접 적으면 `instantiatedTypeParams`가 생성되지 않아 위치 단일화 버그를 100% 회피할 수 있습니다.
  2. **팬텀 함수 / 토큰 활용**: `(T) -> T` 함수 시그니처나 토큰 타입으로 연관 타입을 전달합니다.

## 4. stl-luau 트레이트 설계를 위한 종합 제안

1. **`Entries-as-Source` (진입점 선행) 아키텍처 채택 권장 [제안]**:
   - `v4`의 팩토리 우선 방식은 편한 진입점(`Stack.Push`)이 `any`가 되는 치명적 구멍이 있습니다.
   - `Entries`를 원천으로 두되, 기본 구현(`Default`)에 인라인 람다를 직접 전달하지 않고 **[해법 A] 외부 변수 함수 분리** 또는 **[해법 B] 순수 서명 테이블 분리**를 적용하면, 진입점과 `Of` 완성 표 양쪽 모두 0건의 오류 없이 정밀하게 검사할 수 있습니다.

2. **트레이트 마커 설계 시 읽기 전용 `unknown`/`any` 절대 금지 [제안]**:
   - `FFlag::LuauSubtypingMissingPropertiesAsNil`로 인해 `{ read __tag: unknown }`은 마커가 없는 빈 테이블도 만족합니다.
   - 마커는 반드시 `read __tag: (T) -> T` 형태의 불변 팬텀 함수이거나, 변이(Mut) 속성을 포함해야 합니다.

3. **교집합 인덱서 패턴 금지 [제안]**:
   - 트레이트 객체에 `& { [string]: any }`를 붙이면 `Of<<..>>`의 명시적 타입 인스턴스화가 즉시 무력화됩니다. 진입점 노출이 목적이라면 명시적 네임스페이스 표기를 사용해야 합니다.

4. **연관 타입 인터페이스는 제네릭 별칭 대신 인라인 테이블 사용 [제안]**:
   - 상류의 위치 기반 단일화 버그(`Unifier2.cpp:790`)를 피하기 위해, 다중 제네릭 컨테이너와 상호작용하는 인터페이스는 별칭 대신 인라인 테이블 타입(`Self & { read __generics: ... }`)으로 선언해야 합니다.
