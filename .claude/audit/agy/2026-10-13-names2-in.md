## 1. 개요 및 검토 원칙

stl-luau는 아직 배포 전 단계의 라이브러리로, 다음 핵심 설계 결정을 확고히 유지하고 있습니다:
1. **데이터는 엔티티, 함수는 서비스** [실측: `.claude/conventions.md:40`]: 메타테이블 없는 순수 테이블 + 모듈 네임스페이스 함수. 콜론 메소드 없음.
2. **3층 구조** [실측: `.claude/conventions.md:298`]: 1층 노드 도구(`src/Node/`) → 2층 트리부/알고리즘(`src/Trees/`, `src/Algorithms/`) → 3층 조립(`src/Collections/` — 컨테이너).
3. **트레이트 시스템** [실측: `src/Trait.luau`, `src/Traits/`]: 값에는 타입 토큰 하나(`__type`), 구현은 트레이트가 보관. `Trait.New` 기반의 필수(`Core`) + 기본 구현 결합(`Full`) + 등록 표(`Provided`).
4. **일관된 소유권 및 어휘 규약**: `FromTable`은 복사, `Adopt`는 입양(`conventions.md:243`), `Has`(키 판별) / `Contains`(값 포함 판별)(`todos.md:202`).

본 검토는 총 19개 항목에 대해 내부자 시선으로 최적의 이름을 각각 하나씩 선정하고, 그 근거와 연쇄 범위를 밝힙니다.

- **지금 이름과 비교**: **유지**
- **확신**: **높음**
- **이유 [실측/추정]**:
  1. `Empty`는 10개 모든 컨테이너 [실측: `Arr`, `HashMap`, `HashSet`, `FlatMap`, `TreeMap`, `TreeSet`, `FlatSet`, `Heap`, `CircularDeque`, `LinkedDeque`], `Equal`은 4개 컨테이너에 광범위하게 쓰이고 있는 C++ STL 전통의 기본 상태 확인입니다.
  2. 반면 분사형 형용사(`IsSorted`)나 명사/전치사 복합 술어(`IsSubsetOf`, `IsDisjointFrom`, `IsHeap`, `IsComplete`)는 `Is`가 없으면 `Sorted`처럼 "변환된 배열을 돌려주는 함수"로 치명적인 오해를 부릅니다 [실측: `Arr.luau:1790`, `CompleteArray.luau:113`].
  3. "단일 상태 형용사(`Empty`, `Equal`)는 `Is` 생략, 분사형 및 복합 술어는 `Is` 필수"라는 규칙을 `.claude/conventions.md`에 명문화하면 일관성과 실용성을 모두 챙길 수 있습니다.
- **연쇄**: 없음 (코드 수정 불필요, `conventions.md`에 기준 기술).

## 4. 목록에 없지만 일관성이 깨진 이름 (추가 발견 Top 3)

코드베이스 전수 조사 결과, 목록에는 없으나 내부 일관성을 저해하는 3개 지점을 발견하여 보고합니다:

### 4.1. `Arr.Flatmap` / `FlatmapInplace`의 파스칼 케이스 복합어 대소문자 위반 [실측]
- **관련 파일 및 줄**: `src/Collections/Arr.luau:2228, 2254, 2853` [실측]
- **현상**:
  - `src/Collections/Arr.luau:2228`: `const function Flatmap<T, G>(...)`
  - `src/Collections/Arr.luau:2254`: `const function FlatmapInplace<T, G>(...)`
  - stl-luau의 모든 복합어 파스칼 케이스 함수는 단어마다 첫 글자가 대문자입니다: `PushBack`, `SwapRemove`, `LastIndexOf`, `StableSort`, `GroupBy`, `CountBy`, `SortBy`, `MergeSorted`.
  - 또한 컨테이너 모듈 이름 역시 `FlatMap.luau`(`M`이 대문자)입니다 [실측: `src/Collections/FlatMap.luau`].
  - 오직 `Arr.Flatmap`만 두 번째 단어 'map'의 'm'이 소문자로 되어 있어 명명 규칙을 깨뜨리고 있습니다.
- **제안**: **`Arr.FlatMap`** 및 **`Arr.FlatMapInplace`**로 수정하여 라이브러리 전체의 대소문자 일관성을 회복해야 합니다.

### 4.2. `Set.Core` 계약의 무할당 순회자(`Iter`) 누락 및 불필요한 배열 할당(`Items`) 강제 [실측]
- **관련 파일 및 줄**: `src/Traits/Set.luau:14-19` [실측]
- **현상**:
  - `src/Traits/Set.luau:18`: `read Items: (set: C) -> { T }` 만 필수로 요구하고 `Iter`가 계약에 없습니다.
  - 반면 `Map.Core`는 질문 AO 및 perf 28절 최적화에 따라, 매번 새 레코드 배열을 생성하던 `Records`를 계약에서 빼고 무할당 순회를 지원하는 `read Iter`를 필수로 두었습니다 [실측: `src/Traits/Map.luau:36`].
  - 모든 셋 구현체(`HashSet.luau:133`, `TreeSet.luau:110`, `FlatSet.luau:136`)는 이미 고속 순회 함수 `Iter`를 완벽히 구현하고 있으며 [실측], 규약 문서(`conventions.md:284`)에서도 "셋을 도는 권장 모양은 `for item in X.Iter(s)`"라고 못박고 있습니다.
  - 그럼에도 `Set.Core`는 호출할 때마다 새 배열을 할당해야 하는 `Items`만을 필수로 요구하고 있어, `Map` 트레이트와의 비대칭은 물론 셋을 추상화하는 제네릭 코드의 성능을 불필요하게 낭비시킵니다.
- **제안**: `Set.Core`에 **`read Iter: (set: C) -> ...`**를 추가하고, `Items`는 `Map.Records`처럼 트레이트 진입점(`Set.Items(s)`) 또는 기본 구현으로 전환해야 합니다.

### 4.3. 순차 컨테이너들 간의 `{ T }` 생성자 명명 불일치 (`Arr.FromTable` 대 `FromList`) [실측]
- **관련 파일 및 줄**: `src/Collections/Arr.luau:2594` [실측]
- **현상**:
  - 연속 원소 리스트 `{ T }`를 인자로 받아 컨테이너를 생성하는 함수가 다른 모든 순차/집합 컨테이너에서는 **`FromList`**로 통일되어 있습니다:
    - `LinkedDeque.FromList(list: { T })` [실측: `LinkedDeque.luau:347`]
    - `CircularDeque.FromList(list: { T })` [실측: `CircularDeque.luau:343`]
    - `HashSet.FromList(list: { T })` [실측: `HashSet.luau:315`]
    - `TreeSet.FromList(source: { T }, ...)` [실측: `TreeSet.luau:444`]
    - `FlatSet.FromList(source: { T }, ...)` [실측: `FlatSet.luau:479`]
    - `Heap.FromList(list: { T }, ...)` [실측: `Heap.luau:224`]
  - 그러나 동일하게 `{ T }` 리스트를 받는 `Arr`의 복사 생성자만 유일하게 **`Arr.FromTable(tbl: { T })`**입니다 [실측: `Arr.luau:2594`].
  - 정작 `HashMap.FromTable`은 키-값 사전식 테이블 `{ [K]: V }`를 받습니다 [실측: `HashMap.luau:365`].
  - 규약 문서(`conventions.md:249`)에서도 이들을 묶어 "리스트를 받는 진입점의 길이 규약: `{ T }` 를 받는 함수(`FromList`, `FromRecords`, `Arr.FromTable` …)"라고 표현하고 있어 `Arr`만 겉돌고 있습니다.
- **제안**: `Arr`에도 타 컨테이너와 일관되게 **`Arr.FromList`**를 제공하거나, 점진적 통일을 검토할 필요가 있습니다.
