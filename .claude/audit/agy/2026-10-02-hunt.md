## 1. 개요 및 요약 (Executive Summary)

이 저장소는 Claude(Anthropic) 세션에서 수많은 라운드의 엄격한 리뷰를 거쳤으며, "재현되는 결함 없음" 상태에 도달해 있었습니다. 그러나 동일 모델 계열의 다패스 리뷰는 **"테스트 데이터가 우연히 맞아떨어지는 틀"**과 **"익숙한 관습적 패턴"**을 공유하여 특정한 맹점을 공유하기 쉽습니다.

다른 모델 계열(Gemini)의 시선에서 컨테이너의 중심 표현인 **nil 구멍(`{ n, [number]: T }`)과 길이 규약, 다중 반환, 테이블 연산자의 숨은 동작**을 전수 조사한 결과, Claude 세션이 놓친 **2건의 치명적 런타임 결함**과 **3건의 불변식·설계 결함**, **1건의 어휘 충돌**을 발굴하고 프로브를 통해 실측 재현했습니다.

### [메커니즘 1] Lua 다중 반환의 개수 판별 부재 (Value vs Arity 혼동)

> **뿌리 원인 (한 문장)**:
> Lua/Luau에서 다중 반환의 실제 반환 개수(`select("#", ...)`) 대신 특정 반환값의 `nil` 여부(`b == nil`)로 1개 반환과 2개 반환을 가르면서, **유효한 `nil` 값(구멍)을 "인자 부재"로 오판**하여 데이터 오염을 유발함.

#### 결함 1-1. [실측 결함] `Arr.FromIter`의 `nil` 구멍 오염 결함

- **파일 및 위치**: `src/Arr.luau:2010`
- **원인 코드**:
  ```lua
  const function FromIter<T>(iter: any, state: any?, control: any?): Arr<T>
  	const result: Arr<T> = newSized(0)
  	local count = 0
  	local key = control
  	while true do
  		const a, b = iter(state, key)
  		if a == nil then
  			break
  		end
  		key = a
  		count += 1
  		-- 값이 둘이면 둘째가 값, 하나면 그것이 값입니다.
  		result[count] = if b == nil then a else b
  	end
  	result.n = count
  	return result
  end
  ```
- **메커니즘 상세**:
  주석에서는 `string.gmatch`처럼 값을 1개만 돌려주는 이터레이터(`(val)`)와 `pairs`/`ipairs`/`Arr.Iter`처럼 키-값을 돌려주는 이터레이터(`(key, val)`)를 모두 지원하기 위해 `if b == nil then a else b`라는 휴리스틱을 사용했습니다.
  하지만 Lua에서 **"반환값이 1개인 것"**과 **"반환값이 2개인데 둘째 값이 `nil`인 것"**은 완전히 다릅니다.
  `Arr.Iter`는 구멍이 있는 칸에서 `(nextIdx, nil)`을 정상적으로 반환합니다. 그러나 `FromIter`는 `b == nil`을 보고 "반환값이 1개뿐이구나"라고 오판하여 **`a`(숫자 인덱스)를 배열의 값으로 저장**해 버립니다.
- **실측 프로브 (`agyprobe_fromiter_hole.luau`)**:
  ```lua
  local Arr = require("./src/Arr")

  local holed = Arr.Of(10, nil, 30)
  print("Original holed:", holed.n, holed[1], holed[2], holed[3])

  local collected = Arr.FromIter(Arr.Iter(holed))
  print("Collected from Arr.Iter:", collected.n, collected[1], collected[2], collected[3])
  ```
- **실행 명령 및 출력 [실측]**:
  ```bash
  ( ulimit -v 4000000; timeout 600 luau agyprobe_fromiter_hole.luau )
  # 출력:
  Original holed:	3	10	nil	30
  Collected from Arr.Iter:	3	10	2	30
  ```
- **영향 및 약속 위반**:
  - `conventions.md` "배열 표현" 절: "1..n 사이에 nil 이 있을 수 있으며 각 함수가 구멍을 어떻게 다루는지 약속한다."
  - 라이브러리의 표준 순회자인 `Arr.Iter`를 `Arr.FromIter`로 다시 모으는 가장 기본적인 왕복(round-trip) 연산에서, **2번째 구멍(`nil`)이 숫자 `2`로 변질되어 조용히 데이터가 오염**됩니다.
- **해결 방안 [제안]**:
  함수 호출 시 반환 개수(`select("#", ...)`)를 직접 측정해야 합니다.
  ```lua
  local function callIter(...)
      return select("#", ...), ...
  end
  local nArgs, a, b = callIter(iter(state, key))
  if a == nil then break end
  key = a
  count += 1
  result[count] = if nArgs >= 2 then b else a
  ```
  `agyprobe_fromiter_fix.luau`에서 위 방식으로 수정 후 `3 10 nil 30`으로 완벽히 복원됨을 실측 확인했습니다.

### [메커니즘 2] 희소 배열과 구멍에서 Lua 길이 연산자 `#`의 경계 비결정성 신뢰

> **뿌리 원인 (한 문장)**:
> Lua의 `#` 연산자는 `nil` 구멍이 섞인 테이블에서 "어떤 경계(border)든 임의로 반환할 수 있다"는 언어 규격을 가지는데, **`#`가 실제 물리적 크기나 구멍의 유무를 감지해 줄 것이라고 가정**하여 정리 누락이나 가드 무력화가 발생함.

#### 결함 2-1. [실측 결함] `Arr.FromTable`의 `len` 초과 raw 키 비우기 실패 (불변식 위반)

- **파일 및 위치**: `src/Arr.luau:1961-1965`
- **원인 코드**:
  ```lua
  	-- `n` 이 실제 원소보다 짧으면 그 뒤 raw 칸을 비웁니다 — 남으면 `n` 바깥이라 안
  	-- 보이다가 정렬·삽입 뒤 배열 안으로 다시 들어왔습니다(M0 5라운드). 다른 제자리
  	-- 함수들이 지키는 "원소는 1..n 만" 불변식입니다. 입양이라 넘긴 테이블이 바뀝니다.
  	const raw = tbl :: any
  	for idx = len + 1, #raw do
  		raw[idx] = nil
  	end
  	return wrap(raw, len)
  ```
- **메커니즘 상세**:
  M0 5라운드에서 Claude 세션은 `n` 바깥에 남은 raw 값이 나중에 안으로 침범하는 버그를 막기 위해 위 루프를 추가했습니다. 그러나 상한선으로 `#raw`를 썼습니다.
  입력 테이블 `tbl`에 `len` 이후 구멍이 존재할 경우(예: `[len+1]`이 nil이거나 대입으로 채운 희소 테이블), Lua VM은 `len` 이하의 인덱스를 `#raw`로 반환할 수 있습니다.
  이 경우 `for idx = len + 1, #raw do`의 루프 범위가 역전(`len + 1 > #raw`)되어 **루프가 0회 실행되고 `len` 바깥의 데이터가 전혀 지워지지 않습니다.**
  또한 배열 경계를 벗어난 큰 숫자 키(`[100]` 등)나 음수/소수 키는 `#raw`에 아예 포함되지 않아 완전히 누락됩니다.
- **실측 프로브 (`agyprobe_fromtable_raw.luau`, `agyprobe_fromtable_largekey.luau`)**:
  ```lua
  local Arr = require("./src/Arr")

  -- Case A: len 이후 구멍이 있는 경우
  local tbl1 = { n = 1, [1] = 10, [3] = 30 }
  local a1 = Arr.FromTable(tbl1)
  print("a1.n:", a1.n, "a1[3]:", a1[3])
  Arr.PushBack(a1, 20)
  print("After PushBack: a1.n =", a1.n, "a1[3] =", a1[3])

  -- Case B: 큰 인덱스 잔류
  local tbl2 = { n = 2, [1] = 10, [2] = 20, [100] = 999 }
  local a2 = Arr.FromTable(tbl2)
  print("rawget(a2, 100):", rawget(a2 :: any, 100))
  ```
- **실행 명령 및 출력 [실측]**:
  ```bash
  ( ulimit -v 4000000; timeout 600 luau agyprobe_fromtable_raw.luau )
  # 출력:
  a1.n:	1	a1[3]:	30
  After PushBack: a1.n =	2	a1[3] =	30

  ( ulimit -v 4000000; timeout 600 luau agyprobe_fromtable_largekey.luau )
  # 출력:
  rawget(a2, 100):	999
  ```
- **약속 위반 및 불일치**:
  - 주석의 약속: *"다른 제자리 함수들이 지키는 '원소는 1..n 만' 불변식입니다."*
  - 실제 동작: `FromTable`로 입양된 배열은 `n` 바깥에 `30`, `999` 같은 유령 원소를 품고 있게 됩니다.
  - 대조군 불일치: 복사판인 `CloneFromTable(tbl)`은 `table.move`로 1..len만 복사하므로 `[3]`이나 `[100]`이 완벽히 제거되지만, 입양판인 `FromTable(tbl)`은 유령 원소가 남아 두 생성자 간 불변식이 달라집니다.
- **해결 방안 [제안]**:
  입양 전 테이블의 키들을 순회하며 `len`을 초과하는 숫자 키를 제거하거나, `#raw` 대신 명시적인 비우기 범위를 설정해야 합니다.

#### 결함 2-2. [실측 결함] `Arr.SortInplaceUnchecked`의 `#self ~= self.n` 구멍 감지 무력화

- **파일 및 위치**: `src/Arr.luau:1102`
- **원인 코드**:
  ```lua
  const function SortInplaceUnchecked<T>(self: ArrData<T>, less: LessThan<T>?): Arr<T>
  	if #(self :: any) ~= self.n then
  		return SortInplace(self, less)
  	end
  	if less then
  		table.sort(self :: any, less)
  	else
  		table.sort(self :: any)
  	end
  	return self :: any
  end
  ```
- **메커니즘 상세**:
  M0 6라운드에서 추가된 가드(`if #(self :: any) ~= self.n then return SortInplace(...) end`)는 `#`와 `n`이 다르면 구멍을 인지하고 안전한 `SortInplace`로 넘어간다고 설명합니다.
  그러나 Luau의 메모리 할당 구조상, `table.create`나 `Arr.Sized`로 생성되어 내부 array 버퍼가 확보된 테이블은 **중간(1..n-1)에 `nil` 구멍을 뚫어도 마지막 원소 `t[n]`이 존재하는 한 `#t`는 항상 정확히 `n`을 반환**합니다.
  따라서 `#(self) ~= self.n` 조건은 거짓이 되어 안전 장치가 100% 무력화되고, 날것의 `table.sort`에 `nil` 구멍이 노출되어 비교 연산 크래시가 발생합니다.
- **실측 프로브 (`agyprobe_hole_len.luau`, `agyprobe_sortunchecked_hole.luau`)**:
  - `agyprobe_hole_len.luau`: `n=3..20`에 대해 1..n-1 위치에 단일 구멍을 뚫었을 때 모든 경우에서 `#t == n`임을 전수 실측 확인.
  - `agyprobe_sortunchecked_hole.luau`:
    ```lua
    local Arr = require("./src/Arr")
    local a = Arr.Sized(4, 10)
    a[2] = nil -- 2번에 구멍 뚫음
    print("Sized holed: #a =", #a, "a.n =", a.n)
    local ok, err = pcall(function()
        Arr.SortInplaceUnchecked(a)
    end)
    print("Result of SortInplaceUnchecked:", ok, err)
    ```
- **실행 명령 및 출력 [실측]**:
  ```bash
  ( ulimit -v 4000000; timeout 600 luau agyprobe_sortunchecked_hole.luau )
  # 출력:
  Sized holed: #a =	4	a.n =	4
  Result of SortInplaceUnchecked:	false	attempt to compare nil < number
  ```
- **판정**:
  주석 1095줄에서 *"# 가 우연히 n 과 같으면"*이라고 마치 예외적인 희귀 케이스인 것처럼 기술했으나, 실측 결과 `Sized`나 `table.create`로 만든 일반적인 배열에서는 **중간 구멍에 대해 100% 필연적으로 `# == n`이 성립**합니다. 따라서 이 가드는 꼬리 구멍(`a[n] == nil`)만 잡을 수 있으며 중간 구멍에 대해서는 전혀 보호를 제공하지 못합니다.

### [메커니즘 3] 컨테이너 메타정보 필드(`n`, `__arr__`)와 딕셔너리 순회의 키 오염

> **뿌리 원인 (한 문장)**:
> 테이블 기반 컨테이너의 내부 메타데이터 필드를 딕셔너리/맵으로 흡수할 때, `__arr__` 태그 유무에만 의존하여 `table.pack` 등 `n` 기반 리스트의 메타필드가 맵의 일반 키로 누출됨.

#### 결함 3-1. [실측 결함] `HashMap.FromTable`에 `table.pack` 결과 전달 시 `n` 키 누출

- **파일 및 위치**: `src/HashMap.luau:228-245`
- **원인 코드**:
  ```lua
  const function FromTable<K, V>(tbl: { [K]: V }): HashMap<K, V>
  	const copy: { [K]: V } = {}
  	local count = 0
  	if rawget(tbl :: any, "__arr__") == true then
  		const list = tbl :: any
  		for idx = 1, Common.listLength(list) do
  			const value = list[idx]
  			if value ~= nil then
  				copy[idx :: any] = value
  				count += 1
  			end
  		end
  		return tagged({ data = copy, size = count })
  	end
  	for key, value in tbl do
  		copy[key] = value
  		count += 1
  	end
  	return tagged({ data = copy, size = count })
  end
  ```
- **메커니즘 상세**:
  `HashMap.FromTable`은 `__arr__` 태그가 있는 `Arr`만 특수 처리하여 숫자 인덱스만 맵으로 가져오고 `n`과 태그 키를 제외합니다.
  하지만 `conventions.md` 38~41줄("리스트 길이 규약")에서는 `Arr`뿐만 아니라 `table.pack` 결과도 `n`을 가진 리스트 형태로 규정하고 있습니다.
  `table.pack(10, 20)`은 `__arr__` 태그가 없으므로 `for key, value in tbl do`로 순회하게 되고, 이 과정에서 **문자열 키 `"n"`(값 2)이 맵의 데이터로 들어가며 `size`가 3으로 계산**됩니다.
- **실측 프로브 (`agyprobe_hashmap_pack.luau`)**:
  ```lua
  local HashMap = require("./src/HashMap")
  local packed = table.pack(10, 20)
  local m = HashMap.FromTable(packed)
  print("HashMap size:", HashMap.Len(m))
  for k, v in HashMap.Iter(m) do
      print("key:", k, "val:", v)
  end
  ```
- **실행 명령 및 출력 [실측]**:
  ```bash
  ( ulimit -v 4000000; timeout 600 luau agyprobe_hashmap_pack.luau )
  # 출력:
  HashMap size:	3
  key:	1	val:	10
  key:	2	val:	20
  key:	n	val:	2
  ```
- **판정 [약속 없음 / 정해야 함]**:
  `FromTable`의 인자 타입은 `{ [K]: V }`로 일반 사전을 받는 진입점입니다. `Arr`를 위해 특별 분기를 둔 것처럼 `table.pack` 결과도 리스트로 대우해 `"n"`을 제외할 것인지, 아니면 리스트 형태는 `FromRecords`나 `FromList`류로만 유도할 것인지 규약을 명확히 해야 합니다.

### [메커니즘 4] 비동기 체인의 자기 참조 사이클(Self-Referencing Cycle) 감지 부재

> **뿌리 원인 (한 문장)**:
> `Fut.Chain`에서 후속 프로미스가 자기 자신을 반환할 때, 상호 의존 사이클을 감지하지 못하고 무한 `Pending` 상태(영구 대기 및 리스너 누수)에 빠짐.

#### 결함 4-1. [실측 한계] `Fut.Chain`의 자기 참조 사이클 영구 대기

- **파일 및 위치**: `src/Fut.luau:367` (`adopt(target, inner)`)
- **메커니즘 상세**:
  `Fut.Chain(p, fn)`에서 `fn`이 결과 Fut인 `target` 자신을 반환하는 경우, `adopt(target, target)`이 호출되어 `target`의 `listeners`에 자기 자신을 settle하는 콜백이 등록됩니다.
  `target`은 자기 자신이 settle되기를 영원히 기다리게 되어, 상태가 무한히 `Pending`으로 남고 가비지 컬렉션되지 않는 메모리 누수 및 데드락이 발생합니다.
  표준 Promise/A+ 2.3.1 규격은 "promise와 x가 동일한 객체를 가리키면 TypeError로 reject해야 한다"고 명시하고 있으나, stl-luau에는 이 가드가 없습니다.
- **실측 프로브 (`agyprobe_fut_cycle.luau`)**:
  ```lua
  local Fut = require("./src/Fut")
  local resolver
  local p = Fut.New(function(res) resolver = res end)
  local target
  target = Fut.Chain(p, function() return target end)
  resolver(1)
  print("Target status:", Fut.Status(target))
  ```
- **실행 명령 및 출력 [실측]**:
  ```bash
  ( ulimit -v 4000000; timeout 600 luau agyprobe_fut_cycle.luau )
  # 출력:
  Target status:	Pending
  ```
- **판정 [약속 없음 / 정해야 함]**:
  현재 문서에는 `Chain`의 자기 반환 시 동작에 대한 약속이 없습니다. `if inner == target then settle(target, "Rejected", nil, "Fut: Chaining cycle detected")` 형태로 즉시 Reject할 것을 제안합니다.

### [메커니즘 5] 동일 어휘의 다의성으로 인한 계약 vs 구현의 의미 불일치

> **뿌리 원인 (한 문장)**:
> 동일한 식별자(`Count`)가 개별 컨테이너 구현체에서는 조건부 필터링(`count_if`)으로, 공용 알고리즘 계약에서는 전체 크기(`len`)로 서로 상충되게 정의되어 사용자 혼란과 잠재적 버그를 유발함.

#### 결함 5-1. [추정/어휘 충돌] `Arr.Count` vs `Algorithm.Count`

- **파일 및 위치**: `src/Arr.luau:320`, `src/Algorithm.luau:46`
- **코드 비교**:
  - `Arr.Count(self: ArrData<T>, fn: Predicate<T>): number` (술어 필수, 조건에 맞는 원소 수)
  - `Algorithm.Count<C, E, I>(ops: ListOps<C, E, I>, list: C): number` (술어 없음, 리스트 전체 원소 수)
- **메커니즘 분석 [추정]**:
  `Arr`에서 리스트의 전체 길이는 `Arr.Len(a)`입니다. 반면 `Algorithm.Count(Arr, a)`는 `ops.FirstIndex`와 `ops.NextIndex`를 순회하며 리스트의 전체 길이를 계산합니다.
  사용자가 `Arr.Count(a)`를 호출하면 `fn`이 `nil`이 되어 `attempt to call a nil value` 에러가 발생합니다.
- **판정 [제안]**:
  Rust(`count()` = 전체 길이), C++(`std::count` = 값 일치 개수, `std::count_if` = 술어 개수) 등의 선례를 참고하여, `Arr.Count`를 `Arr.CountIf`로 변경하거나 인자를 옵셔널로 만들어 `Arr.Count(a)`가 전체 길이를 돌려주도록 통일하는 것을 검토할 만합니다.

### [메커니즘 6] 비교자의 비엄격성(Non-strictness)과 정렬/탐색 계약 위반

> **뿌리 원인 (한 문장)**:
> 3방향 비교자 어댑터(`compareFrom`)에 비엄격 비교자(`<=`)가 전달될 때, 동등성 판정이 영구히 불가능해져 중복 키 삽입 및 검색 실패가 발생함.

#### 결함 6-1. [실측 관측] `Common.compareFrom`에 `<=` 전달 시 `TreeMap` 키 무한 중복 삽입 및 조회 불가

- **파일 및 위치**: `src/Common.luau:105-114`, `src/TreeMap.luau:115`
- **원인 코드**:
  ```lua
  function exports.compareFrom<T>(less: LessThan<T>): Comparator<T>
  	return function(a: T, b: T): number
  		if less(a, b) then
  			return -1
  		elseif less(b, a) then
  			return 1
  		end
  		return 0
  	end
  end
  ```
- **메커니즘 상세**:
  만약 사용자가 실수로 `less`에 `<=`를 전달하면 `less(x, x)`가 참이 되므로 `compareFrom(less)(x, x)`는 항상 `-1`을 반환합니다.
  이를 `TreeMap`에 넘기면 `BSearch.LowerBound` 및 `probe(rec, key) == 0`이 영원히 거짓이 되어, 동일한 키를 `Set`할 때마다 새 레코드가 삽입되어 `size`가 계속 증가하고 `Get`은 키를 찾지 못합니다.
- **실측 프로브 (`agyprobe_treemap_badcmp.luau`)**:
  ```lua
  local TreeMap = require("./src/TreeMap")
  local Common = require("./src/Common")

  local badCmp = Common.compareFrom(function(a, b) return a <= b end)
  local tm = TreeMap.New(badCmp)
  TreeMap.Set(tm, 10, "ten")
  TreeMap.Set(tm, 10, "ten_again")
  print("Size:", TreeMap.Len(tm), "Get:", TreeMap.Get(tm, 10))
  ```
- **실행 명령 및 출력 [실측]**:
  ```bash
  ( ulimit -v 4000000; timeout 600 luau agyprobe_treemap_badcmp.luau )
  # 출력:
  size after first Set:	1
  size after second Set:	2
  record:	10	ten
  record:	10	ten_again
  Get:	nil
  ```
- **판정**:
  `conventions.md`에 이미 "비교자는 엄격해야 한다(`less(x, x) == false`)"고 명시되어 있어 사용자의 계약 위반에 해당합니다. 다만 `NthElement` 등에서 `checkSelectArgs`로 `less(sample, sample)`을 1회 검사해 거절하듯이, `compareFrom`이나 `TreeMap.New`에서도 진입 시 엄격성을 1회 검증하는 가드를 두는 것을 고려해 볼 수 있습니다.

## 3. 잘 설계되어 결함이 발생하지 않은 영역들 [실측 확인]

Claude 세션이 이전 라운드들에서 매우 견고하게 구축하여, 극한의 엣지 케이스에서도 완벽히 방어된 부분들도 실측을 통해 확인했습니다:

1. **`Arr.RotateInplace`의 구멍 회원 보존**:
   - `[10, nil, 30, 40]`을 회전했을 때 `table.move`를 통해 구멍이 정확히 `[nil, 30, 40, 10]`으로 이동함을 확인 (`agyprobe_rotate_hole.luau`).
2. **`HashMap`의 `-0`과 `0` 키 일관성**:
   - Luau 테이블 엔진의 동작에 따라 `-0`과 `0`이 완벽히 동일한 키로 취급되어 `size` 오차가 발생하지 않음을 확인 (`agyprobe_hashmap_zero.luau`).
3. **`HashMap`의 `nil` / `NaN` 키 조회 안전성**:
   - `HashMap.Get(m, nil)`, `HashMap.Has(m, 0/0)` 등이 크래시 없이 안전하게 `nil`/`false`를 반환함을 확인 (`agyprobe_hashmap_nil.luau`).
4. **`Fut`의 `immediate` 스케줄러와 yield 코루틴 격리**:
   - `Fut.Async`가 내부에서 다른 `Fut`을 `Await`하여 yield하더라도, `spawnOwned`가 별도 코루틴을 생성하므로 트램펄린의 `draining` 루프가 블로킹되지 않고 후속 작업들이 정상 실행됨을 실측 확인 (`agyprobe_fut_yield.luau`).
5. **`Arr.Flatmap`의 다중 반환 및 0개 반환 무결성**:
   - `table.pack`을 통해 `count == 0` (빈 반환), `count == 1` (단일 반환), `count > 1` (다중 반환 및 중간 구멍)을 완벽하게 처리함을 확인.

## 4. 제안 및 권고 사항

1. **`Arr.FromIter` 즉시 수정 (우선순위: 최상)**:
   - `iter`의 실제 반환 인자 수(`select("#", ...)`)를 기준으로 분기하여, 2개 이상의 인자가 반환된 경우 둘째 인자가 `nil`이더라도 값으로 취택하도록 수정해야 합니다.
2. **`Arr.FromTable`의 잔여 키 비우기 로직 개선 (우선순위: 상)**:
   - `#raw`에 의존하지 않고, 테이블에 존재하는 숫자 키 중 `k > len`인 키들을 순회하여 제거해야 입양 시 불변식이 완벽히 보장됩니다.
3. **`Arr.SortInplaceUnchecked`의 주석 및 가드 현실화 (우선순위: 중)**:
   - `#self ~= self.n`이 `table.create`/`Sized` 할당 테이블의 중간 구멍을 잡지 못한다는 점을 주석에 명시하거나, unchecked 계약 전제("구멍이 절대 없음")를 호출자의 절대적 책임으로 확정짓는 것이 솔직합니다.
4. **`Fut.Chain` 사이클 가드 추가 (우선순위: 중)**:
   - `if inner == target then settle(target, "Rejected", nil, "Fut: Chaining cycle detected")` 한 줄을 추가하여 영구 데드락을 방지할 것을 권장합니다.
