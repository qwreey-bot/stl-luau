#### 1. `Trait.Expose(trait, entries)`
- **고른 이름**: `Expose` (유지)
- **확신**: 높음
- **이유**: 트레이트 객체에 외부 호출용 진입점 함수들을 얹어 외부에 노출(expose)한다는 행위의 목적을 가장 직관적으로 나타냅니다.
- **처음 보고 짐작한 바와 실제 뜻의 괴리**:
  - `[추정]` 처음 보았을 때 "트레이트 모듈의 공개 API를 외부에 노출(export/expose)하는 함수인가?"라고 짐작했으며, 실제 코드(`src/Trait.luau:468`)에서 진입점 테이블을 검사하고 트레이트 테이블에 합성하여 반환하는 동작과 정확히 일치했습니다.
- **타 생태계 대조**:
  - 후보 중 `Extend`는 Lua/Roblox 클래스 라이브러리(30log, Classic 등)나 JS에서 프로토타입/클래스 상속(`Class:extend()`)으로 널리 쓰여, "트레이트 간의 상속(supertrait)"으로 오해될 소지가 큽니다.
  - `Attach`나 `WithEntries`에 비해, 최종 모듈 반환부(`return Trait.Expose(List, { ... })`, `src/Traits/List.luau:261`)에서 "외부로 노출할 표면을 확정한다"는 뉘앙스가 가장 자연스럽습니다.

#### 2. 트레이트 파일 안의 타입 셋 — `List.Core` / `List.Full` / `List.Provided`
- **고른 이름**: `Core` / `Full` / `Provided` (유지)
- **확신**: 중간
- **이유**: `Ops`/`Full`/`Impl` 시절의 `Impl` 함수명 충돌을 명확히 해소하며, 최소 기반 프리미티브(`Core`)와 완성형(`Full`), 구현자 제공형(`Provided`)의 구분이 체계적입니다.
- **처음 보고 짐작한 바와 실제 뜻의 괴리**:
  - `[추정]` `Core`는 "핵심 필수 함수", `Full`은 "기본 구현이 포함된 전체 함수"로 쉽게 짐작됩니다.
  - **주의할 괴리 지점**: Rust 배경의 개발자는 Rust std 트레이트 문서의 "provided methods"(트레이트가 기본 제공하는 메서드)를 떠올려, `Provided`를 "트레이트가 주는 것"으로 반대로 읽을 위험이 있습니다. 그러나 stl-luau에서는 "구현자가 `Trait.Impl`에 제공(provide)하는 입력 표"(`src/Traits/List.luau:78`)를 뜻합니다.
- **타 생태계 대조**:
  - 후보 `Required`/`Full`/`Provided`도 가능하나, `Core`는 단순한 강제성(`Required`)을 넘어 "모든 파생 알고리즘이 유도되는 기저 프리미티브(basis)"라는 의미를 잘 담고 있습니다.
  - `Input`은 타입명으로서 다소 범용적이므로, 구현자 관점의 `Provided` 유지가 최선입니다.

#### 6. `Arr.Adopt(t)` (입양) 대 `Arr.FromTable(t)` (복사)

- **확신**: 높음

- **처음 보고 짐작한 바와 실제 뜻의 괴리**:

- **타 생태계 대조**:

  - DOM의 `document.adoptNode()`, C++/Qt 생태계의 `adopt` 관례처럼 "소유권 이전 및 원본 종속"을 뜻하는 단어로 `Adopt`가 가장 적절합니다.

#### 7. `FlatMap` / `FlatSet`
- **고른 이름**: `ArrayMap` / `ArraySet` (변경)
- **확신**: 높음
- **이유**: 함수형 프로그래밍의 `flatMap` 고차 함수와의 심각한 어휘 충돌을 피하고, 자료구조 3대 계열(Hash/Tree/Array)의 대칭성을 완벽히 완성합니다.
- **처음 보고 짐작한 바와 실제 뜻의 괴리**:
  - `[추정]` modern JS/TS, Rust, Kotlin, Swift, Java 개발자에게 `FlatMap`은 100% "map 후 flatten하는 함수"로 인식됩니다. 게다가 같은 라이브러리의 `Arr`에 실제로 `Arr.Flatmap`(`src/Collections/Arr.luau:2228`)이 존재하여 인지 부조화가 극에 달합니다.
- **타 생태계 대조**:
  - C++23이 `std::flat_map`을 쓴 이유는 C++ 컨테이너에 `flat_map` 메서드가 없기 때문입니다.
  - 반면 안드로이드/자바 표준 라이브러리는 동일한 "정렬 배열 기반 캐시 친화적 맵/셋"을 **`ArrayMap` / `ArraySet`**(`android.util.ArrayMap`)으로 부릅니다.
  - 무엇보다 stl-luau의 컨테이너 계보가 다음과 같이 완벽한 대칭을 이룹니다:
    - 해시 기반: `HashMap` / `HashSet`
    - 트리 기반: `TreeMap` / `TreeSet`
    - 정렬 배열 기반: **`ArrayMap` / `ArraySet`**
  - 개발자가 이름을 보자마자 내부 자료구조가 무엇인지 즉시 이해할 수 있습니다.

#### 10. `Arr.GroupBy(a, key, into)` / `CountBy` / `KeyBy`
- **고른 이름**: `GroupByInto` / `CountByInto` / `KeyByInto` (변경)
- **확신**: 높음
- **이유**: 목적지 맵(`into`)이 **생략 불가능한 필수 인자**이므로, 새 맵을 반환할 것으로 기대하는 전 세계 개발자의 상식을 배신하지 않도록 이름에 명시해야 합니다.
- **처음 보고 짐작한 바와 실제 뜻의 괴리**:
  - `[추정]` JS(lodash `groupBy`), Kotlin(`groupBy`), Python(`groupby`), C# LINQ(`GroupBy`), Roblox Sift/Llama 등 모든 생태계에서 `groupBy(arr, fn)`는 새 컬렉션을 만들어 반환합니다.
  - stl-luau의 `Arr.GroupBy`(`src/Collections/Arr.luau:2334`)는 3번째 인자 `into`가 없으면 에러가 납니다. 이를 모르고 2개 인자로 호출했다가 터지는 외부 개발자가 속출할 것입니다.
- **타 생태계 대조**:
  - Rust(`collect_into`), C++(`copy_backward`, `transform`)처럼 기존 버퍼/목적지에 결과를 모으는 함수는 `_into`를 붙여 구분하는 것이 표준적인 함수 명명법입니다.
  - `GroupByInto`로 명명하면 "아, 모을 대상(into)을 넘겨줘야 하는구나"를 서명만 보고도 즉시 이해합니다.

#### 11. 목적지 인자의 이름: `to?` vs `into`
- **고른 이름**: 전부 `into` (변경)
- **확신**: 높음
- **이유**: 선택적이든 필수적이든 '결과를 담을 목적지 컨테이너'라는 동일한 의미를 가지므로, 라이브러리 전체의 매개변수 이름을 하나로 통일해야 인지 부하가 없습니다.
- **처음 보고 짐작한 바와 실제 뜻의 괴리**:
  - `[추정]` `Map(a, fn, to?)`(`src/Collections/Arr.luau:1810`)와 `GroupBy(a, key, into)`(`src/Collections/Arr.luau:2334`)를 보면 "왜 하나는 `to`이고 하나는 `into`인가? 둘의 수집 메커니즘이 다른가?"라는 불필요한 의문이 생깁니다.
- **타 생태계 대조**:
  - Rust(`collect_into`), Elixir(`Enum.into`) 등 현대 언어에서 컨테이너 수집 대상 매개변수는 전치사 `into`가 사실상 표준입니다.
  - 선택적 목적지는 `into?`, 필수 목적지는 `into`로 통일하는 것이 가장 깔끔합니다.

#### 12. 경계 찾기: `LowerBound`/`UpperBound` vs `CeilingKey`/`HigherKey`/`FloorKey`/`LowerKey`
- **고른 이름**: 2층을 `Ceiling`·`Higher` 로 (변경)
- **확신**: 높음
- **이유**: `LowerBound`는 '이상(>=)'인데 `LowerKey`는 '미만(<)'이라는 라이브러리 내부의 극단적 모순을 해결하고, 2층(노드)과 3층(트리맵)의 어휘를 통일합니다.
- **처음 보고 짐작한 바와 실제 뜻의 괴리**:
  - `[추정]` 한 라이브러리 안에서 `LowerBound(10)`은 10을 포함하여 위쪽(`>= 10`)을 찾는데, `LowerKey(10)`은 10 미만인 아래쪽(`< 10`, 예: 9)을 찾는 것은 상상을 초월하는 버그 유발 지점입니다.
- **타 생태계 대조**:
  - 3층 `TreeMap`(`src/Collections/TreeMap.luau:255, 264, 283, 291`)의 `CeilingKey`(>=), `FloorKey`(<=), `HigherKey`(>), `LowerKey`(<)는 Java `NavigableMap`의 확립된 표준입니다.
  - 문제의 원인은 2층 `Search`(`src/Trees/Search.luau:68, 82`)가 C++ 어휘(`LowerBound`/`UpperBound`)를 혼용했기 때문입니다.
  - 따라서 2층 노드 검색 함수를 `Search.Ceiling`(>= 노드), `Search.Higher`(> 노드)로 변경하여 3층과 어휘를 일치시키고, `LowerBound`는 배열 삽입 인덱스를 찾는 1차원 알고리즘인 `BSearch`(`src/Algorithms/BSearch.luau:42`)에만 남겨두는 것이 가장 정교한 해결책입니다.

#### 14. 노드 도구 `InsertNext`/`InsertPrev` vs 컨테이너 `InsertAfter`/`InsertBefore`
- **고른 이름**: 노드 도구를 `InsertAfter`·`InsertBefore` 로 (변경)
- **확신**: 높음
- **이유**: 특정 노드를 기준으로 앞/뒤에 삽입하는 동작은 영문법상 전치사 `after`와 `before`가 가장 자연스러우며, 계층 간 어휘를 통일합니다.
- **처음 보고 짐작한 바와 실제 뜻의 괴리**:
  - `[추정]` `InsertNext(node, fresh)`(`src/Node/Double.luau:52`)는 "다음 노드를 삽입하라"는 뜻인지 "노드의 뒤에 삽입하라"는 뜻인지 영문법적으로 다소 어색합니다.
- **타 생태계 대조**:
  - DOM API(`insertBefore`), C++ `std::list` 등 위치 기반 삽입은 항상 `before/after` 개념을 사용합니다.
  - 노드의 내부 슬롯 이름이 `NEXT`/`PREV`라는 것은 구현 세부사항일 뿐이므로, 1층 노드 도구도 `LinkedDeque`(`src/Collections/LinkedDeque.luau:216, 232`)와 마찬가지로 `InsertAfter` / `InsertBefore`로 맞추는 것이 옳습니다.

#### 17. `CompleteArray` / `CompleteNode` 및 함수 `Exchange`
- **고른 이름**: 모듈 쌍은 `CompleteArray` / `CompleteNode` (유지), 함수는 `SwapNodes` (변경)

## 4. 목록에 없지만 꼭 바꿔야 한다고 본 이름 (최대 3개 제안)

### 제안 1. `Optional.ToNil` → `Optional.OrNil` 또는 `Optional.ToNullable`
- **위치**: `src/Optional.luau:95` (`const function ToNil<T>(o: Optional<T>): T?`)
- **문제점**:
  - `[추정]` 함수 이름이 `ToNil`이면 영문법상 "이 값을 nil로 변환하라(강제로 비워라)"는 명령형으로 읽힙니다.
  - 그러나 실제 동작은 "값이 있으면 그 값(`o.value`)을 꺼내고, 없으면 `nil`을 반환"합니다. 즉, `Optional.Present(5)`를 넣으면 `5`가 나오는 함수의 이름이 `ToNil`인 것은 극히 부자연스럽고 사용자에게 공포감을 줍니다.
- **개선안**: Kotlin/TypeScript 스타일의 `ToNullable`, 또는 관용적인 `OrNil` / `UnwrapOrNil`로 변경할 것을 제안합니다.

### 제안 2. `Arr.Flatmap` → `Arr.FlatMap` (대문자 `M`)
- **위치**: `src/Collections/Arr.luau:2228` (`const function Flatmap<T, G>(...)`)
- **문제점**:
  - `[실측]` `Arr.luau` 내의 모든 복합어 함수는 `PushBack`, `PushFront`, `TakeWhile`, `DropWhile`, `FoldUntil`, `FillHoles`처럼 파스칼 표기법(PascalCase)에서 단어마다 첫 글자를 대문자로 씁니다.
  - 그런데 오직 `Flatmap`만 소문자 `m`으로 작성되어 라이브러리 전체의 코드 컨벤션을 홀로 위반하고 있습니다. (7번 항목에서 컨테이너가 `ArrayMap`으로 변경되면 충돌 걱정 없이 당당하게 대문자 `FlatMap`을 쓸 수 있습니다.)
- **개선안**: `Arr.FlatMap`으로 파스칼 표기법 통일을 제안합니다.

### 제안 3. `Fut.AndThen` 대 `Fut.Chain`의 명칭 역전 정정
- **위치**: `src/Fut.luau:50-55`
- **문제점**:
  - `[추정]` 모듈 주석 54줄에는 *"Rust 의 map / and_then 과 같은 구분입니다"* 라고 적혀 있으나, 실제 명명은 정반대로 뒤집혀 있습니다:
    - Rust: `map` = 값을 반환하는 콜백 / `and_then` = Future/Option을 반환하는 모나딕 바인드
    - stl-luau: `AndThen` = 값을 반환하는 콜백 / `Chain` = Fut을 반환하는 콜백
  - Rust 개발자가 `Fut.AndThen`을 보면 당연히 Future를 반환하는 콜백을 넘기려 하다가 타입 에러를 겪게 됩니다. 또한 동일 라이브러리의 `Optional.Map`(`src/Optional.luau:86`)은 값을 매핑하는데 왜 `Fut`만 `AndThen`이 값을 매핑하는지 내부적 일관성도 결여되어 있습니다.
- **개선안**: 값을 반환하는 함수를 `Fut.Map`, Fut을 반환하는 함수를 `Fut.AndThen`(또는 `Fut.FlatMap`)으로 변경할 것을 제안합니다.
