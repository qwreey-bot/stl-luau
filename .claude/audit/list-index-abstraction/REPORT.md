# `Index` 를 타입 파라미터로 뺀 공통 List 인터페이스 — 실측

**날짜**: 2026-09-21 · **도구**: `luau-analyze` (luau 0.734)
**스파이크**: `spikes/00-index-abstraction.luau` (기대 진단 **7건**)

## 결론

**된다.** 배열 기반과 연결 기반 리스트가 **인덱스 타입만 다른 같은 인터페이스**를
공유하고, 공통 알고리즘을 **한 번만** 짜서 양쪽이 쓰는 구조가 Luau 타입에서
완전히 성립합니다. 규모 증상 0건.

## 설계

리스트를 "원소 타입 `E`" 와 **"위치를 가리키는 타입 `I`"** 두 파라미터로 봅니다.

```lua
export type ListCore<E, I> = {
	Get:        (self: ListCore<E, I>, idx: I) -> E?,
	FirstIndex: (self: ListCore<E, I>) -> I?,
	LastIndex:  (self: ListCore<E, I>) -> I?,
	NextIndex:  (self: ListCore<E, I>, idx: I) -> I?,
	PrevIndex:  (self: ListCore<E, I>, idx: I) -> I?,
}
```

구현체는 이 **다섯 개만** 제공합니다:

| 구현 | `I` (위치 타입) |
|---|---|
| 배열 기반 | `number` |
| 연결 기반 | `Node<E>` (노드 자체가 곧 위치) |

`IndexOf` / `Contains` / `Count` 같은 순회 알고리즘은 primitive 다섯 개만으로
쓰이므로 **소스에 한 번만 존재하고** 두 구현이 공짜로 씁니다.

## 왜 이 모양인가

연결 리스트에서 `Get(3)` 은 O(n) 입니다. 인덱스를 `number` 로 못박으면
사용자가 `for i = 1, n do list:Get(i) end` 라고 써서 O(n²) 를 만듭니다 —
**타입이 성능 함정을 못 막습니다.** 위치 타입을 구현에 맡기면 연결 리스트의
위치는 노드가 되고, 순회는 `NextIndex` 로만 가능해져 그 함정이 문법적으로
사라집니다.

## 실측 (기대 진단 7건)

**양성 — 에러가 없어야 함**: 같은 `IndexOf`/`Contains`/`Count` 가 배열/연결
양쪽에 쓰이고, 반환 위치 타입이 각각 `number?` 와 `Node<E>?` 로 정확히 잡힙니다.

**음성 — 전부 검출됨**:

| 무엇 | 결과 |
|---|---|
| 배열의 위치를 `Node<E>?` 로 받기 | ✅ 검출 |
| 연결의 위치를 `number?` 로 받기 | ✅ 검출 |
| 원소 타입 불일치 (`string` 리스트에 `42` 찾기) | ✅ 검출 |
| **다른 구현의 위치를 섞어 쓰기** (`al:Get(ll:FirstIndex())`) | ✅ 검출 |
| `Count` 결과를 `string` 에 대입 | ✅ 검출 |

넷째 항목이 핵심입니다 — 배열의 위치와 연결의 위치가 **타입으로 갈라져**
섞이지 않습니다.

## 남은 것

- 이 구조를 지금의 `Arr<T>`(54개 콜론 메소드)와 **어떻게 잇는가**. `Arr` 이
  `ListCore<T, number>` 를 만족하게 두고 공통 알고리즘을 자유 함수로 빼는
  방식이 후보입니다. 메소드 수가 많으므로
  `.claude/audit/arr-type-redesign/` 의 규모 실측(교집합 필수, 30개에서
  `setmetatable` 붕괴)을 같이 만족해야 합니다 — **아직 합쳐서 재보지 않았습니다.**
- 변경 연산(`Insert`/`Remove`)을 이 인터페이스에 넣을지. 위치 타입이 노드면
  삽입/삭제가 O(1) 이고 배열이면 O(n) 이라, 복잡도가 구현마다 다른 연산을
  공통 인터페이스에 두는 게 맞는지 판단이 필요합니다.
