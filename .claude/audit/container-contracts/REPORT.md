# 컨테이너 계약 — Luau 실측

**날짜**: 2026-09-21 · **도구**: `luau-analyze` (luau 0.734)

예전 과제(`Assignment9/Utils/`)의 계약 설계와 세 표준 라이브러리의 구조를
Luau 타입으로 옮길 수 있는지 잰 것입니다.

## 1. 세 계약 모두 성립합니다 (`spikes/00-contracts.luau`)

| 계약 | 결과 |
|---|---|
| **위치 타입을 파라미터로 뺀 트리** `TreeCore<K, V>` | ✅ 배열 기반(`K = number`)과 연결 기반(`K = Node<V>`)이 **같은 `Height` 알고리즘**을 공유. 두 위치를 섞으면 검출 |
| **해시 전략 주입** `Hasher<T>` | ✅ 생성자 인자로 주입, 키 타입 불일치 검출 |
| **레코드 타입을 포함한 Map 계약** `MapCore<K, V>` | ✅ 해시맵/트리맵이 같은 `Keys` 알고리즘 공유 |

이건 `.claude/audit/list-index-abstraction/` 의 `ListCore<E, I>` 와 같은 원리가
트리·맵에도 서는 것을 확인한 것입니다.

## 2. 계약을 확장하는 네 방식 모두 통과 (`spikes/01`, `02`)

공용 알고리즘에 "계약을 확장한 구현체"를 넘길 때:

| 확장 방식 | 결과 |
|---|---|
| 확장 없음(계약 그대로) | ✅ |
| **교집합** `MapCore<K,V> & { Ordered }` | ✅ |
| 필드를 펼쳐 쓴 단일 테이블 | ✅ |
| 컴포지션(`{ core: MapCore<K,V>, … }`) | ✅ |

변경 연산(`Set(k: K, v: V)` — K 가 입력 자리)이 계약에 있어도 깨지지 않습니다.

## 3. ⚠️ 그런데 **선언 순서**가 이걸 깹니다 (`spikes/03`, `04`)

같은 코드인데 **선언 순서만** 바꾸면 결과가 달라집니다:

| 순서 | `Keys(treeMap)` 결과 |
|---|---|
| 트리 절이 맵 절보다 **앞** | ❌ `{K & string}` (기대: `{string}`) |
| 맵 절이 트리 절보다 **앞** | ✅ `{string}` |

`03` 과 `04` 는 **선언 순서 말고 한 글자도 다르지 않습니다.**

**quad `typing-limits.md` §8.21 과 같은 계열**입니다. quad 는 이걸 Luau 솔버
소스까지 파고들어 원인을 밝혀뒀습니다 — 신 솔버가 별칭 확장을 선언 순서대로
처리하는데, 무한 확장 가드가 "아직 확장 안 된 같은 별칭 참조"를 오판해 바깥
확장을 통째로 에러 타입으로 묶고, **진단은 내지 않습니다**. 구 솔버는 문장을
의존성 순으로 재정렬해서 이 문제가 없습니다.

차이: quad 의 사례는 **비균일 재귀 별칭**(`Compute: <U>(…) -> S<U>`)이 원인인데
제 재현은 **재귀 제네릭 함수**가 앞에 있을 때 납니다. 같은 뿌리인지는 확인하지
않았습니다 — 증상과 처방이 같을 뿐입니다.

### 실무 규칙

**공유 계약은 그것을 인스턴스화하는 모든 것보다 먼저 선언합니다.**

파일 안에서 순서를 지키는 것보다 **모듈로 강제하는 게 안전합니다** — 계약을
`common.luau` 같은 말단 모듈에 두고 `require` 하면, 다른 모듈에서 이미 풀린
타입으로 들어오므로 순서 문제가 원천적으로 사라집니다(quad 도 *"다른 모듈에서
가져와 쓸 것"* 을 규칙으로 적어뒀습니다).

이게 스캐폴딩 설계에 직접 영향을 줍니다 — 아래.

## 4. 스캐폴딩에 주는 함의

1. **계약(타입)은 말단 모듈에 모은다.** 다른 컨테이너를 `require` 하지 않는
   파일에 두어 순환도 없고 선언 순서 문제도 없습니다.
2. **구현은 계약만 만족하면 되고, 공용 알고리즘은 한 번만 쓴다.**
   위치 타입을 파라미터로 빼면 배열/연결/트리가 같은 알고리즘을 공유합니다.
3. **전략(해시/비교)은 생성 함수의 인자로 주입한다.** 컨테이너 본체에서
   타입별 분기가 사라집니다.
