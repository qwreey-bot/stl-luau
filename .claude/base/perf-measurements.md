# 성능 실측

이 저장소는 *"최적화 주장은 실측으로 뒷받침한다"* 를 규칙으로 둡니다
(`.claude/conventions.md`). 그래서 잰 것을 전부 여기 모읍니다.

**재는 방법**: 래퍼 클로저를 끼지 말고 루프에서 직접 호출할 것. 여러 번 재고
**최소값**을 쓸 것(노이즈 회피). 환경은 `luau 0.734`, 2026-09-22.

---

## 1. ⭐ 메타테이블이 붙어 있으면 인덱싱이 1.59배 느리다

원소 200만 개를 `for i = 1, t.n do acc += t[i] end` 로 더한 시간:

| 테이블 | 시간 | 배수 |
|---|---|---|
| 메타테이블 없음 | 0.0086s | **1.00x** |
| 빈 메타테이블 `{}` | 0.0136s | **1.59x** |
| `__index` 있는 메타테이블 | 0.0136s | 1.59x |
| `table.freeze` 한 메타테이블 | 0.0136s | 1.59x |
| `rawget(t, i)` 로 우회 시도 | 0.0136s | 1.59x |

**원인은 `__index` 가 아니라 메타테이블의 존재 자체입니다** — 빈 메타테이블도
똑같이 느려지고, `rawget` 로도 못 피합니다(C 함수 호출 비용이 그만큼).

### 그런데 메타테이블을 버릴 수는 없다

메소드를 인스턴스마다 복사하면 인덱싱은 빨라지지만:

| | 메타테이블 부착 | 메소드 54개 복사 |
|---|---|---|
| 작은 배열 20만 개 생성 | 0.0137s | 0.2791s (**20.4배**) |
| 인스턴스당 메모리 | 96바이트 | 2112바이트 (**22배**) |

컨테이너 라이브러리는 작은 인스턴스를 많이 만듭니다. **메타테이블을 씁니다.**
1.59배는 치르는 값이고, 아래 2번이 그걸 되갚는 방법입니다.

## 2. ⭐ `table.move` 는 메타테이블의 영향을 전혀 받지 않는다

원소 100만 개 복사:

| 방법 | 시간 | 배수 |
|---|---|---|
| `table.move` (메타테이블 유무 무관) | 0.0005~0.0008s | **1.00x** |
| 손 루프 `for i = 1, n do b[i] = a[i] end`, 메타테이블 없음 | 0.0059s | 7.6배 |
| 손 루프, **메타테이블 있음** | 0.0111s | **14.3배** |

`table.move` 는 C 안에서 돌며 메타테이블을 보지 않습니다. 그래서 1번의 1.59배
세금을 아예 안 냅니다.

**그래서 이 저장소가 `table.move`/`table.create` 를 고집하는 것이 취향이 아니라
14배짜리 결정입니다.** 벌크로 할 수 있는 일을 원소 루프로 쓰지 마세요.

## 3. 순회 — `ipairs` 가 가장 빠르다 (조건부)

원소 200만 개, 메타테이블이 붙은 실제 컨테이너 모양 기준:

| 방법 | 시간 | 배수 | 루프 변수 타입 | 구멍 |
|---|---|---|---|---|
| `for _, v in ipairs(arr)` | 0.0063s | **0.39x** | ✅ | ⚠️ 첫 구멍에서 멈춤 |
| **`for i = 1, arr.n do … arr[i]`** | 0.0163s | **1.00x (기준)** | ✅ | ✅ `n` 을 지킴 |
| `for _, v in arr:Iter()` | 0.0472s | 2.89x | ✅ | ✅ |
| `for _, v in arr` (`__iter`) | 0.0468s | 2.86x | ❌ **죽음** | ✅ |
| `arr:Fold(init, fn)` 콜백 | — | 2.54x | ✅ | ✅ |

**`ipairs` 의 조건**: `#` 기준으로 돌며 **첫 `nil` 에서 멈춥니다.** 이 저장소의
컨테이너는 `n` 을 진실로 삼고 구멍을 허용하므로, **라이브러리 내부에서는 쓸 수
없습니다.** 배열이 조밀한 것을 아는 사용자에게만 권할 수 있습니다.

**라이브러리 내부의 기본은 `for i = 1, self.n`** 입니다.

## 4. ⭐ `arr:Iter()` 는 교집합에서도 타입이 산다 — `__iter` 는 필요 없다

교집합 타입은 `for-in` 루프 변수의 타입을 잃습니다(`spikes/35`). 그런데 그건
for-in 이 **컨테이너의 인덱서**를 볼 때의 이야기이고, **메소드가 이터레이터
삼중항을 돌려주면** for-in 은 그 함수의 반환 타입을 봅니다. 그래서 삽니다.

```lua
for i, v in arr:Iter() do … end   -- i: number, v: T  (교집합인데도 정확)
```

**단, 이터레이터 함수를 `(number, T)` 로 선언해야 합니다** — 끝에서 `nil` 을
돌려주지만 타입에는 드러내지 않습니다. 정직하게 `(number?, T?)` 로 선언하면
루프 변수가 옵셔널이 되어 산술에 바로 못 씁니다. **Luau 자신의 `ipairs` 도
같은 방식**입니다.

실측: `spikes/37-iter-method-vs-metamethod.luau` (기대 5건).

비용은 2.89배로 `__iter` 와 같습니다 — 타입을 잃지 않는 쪽이 무조건 낫습니다.

## 5. 정렬 비교자 — 3방향을 쓰면 1.82배

20만 개 정렬:

| 방법 | 시간 | 배수 |
|---|---|---|
| `table.sort(t)` — 비교자 없음 | 0.0151s | 0.22x |
| `table.sort(t, lt)` — 불리언 비교자 | 0.0678s | **1.00x (기준)** |
| 3방향 비교자를 래퍼로 감싸 넘김 | 0.1233s | **1.82x** |

`table.sort` 가 받는 것이 불리언이라 3방향은 비교마다 클로저가 한 겹 더 붙습니다.
그래서 **정렬의 기본 통화는 `LessThan`(불리언)** 이고, 3방향 `Comparator` 는
정렬된 구조에서의 탐색(이분 탐색·트리)용입니다 — 거기서는 "같다" 를 한 번에
알아야 해서 3방향이 오히려 절반입니다. 자세한 것은 `src/Common.luau` 상단.

## 9. ⭐ 정렬 병합은 해싱을 못 이긴다 (2026-09-22)

`TreeSet` 의 집합 연산은 양쪽 정렬 배열을 한 번씩 훑는 **O(n + m) 병합**이고
해시를 한 번도 계산하지 않습니다. 교과서대로라면 이겨야 합니다. 원소 10만
개(절반 겹침)로 쟀습니다:

| 연산 | HashSet | TreeSet | |
|---|---|---|---|
| `Union` | 0.0028s | 0.0163s | **5.9배 느림** |
| `Intersect` | 0.0043s | 0.0049s | 1.2배 |
| `Has` × 10만 | 0.0030s | 0.0696s | **23.4배 느림** |
| `FromList` | 0.0010s | 0.0495s | **50배 느림** |

**이유**: Luau 의 테이블 해싱은 **C 안에서** 돌고, 우리 병합은 **Lua 클로저로
비교자를 부릅니다.** 알고리즘 차수가 아니라 상수가 이깁니다. 1번·2번에서
본 것과 같은 이야기입니다 — *이 런타임에서는 C 로 내려가는 쪽이 거의 항상
이깁니다.*

`Intersect` 만 비슷한 것은 결과가 작아 양쪽 다 할당이 적기 때문입니다.
`Union` 의 격차에는 레코드 테이블을 원소마다 새로 만드는 비용이 섞여 있습니다.

**그래서 `TreeSet`/`TreeMap` 은 순서를 위한 것이지 속도를 위한 게 아닙니다.**
순서가 필요 없으면 해시 쪽이 모든 축에서 낫습니다.

### 정렬 컨테이너에 많이 담을 때는 벌크 생성자를 쓸 것

| 원소 2만 개 담기 | 시간 | |
|---|---|---|
| `Add` 를 2만 번 | 0.0959s | **7.5배** |
| `FromList` (정렬 후 한 번에) | 0.0129s | 1.00x |

삽입마다 뒤를 밀어 O(n^2) 이 됩니다. `TreeMap.FromRecords` 도 같은 이유로
한 번에 정렬해서 담습니다.

## 10. 힙 — 교과서의 O(n) 대 O(n log n) 이 실측에선 상수차다 (2026-09-22)

`Heap.FromList`(가운데부터 거꾸로 내려가며 만들기)와 `Push` 반복:

| N | FromList | Push 반복 | |
|---|---|---|---|
| 10,000 | 0.0005s | 0.0009s | 1.86배 |
| 100,000 | 0.0056s | 0.0095s | 1.68배 |
| 500,000 | 0.0271s | 0.0473s | 1.74배 |

차수로는 O(n) 대 O(n log n) 이라 N 이 커질수록 벌어져야 하는데 **1.7배
안팎으로 거의 일정합니다.** 무작위 입력에서는 `Push` 의 평균 밀어올림 깊이가
상수이기 때문입니다 — 새 원소는 거의 항상 아래쪽에 자리잡습니다.

**교훈**: 차수만 보고 "훨씬 빠를 것" 이라고 쓰지 말 것. 1.7배는 1.7배대로
값지지만, 그게 이유인 척하면 안 됩니다.

### 그 밖

| `PushPop` vs `Push` 후 `Pop` (20만 회) | **1.78배 쌈** |

## 11. checked / unchecked 로 가른 값 (2026-09-22)

`nil` 구멍 검사를 빼면 얼마나 빨라지는가. **실제 콜론 메소드 호출로** 쟀고
원소 20만/200만에서 같은 배수가 나왔습니다.

| 무엇 | checked | unchecked | |
|---|---|---|---|
| `Max` / `Min` | 0.0262s | 0.0143s | **1.83배** |
| `SortInplace` | 0.0179s | 0.0151s | 1.18배 |
| `Sum` / `Prod` | 0.0147s | 0.0136s | 1.08배 |

(`Max`/`Sum` 은 N=200만, `SortInplace` 는 N=20만)

**`Max`/`Min` 이 유독 큰 이유**: 검사 있는 판은 원소마다 `nil` 검사에 더해
*"아직 첫 값을 못 찾았는가"* (`best == nil`) 분기까지 봅니다. 검사를 빼면
첫 원소를 씨앗으로 잡고 2번부터 도는 단순한 루프가 됩니다.

**`Sum` 의 8%** 는 작지만 두 크기에서 똑같이 나왔습니다. 앞서 6절에서
평범한 테이블에 13% 로 쟀던 것과 방향이 같고, 메타테이블 세금(1번)이 섞여
상대 비중이 줄어든 것입니다.

### ⚠️ `SortUnchecked` 만 조용히 틀린다

| 무엇 | 구멍을 만나면 |
|---|---|
| `SumUnchecked` / `ProdUnchecked` | `nil` 산술로 **터짐** |
| `MaxUnchecked` / `MinUnchecked` | 비교에서 **터짐** |
| `SortUnchecked` / `SortInplaceUnchecked` | `table.sort` 가 `#` 를 보므로 **구멍 뒤쪽이 조용히 잘림** |

셋 중 마지막만 터지지 않습니다. 그래서 문서에서 그 줄을 특히 강조합니다.
(2026-10-02 꼬리표: **M0 6라운드 이후 사실 아님** — `#` ≠ `n` 이면 checked 판으로 넘어가고,
같으면 비교 에러로 터집니다. 무작위 2만 건에서 조용히 틀린 답 0. 위 표는 당시 기록.)

## 12. 구멍을 정리하고 unchecked 로 가는 것 — 한 번이면 손해 (2026-09-26)

원소 20만, 구멍 10%.

| 무엇 | 배수 (checked `Sum` = 1.00) |
|---|---|
| `FillHolesInplace` 만 | 1.02x |
| `FillHolesInplace` + `SumUnchecked` | **1.88x (더 느림)** |
| `FillHoles`(새 배열) 만 — 2026-09-30 | 1.45x |
| `FillHoles`(새 배열) + `SumUnchecked` — 2026-09-30 | 2.33x |
| `CompactInplace` + `SumUnchecked` | 2.41x |

| `ToOptionals` | 4.96x |

**정리 한 번이 checked 집계 한 번만큼 듭니다.** 그래서 손익은 횟수로
갈립니다 — 한 번 정리하고 `Max` 를 k 번:

| k | checked 대비 |
|---|---|
| 1 | 0.87x (손해) |
| 2 | 1.15x |
| 3 | 1.32x |

구멍을 치우는 비용까지 셈에 넣으면 **두 번째 연산부터** 이득입니다.

(2026-09-30) 이 표의 제자리 판은 그때 이름이 `FillHoles` 였고 지금은

하면서(`question.md` T, U) 들였고 `?` 를 떼는 정식 경로입니다 — 할당이 있어도
`Compact`(1.8~1.9x)보다 쌉니다. 같은 조건에서 다시 재니 제자리 판은
1.03~1.05x, `+ SumUnchecked` 는 1.91x 로 위 숫자와 맞았습니다.

`Optional.Present` 하나는 **128바이트**입니다.

## 13. `Fut` 한 번의 값 (2026-09-26)

10만 회 × 5회 중 최소.

| 무엇 | 1회당 |
|---|---|
| 평범한 함수 호출 | 0.012µs |
| `pcall` | 0.037µs |
| 코루틴 생성 + `resume` | 0.174µs |
| `Fut.Resolved(x)` | 0.150µs |
| `Fut.Resolved(x):AndThen(fn)` | **0.774µs** |

`AndThen` 은 콜백을 **새 코루틴에서** 돌립니다 — 그래야 콜백 안에서
`Await` 할 수 있습니다. 그 몫이 0.17µs 이고 나머지는 결과 팩·리스너 테이블
할당입니다. 비동기 연산은 컨테이너 연산보다 훨씬 드물게 일어나는 자리라
받아들였습니다. 핫 루프에서 `Fut` 을 만들지는 마세요.

**나중에 재볼 것**: 코루틴을 풀로 재사용하면 0.17µs 를 줄일 수 있습니다.
부르는 곳이 생겨 이게 병목으로 측정되면 그때.

### [2026-09-30] 정확성 수정 뒤 — 0.77µs → 1.05µs

리뷰가 재현한 버그 둘을 고치느라 즉시 스케줄러를 **트램펄린**(재진입 가드가
있는 드레인 루프)으로 바꾸고 **잡마다 `pcall` 로 격리**했습니다. 그 값이
`AndThen` 한 번에 약 **+0.35µs** 입니다(3회 반복, 이전 커밋과 같은 벤치로 대조).

| | `AndThen` 순수 비용 |
|---|---|
| 이전 (그냥 `job()`) | 0.60µs |
| 지금 (트램펄린 + 격리) | 0.95µs |

**받아들였습니다.** 이전 판은 사슬이 약 198단을 넘으면 "C stack overflow" 로
**거짓 실패**했고, 리스너 하나가 에러를 내면 **나머지가 영원히 대기**했습니다.

본문을 감싸는 클로저 할당을 없애는 판(큐에 "코루틴으로 띄울 본문" 표시를
따로 둠)도 재봤는데 **빨라지지 않아** 되돌렸습니다. 비용은 할당이 아니라 격리
`pcall` 과 큐를 도는 데서 옵니다.

## 14. 호출 모양 — 네임스페이스 함수가 콜론보다 빠르다 (2026-09-30)

같은 함수(`Len`)를 세 모양으로 500만 회:

| 모양 | 배수 |
|---|---|
| `a:Len()` (콜론 — 메타테이블 `__index` 경유) | 1.00x |
| `Arr.Len(a)` (네임스페이스 필드) | **0.82x** |
| `local Len = Arr.Len; Len(a)` (지역 변수) | **0.64x** |
| `a.n` (참고 — 필드를 바로) | 0.24x |

콜론 호출은 인스턴스에서 못 찾고 메타테이블 `__index` 로 한 번 더 가야
합니다. 네임스페이스는 평범한 테이블 필드 조회 한 번이고, `local` 로 받으면
그것도 없어집니다.

**사용자 방향(절차적 호출이 1급)과 성능이 같은 쪽을 가리킵니다.** 그래서
모든 컨테이너가 메소드를 네임스페이스 함수로도 노출합니다(`Arr.Map(a, fn)`).
뜨거운 루프에서는 `local Map = Arr.Map` 으로 받아 쓰세요 — 제네릭은 호출마다
새로 풀립니다(`spikes/49`).

### 15-3. 선택의 병적 입력 — 리뷰가 찾은 O(n²) 와 고친 뒤 (2026-09-30)

리뷰(opus)가 "정렬된 배열 끝에 최솟값 하나" 에서 `NthElement` 가 **n=16000 에
1.4초, 10만에 2분 넘게**라는 걸 재현했습니다. 중앙값 셋의 후보가 끝점(lo/hi)
이라 끝의 극단값이 매번 나쁜 피벗을 만들었습니다. 두 겹으로 고쳤습니다.

| 원소 10만, 기준 = `Arr.Sort(a, less)` | 끝점 후보 + 예산 폴백 | **1/4·1/2·3/4 후보** + 예산 폴백 |
|---|---|---|
| 무작위 | 0.18x | 0.18x |
| 정렬 + 끝에 최솟값 | 3.02x (폴백이 구함) | **0.12x** |
| 최댓값 + 정렬 | — | 0.12x |
| 오르내림(organ pipe) | — | 0.13x |
| 이미 정렬 / 역순 | 0.08x / — | 0.08x / 0.13x |

**예산 폴백**(분할이 약 2·log₂n 번을 넘으면 남은 구간을 `table.sort`)은 어떤
피벗 규칙이든 이기는 입력을 위한 보증입니다. McIlroy 의 적대적 비교자로 재면
n=4000 에서 **폴백 없이 300만 번(751n), 있으면 28만 번(70n)** 입니다 —
`spec.arr` 18절이 이 적대자로 폴백 경로를 지킵니다. 스캔 경계 검사(엄격하지
않은 비교자 방어)는 무작위 입력에서 측정 차이가 없었습니다(0.17x → 0.18x).

**남은 한계(2라운드 리뷰 실측)**: 주기가 n/4 인 톱니, 정렬된 구간 넷을 이어붙인
모양처럼 **1/4·1/2·3/4 후보가 같은 위상에 걸리는** 입력에서는 비교가 10~14n 이라
n=2만에서 `NthElementInplace` 4~5ms 대 비교자 없는 `Sort()` 1.3~1.5ms 입니다.
이차는 아니고(예산 폴백), 비교자를 주는 `Sort(lt)` 보다는 여전히 빠릅니다.
무작위 입력은 수정 전과 같습니다(2.43n 대 2.38n).

## 16. 메타테이블을 아예 없애면 — 호출 모양이 아니라 **인덱싱**이 갈린다 (2026-10-01)

## 17. `SortInplaceUnchecked` 의 `#` 검사 비용 (2026-10-01, M0 6라운드)

- ⭐ **`data` 테이블을 돌려줌 — 같은 날 사용자 결정(질문 AP 1)으로 이것이 지금입니다.** 일반화 순회(`for k, v in
  HashMap.Iter(m)` 이 테이블을 직접 돎)라 Luau 래퍼 대비 **9배**, `next` 삼중항 대비 5배. 실제 모듈로 다시 잼:
  조밀한 숫자 1000개 **3.15us**, 10만 개 0.32ms, 문자열 10만 개 0.54ms — 표의 "`data` 테이블" 열 그대로. 반환이 함수가
  아니게 돼서 `Arr.FromIter` 가 테이블을 받게 했고, `MapOps.Iter` 의 계약 타입은 "테이블 또는 인자 없는 함수" 유니온이
  됐습니다(그 대가: 계약 타입을 거친 `ops.Iter(m)` 의 루프 변수는 `any` — `spikes/63` 알려진 경계).
- `HashSet.Iter` 는 `(item, item)` 을 돌려주는 설계(`TreeSet` 과 바꿔 끼우려고)라 래퍼가 필요해 그대로입니다.
  (→ 2026-10-13 에 안쪽을 `원소 → 원소` 로 바꿔 같은 이득을 얻음 — 29절.)
- (정정) 25절의 "`Iter` 로 옮기면 할당이 결과 테이블 하나로" 는 맞지만 **시간은 따로 재야** 했습니다 — 래퍼가 있던
  때는 `Records` 경유와 비겼습니다(HashMap 0.95~1.13배, TreeMap 0.77~0.90배). 옮긴 뒤의 숫자는 28절.

## 29. `HashSet.Iter` — 안쪽을 `원소 → 원소` 로 두고 테이블 그대로 (2026-10-13, 사용자 결정)

`HashSet.Iter` 는 `(item, item)` 을 내려고(`TreeSet.Iter` 와 `for _, item in` 모양을 맞추려고) `next` 를 Luau 함수로
감싸고 있었습니다 — 27절의 `HashMap.Iter` 와 같은 비용. 안쪽 테이블이 `원소 → true` 라 그대로 돌려주면 둘째 값이
`true` 가 되는 것이 걸림돌이었는데, **값에 원소 자신을 넣으면**(`data[item] = item`) 테이블을 그대로 돌려줘도
`(item, item)` 입니다. `bench-ignoreme/set-iter.luau`(사본)·`set-iter-mod.luau`(실제 모듈 전·후), `-O2`, 25회 최소:

| 키 | N | `Iter` 순회 예전 | **지금** | `FromList` 예전 → 지금 | `Union` | `Add` ×N |
|---|---|---|---|---|---|---|
| 숫자 | 10 | 0.40us | **0.07us (0.18)** | 0.97 → 0.97us | 0.80 → 0.81 | 1.00 → 1.02 |
| 숫자 | 1000 | 35.8us | **3.7us (0.10)** | 53~56 → 54~58us | 52~54 → 47~54 | 74~78 → 72~81 |
| 숫자 | 100000 | 4.37ms | **0.55ms (0.13)** | 8.12 → 8.00ms | 7.22 → 7.14 | 9.15 → 9.06 |
| 문자열 | 1000 | 37.8us | **3.7us (0.10)** | 45.8 → 44.4us | 42.9 → 38.4 | 68.0 → 65.6 |
| 문자열 | 100000 | 5.08ms | **0.54ms (0.11)** | 7.49 → 7.07ms | 7.95 → 8.49 | 9.24 → 9.05 |

- 순회만 0.10~0.18배, **쓰기 쪽(생성·합집합·추가)은 잡음 안에서 같습니다** — 값 칸에 `true` 대신 원소를 넣을 뿐이라
  메모리도 같습니다(숫자 1000개 `FromList` 가 한 번 76us 로 튄 것은 다시 세 번 재서 54~58us — 잡음).
- 다른 안: 안쪽을 `원소 → true` 로 두고 테이블을 돌려주면 속도는 같지만(사본 벤치 3.5us) `for _, item in` 과
  `Arr.FromIter(HashSet.Iter(s))` 가 `true` 를 받습니다(뒤쪽은 `any` 라 타입도 못 잡음). 그래서 이쪽.
- `TreeSet.Iter` 는 정렬 레코드 배열이라 테이블을 그대로 내줄 수 없습니다(내주면 원소가 둘째 자리). 값 하나만
  내는 클로저로 바꾸면 0.81~0.85배(34.9 → 28.2us)인데 `for _, item in` 이 깨져 그대로 뒀습니다.

## 30. `TreeMap`(정렬 배열) 대 노드 기반 균형 트리 (2026-10-13, 사용자 질문)

사용자: *"트리맵은 정렬 배열이였음? … 인서트가 뒤 밀기 때문에 문제가 되지 않아? 일반 정의는 아닌것 같은데."*
정렬 배열로 정한 뒤 **노드 트리와 견줘 잰 적이 없었습니다.** `bench-ignoreme/treemap-vs-nodes.luau`(`-O2`, 서로 다른 키 N 개,
비교용 노드 트리는 최소 AVL — 넣기·조회·중위 순회만):

| N | 무작위로 넣기 (배열 / 노드) | 오름차순으로 넣기 | 내림차순(배열) | 조회 N 번 (배열 / 노드) | 순회 | `FromRecords`(한 번에) |
|---|---|---|---|---|---|---|
| 100 | 0.04 / 0.06ms (**0.65배**) | 0.03 / 0.06ms | 0.04ms | 0.04 / 0.01ms (2.4배) | 같음 | 0.04ms |
| 1000 | 0.63 / 0.85ms (**0.75배**) | 0.33 / 0.79ms | 0.63ms | 0.49 / 0.24ms (2.0배) | 0.034 / 0.043ms | 0.57ms |
| 10000 | 18.2 / 12.8ms (**1.42배**) | 4.4 / 10.6ms | 26.6ms | 7.6 / 3.9ms (2.0배) | 0.51 / 0.64ms | 8.5ms |
| 100000 | 1356 / 266ms (**5.1배**) | 62 / 144ms | **2227ms** | 190 / 107ms (1.8배) | 24.4 / 28.9ms | 172ms |

- **넣기**: 뒤를 미는 비용은 `table.move` 라 작은 맵(~수천)에서는 노드 트리보다 오히려 빠르지만, 그 위로는 O(n²) 이
  드러납니다 — 10만 개를 무작위로 넣으면 5배, 앞쪽에 계속 넣으면(내림차순) 2.2초. 뒤에만 붙는 경우(오름차순)와
  한 번에 만드는 경우(`FromRecords`)는 배열이 빠릅니다.
- **조회**: 지금 구현은 노드 트리의 절반 속도입니다 — 이분 탐색 한 걸음마다 `probe` 클로저와 비교자, 호출이 둘씩
  듭니다(노드 트리는 비교자 하나). 정렬 배열이라서가 아니라 구현 탓이라 줄일 여지가 있습니다.
- **순회**: 비슷(배열이 조금 빠름).
- 정리: 정렬 배열 맵은 **작거나, 한 번에 만들거나, 순서대로 들어오는** 쓰임에 맞고, 크면서 아무 데나 넣고 빼는
  쓰임에는 맞지 않습니다. 이름으로는 C++ 의 `flat_map`·C# 의 `SortedList` 에 해당하고, Java 의 `TreeMap`(레드-블랙
  트리)과는 성능 모양이 다릅니다.

## 36. `Join` 위에 세운 균형 트리 — 시제품 (2026-10-13, `papers/07` 9-3 의 근거)

질문(사용자): 이진 트리에서 어떤 키보다 작거나 큰 영역을 **떼어 트리로** 둘 수 있는가, 균형 방식(RB 등)을 여럿
두면서 구현을 **공유**할 수 있는가. 시제품 `.claude/research/tree-join/SearchTree.luau` — 균형 방식은
`Join(left, mid, right)` 하나만 구현하고(AVL 로 해 봄), `Split`·넣기·지우기·합집합은 `Join` 만 받아 한 번 씁니다.
노드는 `Node` 의 모양(값 필드 + 번호 칸 1 = 왼쪽, 2 = 오른쪽, 균형 정보 한 칸).
정확성: 무작위 넣기·지우기·`Split`·다시 잇기 200회 × 200걸음을 정렬 모델과 대조하고 AVL 불변식(높이 차 ≤ 1)을 검사.

`bench.luau`(`-O2`, 최소값, 무작위 키):

| N | 넣기: `Join` 위(공유 구현) | 넣기: 직접 회전(손으로 짠 AVL) | 넣기: 정렬 배열(지금 `TreeMap`) | 조회: 노드 트리 | 조회: 정렬 배열 |
|---|---|---|---|---|---|
| 1만 | 18.1ms | 8.6ms | 18.8ms | 4.0ms | 7.5ms |
| 10만 | 349~371ms | 163~185ms | 1285~1292ms | 122~126ms | 206~215ms |

| N | 임의의 키에서 쪼개고 다시 잇기 한 쌍(노드 트리) | 정렬 배열을 두 조각으로 복사 |
|---|---|---|
| 1만 | 1.8μs | 22~25μs |
| 10만 | 1.9~2.0μs | 300~475μs |

- **떼어 내기는 됩니다**: `Split` 은 O(log n) 이고 결과 둘 다 온전한 균형 트리입니다(1만 개든 10만 개든 한 쌍에 약 2μs).
  정렬 배열은 복사라 크기에 비례합니다.
- **공유 구현의 값은 넣기에서 약 2배**(직접 회전 대비 2.0~2.2배)입니다. 그래도 10만 개에서는 지금의 정렬 배열보다
  3.5배 빠르고, 1만 개에서는 같습니다. 느린 것이 걸리면 균형 방식이 `Insert` 를 직접 회전으로 **재정의**하면 됩니다
  (리스트에서 `Arr` 가 기본 구현을 재정의하는 것과 같은 길).
- ⚠️ **조회 숫자는 30절과 어긋납니다** — 30절은 "조회는 지금 구현(정렬 배열)이 노드 트리의 절반" 이었는데 여기서는
  노드 트리가 0.55배입니다. 이 시제품의 조회는 맨 루프이고 `TreeMap.Get` 은 키 검사·`BSearch` 호출·레코드 접근을
  거칩니다 — 같은 조건이 아닙니다. 노드 기반 `TreeMap` 을 들일 때 **같은 표면(키 검사 포함)으로 다시** 재야 합니다.
- 함정 하나(벤치): 같은 키로 쪼개고 잇기를 되풀이하면 그 노드가 뿌리가 돼 다음 쪼개기가 O(1) 이 됩니다(처음엔 0.1μs 로
  나왔음) — 기준 키를 매번 바꿔 쟀습니다.

- **함수를 거치면 해시 필드보다 느립니다** — 읽기 하나에 2.5배(+8ns), 노드를 함수로만 따라가면 2.1배.
- 번호 칸의 이득은 **만들기와 메모리**(트리 노드 0.44배 / 0.64배 — 38절)와 라이브러리 **안쪽**의 직접 인덱싱(0.9배)에
  있고, 밖에서 함수로 읽는 길은 손해입니다.
- 그래서 저울은 "밖에서 노드의 값을 직접 읽는 일이 얼마나 잦은가" 입니다. 지금 표면에서는 드뭅니다: `TreeMap`·
  `TreeSet` 은 노드를 밖에 내주지 않고(`Get`·`Iter` 가 값을 줌), `LinkedDeque.Iter` 는 `(노드, 값)` 을 같이 주며,
  위치는 주로 컨테이너의 함수에 되돌려 넘깁니다(`Remove(d, node)` — 지금도 함수 호출).

## 39. 트레이트 조회를 배열 접근으로 — 숫자 토큰, 함수 번호 (2026-10-13, 사용자 제안을 재 봄)

제안: ① 타입 토큰을 숫자로(`impls[숫자]` — 배열 칸), ② 트레이트의 함수를 번호로(`impl[번호]`). 진입점의 실제 모양
(`impls[rawget(value, "__type")]` 로 구현을 찾고 그 함수를 부름)으로 쟀습니다. `bench-ignoreme/trait-array.luau`
(`-O2`, 21회 최소, 500만 번, 종류 20개가 등록된 표, 함수 몸통은 빈 것):

| 진입점 호출 하나 | ns |
|---|---|
| 지금 — 테이블 토큰(약한 키 해시) + 이름 필드 | 28.8~30.8 |
| ① 숫자 토큰 + 이름 필드 | 25.8~26.0 |
| ① + ② 숫자 토큰 + 함수 번호 | 25.4~25.5 |
| (참고) ① + ② 에서 `type()` 검사를 뺌 / `rawget` 대신 `value.__type` | 22.4 / 21.3 |

| 조회만 | ns |
|---|---|
| `impls[테이블 토큰]`(`rawget` 포함) | 14.8 |
| `impls[숫자 토큰]`(`rawget` 포함) | 9.1 |
| `impl.IndexOf`(문자열 상수 필드) | 3.9 |
| `impl[1]`(번호) | 3.5 |

- **① 숫자 토큰은 진입점 하나에 3~5ns(10~15%)**를 줄입니다. 표에서 구현을 찾는 조회가 14.8 → 9.1ns.
- **② 함수 번호는 0.4ns** — 사실상 차이가 없습니다. Luau 는 상수 문자열 필드 접근(`impl.IndexOf`)을 인라인 캐시로
  처리해 이미 배열 접근과 같은 값입니다.
- 진입점 비용의 대부분(20ns 남짓)은 조회가 아니라 **표에서 꺼낸 함수를 부르는 간접 호출**과 진입점 함수 자체의
  호출입니다 — 둘 다 이 최적화로 줄지 않습니다.
- ①의 대가(아직 안 넣음 — 판단 재료): 토큰이 숫자면 값의 `__type` 이 직렬화했다 되읽어도 같은 값이라 "우연한
  충돌은 없다" 가 사라지고, 버린 사용자 종류의 등록이 수거되지 않으며(약한 키를 못 씀), 에러 메시지에 쓸 이름을
  번호 → 이름 표로 따로 들어야 하고, 사본이 둘이면 번호가 겹쳐 서로의 값을 **자기 종류로 잘못 읽습니다**(지금은
  서로 모르는 종류로 봄).

## 40. 트리 순회자 — 부모 칸 따라가기 대 스택 대 재귀, 층별 순회의 큐 (2026-10-13)

`Trees/Traverse` 를 넣으며 쟀습니다. `bench-ignoreme/traverse.luau`(`-O2`, 7회 최소, 레드블랙 트리 10만 노드, 키는
흩어진 순서로 넣음 — 노드가 메모리에 흩어져 있어 **캐시 실패가 지배적이고 실행마다 ±30% 흔들립니다**. 아래는 여러 번
돌린 범위).

| 10만 노드를 한 번 돎 | ms |
|---|---|
| `Traverse.PreOrder`(부모 칸을 따라감 — 스택 없음) | 14.2~22.8 |
| 전위 — 명시적 스택을 든 순회자 | 15.8~22.2 |
| 전위 — 재귀 + 콜백(순회자 아님) | 14.3~22.2 |
| `Traverse.InOrder` | 16.0~20.8 |
| `Search.Next` 를 손으로 따라감(순회자 없이) | 11.3~12.7 |
| `Traverse.PostOrder` | 11.1~16.6 |

| 층별 순회의 구현 | ms |
|---|---|
| 큐 하나 + 지나간 칸을 `nil` 로 비움(처음 쓴 것) | 36.7~40.2 |
| 큐 하나, 안 비움(순회자가 노드 전부를 붙잡음) | 17.2~22.1 |
| **층 두 개를 번갈아**(넣은 것 — 메모리는 가장 넓은 층만큼) | 21.5~25.3 |

- **부모 칸을 따라가는 순회는 스택을 든 순회와 같은 값**입니다(흔들림 안). 그래서 추가 메모리가 없는 쪽을 넣었습니다.
  재귀 + 콜백도 같은 범위 — 순회자(`for … in`)라서 느려지는 것은 재지 못했습니다.
- 중위는 순회자를 거치면 손으로 `Next` 를 따라가는 것의 1.3~1.6배입니다(걸음마다 클로저 호출 하나). 뜨거운 루프면
  `Search.First` / `Search.Next` 를 직접 쓰세요.
- ⚠️ **앞에서부터 `nil` 로 비워 가는 배열 큐는 느립니다**(1.7배): Luau 는 배열이 늘어날 때 채워진 비율을 보고 배열
  부분의 크기를 정하는데, 앞이 비어 있으면 칸들이 해시 부분으로 옮겨집니다. 큐가 필요하면 **머리 번호만 올리고
  비우지 않거나**(끝나면 통째로 버림), 여기처럼 **배열 둘을 번갈아** 쓰세요. `CircularDeque` 가 링 버퍼인 이유와 같은
  뿌리입니다.

## 41. `Heap` 의 올리기·내리기를 `Trees/CompleteArray` 로 뺌 — 비용 차이 없음 (2026-10-13)

`Heap` 안의 지역 함수 `siftUp`·`siftDown` 을 2층 조각(`Trees/CompleteArray.SiftUp`·`SiftDown`·`Heapify`)으로 옮기고
`Heap` 은 그것을 **지역으로 받아** 부르게 했습니다(`const siftUp, siftDown, heapify = CompleteArray.SiftUp, …`).
`bench-ignoreme/heap-complete.luau`(`-O2`, 최소값, N = 20만, 같은 파일을 옮기기 전·후에 세 번씩):

| | 옮기기 전 (ms) | 옮긴 뒤 (ms) |
|---|---|---|
| `Push` × N | 18.3~19.8 | 17.7~18.4 |
| `Clone` + `Pop` × N | 152.8~155.3 | 146.6~152.1 |
| `FromList(N)` | 11.4~11.9 | 11.4~11.7 |
| `Sorted(N)` | 143.7~148.7 | 143.4~149.0 |
| `PushPop` × N (힙 100개) | 5.9~7.4 | 5.8~6.0 |

차이는 흔들림 안입니다. 올리기·내리기는 루프가 있어 예전에도 인라인되지 않던 함수라, 같은 파일의 지역 함수든 다른
모듈에서 받아 온 지역 값이든 호출 하나입니다. **모듈의 함수를 조립해 쓸 땐 지역으로 받아 두세요** — `CompleteArray.SiftUp(…)`
처럼 부를 때마다 테이블에서 꺼내는 모양은 재지 않았습니다(노드 도구에서는 그 차이가 컸음 — perf 38-2절).

## 42. `LinkedDeque` 의 위치 연산을 `Node.Double` 도구로 바꾸면 — 넣기가 1.13~1.24배, 그대로 둠 (2026-10-13)

`LinkedDeque.InsertAfter`·`Remove` 는 노드의 칸을 직접 고칩니다. 1층 도구(`Node.Double.InsertNext`·`Unlink`)를 불러
같은 일을 하게 짠 판과 견줬습니다(검사·크기·머리·꼬리 갱신까지 같게). `bench-ignoreme/linked-position.luau`
(`-O2`, 15회 최소, 20만 번, 세 번 돌린 범위):

| | 지금(칸을 직접) | 도구를 불러서 |
|---|---|---|
| 가운데에 넣고 바로 뺌 (한 쌍) | 117.6~123.0 ns | 115.1~122.0 ns |
| 맨 뒤 노드 뒤에 계속 잇기 (하나) | 68.0~68.8 ns | 77.3~84.8 ns |

- 넣고 빼는 쌍은 같습니다(흔들림 안). **넣기만 하면 도구 판이 1.13~1.24배** 느립니다 — 호출 하나가 더 붙고, 노드를
  빈 연결로 만든 뒤 도구가 칸을 다시 씁니다(직접 판은 `{ item, at, after }` 로 한 번에 만듦 — perf 34절과 같은 뿌리).
- 그래서 **`LinkedDeque` 는 칸을 직접 고치는 지금 구현을 둡니다**(컨테이너의 뜨거운 길). `Node.Double` 의 도구는
  자기 구조를 조립하는 쪽을 위한 것입니다. 둘은 **따로** 테스트됩니다(덱은 `spec.linkeddeque`, 도구는 `spec.trees` 5절) —
  서로를 직접 대조하는 테스트는 없습니다.

## 43. 완전 이진 트리의 노드식 대 배열식 — 힙으로 썼을 때 (2026-10-13)

`Trees/CompleteNode`(노드를 다시 이어 순서를 맞춤)로 짠 힙과 배열식 `Heap` 을 견줬습니다.
`bench-ignoreme/complete-node.luau`(`-O2`, 9회 최소, N = 10만, 두 번 돌린 범위):

| | 배열식 `Heap` | 노드식 | 배 |
|---|---|---|---|
| 넣기 N | 9.2~9.5 ms (92~95 ns) | 56.8~61.9 ms (567~619 ns) | 6.2~6.5 |
| 넣기 N + 꺼내기 N | 76.6~77.6 ms | 363.0~369.1 ms | 4.7~4.8 |

- 노드식은 넣을 때 노드 테이블을 하나 만들고, 맨 뒤 자리를 뿌리에서 비트를 따라 찾고(O(log n)), 올릴 때 걸음마다
  연결을 열 군데쯤 고칩니다. 배열식은 "구멍" 을 밀어 올리며 걸음마다 쓰기 하나입니다.
- 그래서 **양끝만 쓰는 힙은 배열식**입니다. 노드식의 값은 속도가 아니라 **위치를 쥘 수 있다는 것**입니다 — 가운데
  원소의 우선순위를 고치거나 빼는 일이 O(log n)(배열식은 그 원소를 찾는 데 O(n)).
- 값을 맞바꾸는 판(연결은 그대로, 값 칸만 교환)은 더 빠를 것이지만 재지 않았습니다 — 쥐고 있던 노드가 다른 값을
  가리키게 되어 노드식을 둘 이유가 사라집니다.

## 44. 트레이트의 함수를 번호로 — 구현 표가 번갈아 바뀌는 자리에서 다시 잼 (2026-10-13, 사용자 요청)

39절은 "함수 번호는 0.4ns — 차이 없음" 이었는데, 그건 **한 호출 자리가 표 하나만 보는** 경우였습니다. 사용자:
*"해시 슬롯 겹치는게 생길때에도 괜찮은지 한번 테스트 해보고싶긴 하네."* Luau 는 `t.Name` 을 "지난번에 그 키가 있던
칸" 을 그 명령어에 기억해 두고 바로 읽습니다(인라인 캐시). 진입점(`List.IndexOf(v, x)`)은 한 자리에서 `Arr` 의 표도
덱의 표도 보니, 표마다 그 키의 칸이 다르면 기억이 빗나가 해시를 다시 찾습니다.
`bench-ignoreme/trait-fn-number.luau`(`-O2`, 11회 최소, 200만 바퀴 × 접근 12, 두 번 돌린 범위. 표는 이름 열둘 +
번호 1..12 를 같이 들고, "큼" 은 다른 키 150개를 먼저 넣은 것 — 모듈을 통째로 등록한 표):

| 꺼내기만(부르지 않음), 접근 하나 | 이름 `t.Name` | 번호 `t[i]` |
|---|---|---|
| 표 하나, 작음 | 5.1~5.2 ns | 4.7~4.8 ns |
| 표 하나, 큼(키 162 — 칸이 겹침) | 5.1~5.2 | 4.6~4.7 |
| 표 둘을 번갈아(작음·큼) | **6.5~6.6** | 4.6 |
| 표 넷을 번갈아(크기 0·7·40·150) | **6.6~6.7** | 4.6~4.7 |
| 표 넷을 번갈아(전부 큼) | **6.4~6.7** | 4.6 |

| 꺼내서 부름(빈 함수), 접근 하나 | 이름 | 번호 |
|---|---|---|
| 표 하나(작음 / 큼) | 17.0~17.3 | 16.4~16.8 |
| 표 둘·넷을 번갈아 | 17.1~18.0 | 16.7~16.9 |

- **표가 하나면 칸이 겹쳐도 차이가 없습니다**(0.4ns) — 빗나간 뒤 한 번 찾으면 그 칸을 기억합니다. 표의 크기도 무관.
- ⭐ **한 자리가 여러 표를 번갈아 보면 이름 조회가 1.9~2.0ns 더 듭니다**(6.5 대 4.6 — 조회만 놓고 보면 1.4배). 번호는
  표가 바뀌어도 그대로입니다. 사용자의 짐작이 맞았습니다.
- 다만 진입점 하나의 비용(약 28ns — 39절) 가운데 2ns(약 7%)입니다. 숫자 토큰(39절의 3~5ns)과 합치면 5~7ns(20% 안팎).
- 같은 종류만 넘기는 뜨거운 루프에서는 빗나감이 없어 이득이 0.4ns 입니다. 종류가 섞이는 자리(여러 컨테이너를 한
  함수로 다루는 공용 코드)에서만 2ns 가 나옵니다.
- 넣는다면: 트레이트가 함수 이름 → 번호 표를 들고, 완성 표의 **배열 부분**에 같은 함수를 번호로도 넣습니다(이 측정의
  표가 그 모양 — 이름과 번호를 한 표에). 진입점은 `impl[번호]` 로, 바깥은 지금처럼 이름으로. 재정의(저절로 따라온 표
  위의 등록)는 두 자리를 같이 고쳐야 합니다.

## 45. 트리 노드에 부분 크기 칸을 두면 — 시제품 (2026-10-13, 사용자 요청)

부분을 떼어 낸 트리의 크기를 O(log n) 에 알려면(그리고 순위로 조회하려면) 노드가 "내 부분 트리의 노드 수" 를 들어야
합니다. 사용자: *"놓아야할 플레이스로 내려가면서 +씩 추가해주는식이 가능하긴 해보이는데. 그게 성능면에서 이로울지
모르겠음 … 시제품과 테스트가 있어야 결정 가능"*. 지금의 `Trees/RedBlack` 에 일곱째 칸을 더한 시제품 둘을 만들었습니다
(`.claude/research/tree-size/` — 크기 칸이 늘 맞는지 무작위 2만 4천 걸음으로 검증, `check.luau`):
**아래에서 위로**(새 노드를 단 뒤 조상을 뿌리까지 +1) / **내려가면서**(지나는 노드마다 +1, 있던 키면 거슬러 올라가 −1).
회전은 두 노드의 크기만 다시 셈, 지우기는 빠진 자리의 조상을 뿌리까지 −1.
`bench.luau`(`-O2`, 9~11회 최소, N = 10만, 세 번 돌린 범위 — 지금 판 대비 배수):

| | 아래에서 위로 | 내려가면서 |
|---|---|---|
| 넣기 N (흩어진 키) | 1.11~1.27 | 1.09~1.20 |
| 넣기 N (오름차순) | 1.20~1.30 | 1.11~1.24 |
| 있던 키 덮어쓰기 N | 1.02~1.04 | **1.47~1.56** |
| 지우기 N | **1.46~1.98** | 같은 코드 |
| 넣고 지우기 섞음 | 1.30~1.42 | 1.19~1.38 |
| 노드당 메모리 | 144 → 160 바이트 (1.11) | 같음 |

- 넣기는 1.1~1.3배, **지우기는 1.5~2배**(뿌리까지 한 번 더 걸음), 메모리는 노드당 16바이트.
- 내려가면서 올리는 판은 새 키에서 조금 낫지만(따로 올라가는 걸음이 없음) **있던 키를 덮어쓸 때 1.5배**입니다 —
  내려가기 전에는 새 키인지 모르니 되돌려야 합니다. 맵은 덮어쓰기가 흔합니다. 넣는다면 아래에서 위로.
- ⭐ **권장: 기본 노드에는 크기 칸을 두지 않습니다.** 넣고 빼는 모든 호출이 값을 치르는데, 크기 칸이 필요한 것은
  떼어 내기와 순위 조회뿐입니다. 대신:
  - **떼어 낸 두 트리의 크기는 "두 쪽을 번갈아 한 걸음씩 세다가 먼저 끝나는 쪽" 으로** — 작은 쪽의 크기를 알면 큰 쪽은
    전체에서 뺍니다. 떼어 내기가 O(log n + 작은 쪽의 크기) 가 되고, 넣기·지우기·`Len` 은 지금 그대로입니다
    (`Len` 을 "불러야 세는" 것으로 바꾸면 `Set` 마다 크기를 아는지 봐야 해서 뜨거운 길에 검사가 붙습니다).
  - 순위로 조회해야 하는 것(자동 정렬 래퍼의 "i 번째")은 **크기 칸을 든 균형 방식을 따로**(같은 계약 `Balance.Scheme`,
    `TreeMap.New(compare, 그_방식)`) — 필요한 쪽만 값을 치릅니다.

## 46. 정렬 배열 + 이분 탐색 대 완전 이진 트리 배치의 탐색 배열 (2026-10-13, 사용자 질문)

사용자: *"FlatMap 있잖아. 완전이진트리 모듈화 된거로 구현하지 않은 이유가 있어?"* `FlatMap` 은 **키 순서로 놓은 배열**을
`Algorithms/BSearch`(가운데를 짚는 이분 탐색)로 찾습니다. `Trees/CompleteArray` 의 배치(자식이 `2i`·`2i+1`)와는 다른
배열입니다 — 같은 원소를 **완전 이진 트리의 번호 배치에 탐색 트리 순서로** 담으면(Eytzinger 배치) `CompleteArray` 의
자리 계산을 그대로 쓰는 "배열에 담은 탐색 트리" 가 됩니다. 그 둘을 쟀습니다.
`bench-ignoreme/eytzinger.luau`(`-O2`, 9회 최소, 숫자 키, 찾기 100만 번):

| | 정렬 배열(`FlatMap` 의 모양) | 완전 이진 배치 | 배 |
|---|---|---|---|
| 찾기 하나, N = 1천 | 167.9 ns | 127.3 ns | 0.76 |
| 찾기 하나, N = 10만 | 400.1 ns | 277.7 ns | 0.69 |
| 찾기 하나, N = 100만 | 616.5 ns | 392.7 ns | 0.64 |
| 순서대로 돎, 원소 하나 | 5.2~5.4 ns | 24.2~31.7 ns | 4.6~6.0 |

- **찾기는 완전 이진 배치가 0.64~0.76배**(빠름) — 걸음마다 `lo`·`hi`·가운데를 셈하지 않고 번호 하나만 두 배로
  하며, 위쪽 층이 배열 앞에 모여 있습니다. 클수록 벌어집니다.
- **순서대로 돌기는 4.6~6배 느립니다** — 정렬 배열은 `1..n` 을 그냥 걷고(구간도 연속이라 `table.move` 로 떠냄),
  완전 이진 배치는 번호를 오르내려야 합니다.
- 넣기: 정렬 배열은 뒤를 한 칸 미는 것(`table.move` — C 안에서)이고, 완전 이진 배치는 원소 하나를 넣어도 배치가
  통째로 바뀝니다(다시 지음, O(n) 을 Luau 로).
- 그래서 `FlatMap` 을 완전 이진 배치로 **바꾸면** 그것을 고르는 이유(`Keys`·순회·구간이 빠름, 끼워 넣기가 블록
  이동 — perf 37절)가 사라집니다. 다만 **한 번 지어 찾기만 하는 표**(게임의 정적 데이터)에는 완전 이진 배치가
  낫습니다 — 넣는다면 `FlatMap` 을 대체하는 것이 아니라 세 번째 판(찾기 전용, `Trees/CompleteArray` 의 자리 계산 위에
  찾기 도구를 더함)입니다. 아직 넣지 않았습니다(사용자 판단 대기).

## 47. `FlatMap` 의 넣기·빼기를 `Trees/SortedArray` 로 뺌 — 구조 연산마다 호출 하나 (2026-10-14)

사용자: *"insert 넣은 구현 자체가 그쪽(컬렉션)이 자리가 아닌것 같음. 노드 연산이 컬랙션에 정의인게 걸린점"*. `FlatMap` 안에
있던 배열 밀고 당기기를 2층 `Trees/SortedArray`(`InsertAt`·`RemoveAt`)로 옮겼습니다. `Heap` 때(41절)와 달리 여기는
**옮기기 전에 그 코드가 함수 안에 그대로 풀려 있어서**, 옮기면 호출이 하나 생깁니다.
`bench-ignoreme/flatmap-structure.luau`(`-O2`, 15회 최소, 두세 번 돌린 범위, 연산 하나당 ns):

| | 옮기기 전 | 찾기까지 도구로(`Locate`) | 찾기는 직접, 구조만 도구로(넣은 것) |
|---|---|---|---|
| `Set` 새 키, 맵 ~16 | 234~240 | 252~259 (+7%) | 245~250 (+4%) |
| `Set` 새 키, 맵 ~256 | 428~435 | 460~471 (+7%) | 440~460 (+3~5%) |
| `Set` 새 키, 맵 ~4096 | 1081~1098 | 1098~1108 | 1095~1135 (흔들림 안) |
| `Set` 있던 키, 맵 ~16 | 206 | 209~220 | 204~216 (같음) |
| `Remove` 뒤 `Set`, 맵 ~16 | 513~527 | 543~546 | 531~558 (+4%) |
| `PopFirst` 뒤 `Set`, 맵 ~16 | 315~320 | 343~353 | 334~345 (+6~7% — 도구를 두 번 부름) |

- 구조 연산 하나에 **호출 하나(10~15ns)** 가 붙습니다. 작은 맵에서 3~7%, 맵이 크면(밀기가 지배) 묻힙니다. 조회와
  덮어쓰기는 구조를 안 고치니 그대로.
- 찾기까지 2층 도구(`Locate` = `LowerBound` + 같은지 확인)로 감싸면 한 겹이 더 붙어 7% — 그래서 `FlatMap` 은 찾기를
  예전처럼 `BSearch` 로 바로 하고 **밀고 당기기만** 도구를 부릅니다. `Locate` 는 바깥에서 조립하는 쪽을 위해 둡니다.
- 층을 지키는 값입니다(사용자 방향). 되돌리려면 `FlatMap` 의 네 자리를 다시 풀어 쓰면 됩니다.
