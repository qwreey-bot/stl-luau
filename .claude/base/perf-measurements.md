# 성능 실측

이 저장소는 *"최적화 주장은 실측으로 뒷받침한다"* 를 규칙으로 둡니다
(`.claude/conventions.md`). 그래서 잰 것을 전부 여기 모읍니다.

**재는 방법**: 래퍼 클로저를 끼지 말고 루프에서 직접 호출할 것. 여러 번 재고
**최소값**을 쓸 것(노이즈 회피). 환경은 `luau 0.734`, 2026-09-22.

---

## 1. ⭐ 메타테이블이 붙어 있으면 인덱싱이 1.59배 느리다

원소 200만 개를 `for i = 1, t.n do acc += t[i] end` 로 더한 시간:

| 테이블 | 시간 | 배수 |
|---|---|---|
| 메타테이블 없음 | 0.0086s | **1.00x** |
| 빈 메타테이블 `{}` | 0.0136s | **1.59x** |
| `__index` 있는 메타테이블 | 0.0136s | 1.59x |
| `table.freeze` 한 메타테이블 | 0.0136s | 1.59x |
| `rawget(t, i)` 로 우회 시도 | 0.0136s | 1.59x |

**원인은 `__index` 가 아니라 메타테이블의 존재 자체입니다** — 빈 메타테이블도
똑같이 느려지고, `rawget` 로도 못 피합니다(C 함수 호출 비용이 그만큼).

### 그런데 메타테이블을 버릴 수는 없다

메소드를 인스턴스마다 복사하면 인덱싱은 빨라지지만:

| | 메타테이블 부착 | 메소드 54개 복사 |
|---|---|---|
| 작은 배열 20만 개 생성 | 0.0137s | 0.2791s (**20.4배**) |
| 인스턴스당 메모리 | 96바이트 | 2112바이트 (**22배**) |

컨테이너 라이브러리는 작은 인스턴스를 많이 만듭니다. **메타테이블을 씁니다.**
1.59배는 치르는 값이고, 아래 2번이 그걸 되갚는 방법입니다.

## 2. ⭐ `table.move` 는 메타테이블의 영향을 전혀 받지 않는다

원소 100만 개 복사:

| 방법 | 시간 | 배수 |
|---|---|---|
| `table.move` (메타테이블 유무 무관) | 0.0005~0.0008s | **1.00x** |
| 손 루프 `for i = 1, n do b[i] = a[i] end`, 메타테이블 없음 | 0.0059s | 7.6배 |
| 손 루프, **메타테이블 있음** | 0.0111s | **14.3배** |

`table.move` 는 C 안에서 돌며 메타테이블을 보지 않습니다. 그래서 1번의 1.59배
세금을 아예 안 냅니다.

**그래서 이 저장소가 `table.move`/`table.create` 를 고집하는 것이 취향이 아니라
14배짜리 결정입니다.** 벌크로 할 수 있는 일을 원소 루프로 쓰지 마세요.

## 3. 순회 — `ipairs` 가 가장 빠르다 (조건부)

원소 200만 개, 메타테이블이 붙은 실제 컨테이너 모양 기준:

| 방법 | 시간 | 배수 | 루프 변수 타입 | 구멍 |
|---|---|---|---|---|
| `for _, v in ipairs(arr)` | 0.0063s | **0.39x** | ✅ | ⚠️ 첫 구멍에서 멈춤 |
| **`for i = 1, arr.n do … arr[i]`** | 0.0163s | **1.00x (기준)** | ✅ | ✅ `n` 을 지킴 |
| `for _, v in arr:Iter()` | 0.0472s | 2.89x | ✅ | ✅ |
| `for _, v in arr` (`__iter`) | 0.0468s | 2.86x | ❌ **죽음** | ✅ |
| `arr:Fold(init, fn)` 콜백 | — | 2.54x | ✅ | ✅ |

**`ipairs` 의 조건**: `#` 기준으로 돌며 **첫 `nil` 에서 멈춥니다.** 이 저장소의
컨테이너는 `n` 을 진실로 삼고 구멍을 허용하므로, **라이브러리 내부에서는 쓸 수
없습니다.** 배열이 조밀한 것을 아는 사용자에게만 권할 수 있습니다.

**라이브러리 내부의 기본은 `for i = 1, self.n`** 입니다.

## 4. ⭐ `arr:Iter()` 는 교집합에서도 타입이 산다 — `__iter` 는 필요 없다

교집합 타입은 `for-in` 루프 변수의 타입을 잃습니다(`spikes/35`). 그런데 그건
for-in 이 **컨테이너의 인덱서**를 볼 때의 이야기이고, **메소드가 이터레이터
삼중항을 돌려주면** for-in 은 그 함수의 반환 타입을 봅니다. 그래서 삽니다.

```lua
for i, v in arr:Iter() do … end   -- i: number, v: T  (교집합인데도 정확)
```

**단, 이터레이터 함수를 `(number, T)` 로 선언해야 합니다** — 끝에서 `nil` 을
돌려주지만 타입에는 드러내지 않습니다. 정직하게 `(number?, T?)` 로 선언하면
루프 변수가 옵셔널이 되어 산술에 바로 못 씁니다. **Luau 자신의 `ipairs` 도
같은 방식**입니다.

실측: `spikes/37-iter-method-vs-metamethod.luau` (기대 5건).

비용은 2.89배로 `__iter` 와 같습니다 — 타입을 잃지 않는 쪽이 무조건 낫습니다.

## 5. 정렬 비교자 — 3방향을 쓰면 1.82배

20만 개 정렬:

| 방법 | 시간 | 배수 |
|---|---|---|
| `table.sort(t)` — 비교자 없음 | 0.0151s | 0.22x |
| `table.sort(t, lt)` — 불리언 비교자 | 0.0678s | **1.00x (기준)** |
| 3방향 비교자를 래퍼로 감싸 넘김 | 0.1233s | **1.82x** |

`table.sort` 가 받는 것이 불리언이라 3방향은 비교마다 클로저가 한 겹 더 붙습니다.
그래서 **정렬의 기본 통화는 `LessThan`(불리언)** 이고, 3방향 `Comparator` 는
정렬된 구조에서의 탐색(이분 탐색·트리)용입니다 — 거기서는 "같다" 를 한 번에
알아야 해서 3방향이 오히려 절반입니다. 자세한 것은 `src/Common.luau` 상단.

## 9. ⭐ 정렬 병합은 해싱을 못 이긴다 (2026-09-22)

`TreeSet` 의 집합 연산은 양쪽 정렬 배열을 한 번씩 훑는 **O(n + m) 병합**이고
해시를 한 번도 계산하지 않습니다. 교과서대로라면 이겨야 합니다. 원소 10만
개(절반 겹침)로 쟀습니다:

| 연산 | HashSet | TreeSet | |
|---|---|---|---|
| `Union` | 0.0028s | 0.0163s | **5.9배 느림** |
| `Intersect` | 0.0043s | 0.0049s | 1.2배 |
| `Has` × 10만 | 0.0030s | 0.0696s | **23.4배 느림** |
| `FromList` | 0.0010s | 0.0495s | **50배 느림** |

**이유**: Luau 의 테이블 해싱은 **C 안에서** 돌고, 우리 병합은 **Lua 클로저로
비교자를 부릅니다.** 알고리즘 차수가 아니라 상수가 이깁니다. 1번·2번에서
본 것과 같은 이야기입니다 — *이 런타임에서는 C 로 내려가는 쪽이 거의 항상
이깁니다.*

`Intersect` 만 비슷한 것은 결과가 작아 양쪽 다 할당이 적기 때문입니다.
`Union` 의 격차에는 레코드 테이블을 원소마다 새로 만드는 비용이 섞여 있습니다.

**그래서 `TreeSet`/`TreeMap` 은 순서를 위한 것이지 속도를 위한 게 아닙니다.**
순서가 필요 없으면 해시 쪽이 모든 축에서 낫습니다.

### 정렬 컨테이너에 많이 담을 때는 벌크 생성자를 쓸 것

| 원소 2만 개 담기 | 시간 | |
|---|---|---|
| `Add` 를 2만 번 | 0.0959s | **7.5배** |
| `FromList` (정렬 후 한 번에) | 0.0129s | 1.00x |

삽입마다 뒤를 밀어 O(n^2) 이 됩니다. `TreeMap.FromRecords` 도 같은 이유로
한 번에 정렬해서 담습니다.

## 10. 힙 — 교과서의 O(n) 대 O(n log n) 이 실측에선 상수차다 (2026-09-22)

`Heap.FromList`(가운데부터 거꾸로 내려가며 만들기)와 `Push` 반복:

| N | FromList | Push 반복 | |
|---|---|---|---|
| 10,000 | 0.0005s | 0.0009s | 1.86배 |
| 100,000 | 0.0056s | 0.0095s | 1.68배 |
| 500,000 | 0.0271s | 0.0473s | 1.74배 |

차수로는 O(n) 대 O(n log n) 이라 N 이 커질수록 벌어져야 하는데 **1.7배
안팎으로 거의 일정합니다.** 무작위 입력에서는 `Push` 의 평균 밀어올림 깊이가
상수이기 때문입니다 — 새 원소는 거의 항상 아래쪽에 자리잡습니다.

**교훈**: 차수만 보고 "훨씬 빠를 것" 이라고 쓰지 말 것. 1.7배는 1.7배대로
값지지만, 그게 이유인 척하면 안 됩니다.

### 그 밖

| `PushPop` vs `Push` 후 `Pop` (20만 회) | **1.78배 쌈** |

## 11. checked / unchecked 로 가른 값 (2026-09-22)

`nil` 구멍 검사를 빼면 얼마나 빨라지는가. **실제 콜론 메소드 호출로** 쟀고
원소 20만/200만에서 같은 배수가 나왔습니다.

| 무엇 | checked | unchecked | |
|---|---|---|---|
| `Max` / `Min` | 0.0262s | 0.0143s | **1.83배** |
| `SortInplace` | 0.0179s | 0.0151s | 1.18배 |
| `Sum` / `Prod` | 0.0147s | 0.0136s | 1.08배 |

(`Max`/`Sum` 은 N=200만, `SortInplace` 는 N=20만)

**`Max`/`Min` 이 유독 큰 이유**: 검사 있는 판은 원소마다 `nil` 검사에 더해
*"아직 첫 값을 못 찾았는가"* (`best == nil`) 분기까지 봅니다. 검사를 빼면
첫 원소를 씨앗으로 잡고 2번부터 도는 단순한 루프가 됩니다.

**`Sum` 의 8%** 는 작지만 두 크기에서 똑같이 나왔습니다. 앞서 6절에서
평범한 테이블에 13% 로 쟀던 것과 방향이 같고, 메타테이블 세금(1번)이 섞여
상대 비중이 줄어든 것입니다.

### ⚠️ `SortUnchecked` 만 조용히 틀린다

| 무엇 | 구멍을 만나면 |
|---|---|
| `SumUnchecked` / `ProdUnchecked` | `nil` 산술로 **터짐** |
| `MaxUnchecked` / `MinUnchecked` | 비교에서 **터짐** |
| `SortUnchecked` / `SortInplaceUnchecked` | `table.sort` 가 `#` 를 보므로 **구멍 뒤쪽이 조용히 잘림** |

셋 중 마지막만 터지지 않습니다. 그래서 문서에서 그 줄을 특히 강조합니다.
(2026-10-02 꼬리표: **M0 6라운드 이후 사실 아님** — `#` ≠ `n` 이면 checked 판으로 넘어가고,
같으면 비교 에러로 터집니다. 무작위 2만 건에서 조용히 틀린 답 0. 위 표는 당시 기록.)

## 12. 구멍을 정리하고 unchecked 로 가는 것 — 한 번이면 손해 (2026-09-26)

원소 20만, 구멍 10%.

| 무엇 | 배수 (checked `Sum` = 1.00) |
|---|---|
| `FillHolesInplace` 만 | 1.02x |
| `FillHolesInplace` + `SumUnchecked` | **1.88x (더 느림)** |
| `FillHoles`(새 배열) 만 — 2026-09-30 | 1.45x |
| `FillHoles`(새 배열) + `SumUnchecked` — 2026-09-30 | 2.33x |
| `CompactInplace` + `SumUnchecked` | 2.41x |

| `ToOptionals` | 4.96x |

**정리 한 번이 checked 집계 한 번만큼 듭니다.** 그래서 손익은 횟수로
갈립니다 — 한 번 정리하고 `Max` 를 k 번:

| k | checked 대비 |
|---|---|
| 1 | 0.87x (손해) |
| 2 | 1.15x |
| 3 | 1.32x |

구멍을 치우는 비용까지 셈에 넣으면 **두 번째 연산부터** 이득입니다.

(2026-09-30) 이 표의 제자리 판은 그때 이름이 `FillHoles` 였고 지금은

하면서(`question.md` T, U) 들였고 `?` 를 떼는 정식 경로입니다 — 할당이 있어도
`Compact`(1.8~1.9x)보다 쌉니다. 같은 조건에서 다시 재니 제자리 판은
1.03~1.05x, `+ SumUnchecked` 는 1.91x 로 위 숫자와 맞았습니다.

`Optional.Present` 하나는 **128바이트**입니다.

## 13. `Fut` 한 번의 값 (2026-09-26)

10만 회 × 5회 중 최소.

| 무엇 | 1회당 |
|---|---|
| 평범한 함수 호출 | 0.012µs |
| `pcall` | 0.037µs |
| 코루틴 생성 + `resume` | 0.174µs |
| `Fut.Resolved(x)` | 0.150µs |
| `Fut.Resolved(x):AndThen(fn)` | **0.774µs** |

`AndThen` 은 콜백을 **새 코루틴에서** 돌립니다 — 그래야 콜백 안에서
`Await` 할 수 있습니다. 그 몫이 0.17µs 이고 나머지는 결과 팩·리스너 테이블
할당입니다. 비동기 연산은 컨테이너 연산보다 훨씬 드물게 일어나는 자리라
받아들였습니다. 핫 루프에서 `Fut` 을 만들지는 마세요.

**나중에 재볼 것**: 코루틴을 풀로 재사용하면 0.17µs 를 줄일 수 있습니다.
부르는 곳이 생겨 이게 병목으로 측정되면 그때.

### [2026-09-30] 정확성 수정 뒤 — 0.77µs → 1.05µs

리뷰가 재현한 버그 둘을 고치느라 즉시 스케줄러를 **트램펄린**(재진입 가드가
있는 드레인 루프)으로 바꾸고 **잡마다 `pcall` 로 격리**했습니다. 그 값이
`AndThen` 한 번에 약 **+0.35µs** 입니다(3회 반복, 이전 커밋과 같은 벤치로 대조).

| | `AndThen` 순수 비용 |
|---|---|
| 이전 (그냥 `job()`) | 0.60µs |
| 지금 (트램펄린 + 격리) | 0.95µs |

**받아들였습니다.** 이전 판은 사슬이 약 198단을 넘으면 "C stack overflow" 로
**거짓 실패**했고, 리스너 하나가 에러를 내면 **나머지가 영원히 대기**했습니다.

본문을 감싸는 클로저 할당을 없애는 판(큐에 "코루틴으로 띄울 본문" 표시를
따로 둠)도 재봤는데 **빨라지지 않아** 되돌렸습니다. 비용은 할당이 아니라 격리
`pcall` 과 큐를 도는 데서 옵니다.

## 14. 호출 모양 — 네임스페이스 함수가 콜론보다 빠르다 (2026-09-30)

같은 함수(`Len`)를 세 모양으로 500만 회:

| 모양 | 배수 |
|---|---|
| `a:Len()` (콜론 — 메타테이블 `__index` 경유) | 1.00x |
| `Arr.Len(a)` (네임스페이스 필드) | **0.82x** |
| `local Len = Arr.Len; Len(a)` (지역 변수) | **0.64x** |
| `a.n` (참고 — 필드를 바로) | 0.24x |

콜론 호출은 인스턴스에서 못 찾고 메타테이블 `__index` 로 한 번 더 가야
합니다. 네임스페이스는 평범한 테이블 필드 조회 한 번이고, `local` 로 받으면
그것도 없어집니다.

**사용자 방향(절차적 호출이 1급)과 성능이 같은 쪽을 가리킵니다.** 그래서
모든 컨테이너가 메소드를 네임스페이스 함수로도 노출합니다(`Arr.Map(a, fn)`).
뜨거운 루프에서는 `local Map = Arr.Map` 으로 받아 쓰세요 — 제네릭은 호출마다
새로 풀립니다(`spikes/49`).

### 15-3. 선택의 병적 입력 — 리뷰가 찾은 O(n²) 와 고친 뒤 (2026-09-30)

리뷰(opus)가 "정렬된 배열 끝에 최솟값 하나" 에서 `NthElement` 가 **n=16000 에
1.4초, 10만에 2분 넘게**라는 걸 재현했습니다. 중앙값 셋의 후보가 끝점(lo/hi)
이라 끝의 극단값이 매번 나쁜 피벗을 만들었습니다. 두 겹으로 고쳤습니다.

| 원소 10만, 기준 = `Arr.Sort(a, less)` | 끝점 후보 + 예산 폴백 | **1/4·1/2·3/4 후보** + 예산 폴백 |
|---|---|---|
| 무작위 | 0.18x | 0.18x |
| 정렬 + 끝에 최솟값 | 3.02x (폴백이 구함) | **0.12x** |
| 최댓값 + 정렬 | — | 0.12x |
| 오르내림(organ pipe) | — | 0.13x |
| 이미 정렬 / 역순 | 0.08x / — | 0.08x / 0.13x |

**예산 폴백**(분할이 약 2·log₂n 번을 넘으면 남은 구간을 `table.sort`)은 어떤
피벗 규칙이든 이기는 입력을 위한 보증입니다. McIlroy 의 적대적 비교자로 재면
n=4000 에서 **폴백 없이 300만 번(751n), 있으면 28만 번(70n)** 입니다 —
`spec.arr` 18절이 이 적대자로 폴백 경로를 지킵니다. 스캔 경계 검사(엄격하지
않은 비교자 방어)는 무작위 입력에서 측정 차이가 없었습니다(0.17x → 0.18x).

**남은 한계(2라운드 리뷰 실측)**: 주기가 n/4 인 톱니, 정렬된 구간 넷을 이어붙인
모양처럼 **1/4·1/2·3/4 후보가 같은 위상에 걸리는** 입력에서는 비교가 10~14n 이라
n=2만에서 `NthElementInplace` 4~5ms 대 비교자 없는 `Sort()` 1.3~1.5ms 입니다.
이차는 아니고(예산 폴백), 비교자를 주는 `Sort(lt)` 보다는 여전히 빠릅니다.
무작위 입력은 수정 전과 같습니다(2.43n 대 2.38n).

## 16. 메타테이블을 아예 없애면 — 호출 모양이 아니라 **인덱싱**이 갈린다 (2026-10-01)

## 17. `SortInplaceUnchecked` 의 `#` 검사 비용 (2026-10-01, M0 6라운드)
