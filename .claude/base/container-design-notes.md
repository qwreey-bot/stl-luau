## 1. ⭐ 인덱스 접근을 "리스트"의 필수 연산으로 두지 않는다

**세 언어가 전부 같은 결론에 도달했습니다.** 연결 리스트에서 `list[i]` 는
O(n) 인데, 인덱스 표기를 허용하면 사용자가 `for i = 1, n do list[i] end` 라고
써서 조용히 O(n²) 를 만듭니다. 표기가 비용을 속이는 것입니다.

| 언어 | 어떻게 막았나 | 강제 시점 |
|---|---|---|
| Java | `RandomAccess` 마커 인터페이스. 멤버가 하나도 없는 빈 인터페이스이고, 범용 알고리즘이 이걸 검사해 인덱스 루프와 반복자 루프를 갈라 씁니다. 배열 기반만 구현하고 연결 기반은 구현하지 않습니다. | 런타임 |
| Rust | 연결 리스트에 인덱스 연산(`Index` trait)을 **아예 구현하지 않습니다.** 대신 전용 커서 타입을 주고, 커서는 한 칸씩 앞뒤 이동만 됩니다. | 컴파일타임 |
| C++ | `std::list` 에는 `operator[]` 도 `at()` 도 **없습니다.** 대신 조회기에 능력 등급 태그를 달고, 범용 알고리즘이 그 태그로 자기를 분기합니다(임의 이동이 되면 포인터 산술, 아니면 한 칸씩 루프). | 컴파일타임 |

셋의 공통 원칙: **"느린 연산을 저렴해 보이는 표기로 감추지 않는다."**
그리고 인터페이스를 작게 유지하고, 파생 연산은 최소 원시 연산 위에 **한 번만**
얹습니다 — Java 는 `get(i)` 와 반복자를 서로의 구현 기반으로 교환하고, Rust 는
`next()` 하나 위에 수십 개 어댑터를 디폴트로 얹고, C++ 은 `++` 반복만으로
임의 이동을 흉내 냅니다.

## 2. ⭐⭐ 더 나은 네 번째 답 — 위치 타입 자체를 제네릭으로

세 언어의 해법은 전부 "인덱스를 줄지 말지"의 이분법입니다. 그런데 **위치를
가리키는 타입 자체를 타입 파라미터로 빼면** 이분법이 사라집니다.

```lua
export type ListCore<E, I> = {
	Get:        (self: ListCore<E, I>, idx: I) -> E?,
	FirstIndex: (self: ListCore<E, I>) -> I?,
	LastIndex:  (self: ListCore<E, I>) -> I?,
	NextIndex:  (self: ListCore<E, I>, idx: I) -> I?,
	PrevIndex:  (self: ListCore<E, I>, idx: I) -> I?,
}
```

| 구현 | 위치 타입 `I` |
|---|---|
| 배열 기반 | `number` |
| 연결 기반 | `Node<E>` — 노드 자체가 곧 위치 |

- 구현체는 **이 다섯 개만** 제공합니다.
- `IndexOf`/`Contains`/`Count` 같은 순회 알고리즘은 이 다섯 개만으로 쓰이므로
  소스에 **한 번만 존재하고** 두 구현이 공짜로 씁니다.
- **순회 방식이 양쪽에서 문자 그대로 같습니다** — 배열 쪽도 `i + 1` 이 아니라
  `NextIndex` 를 거칩니다. 그래서 알고리즘이 구현을 몰라도 됩니다.
- 배열 쪽만 "n번째 위치 얻기"를 O(1) 로 재정의하고, 나머지는 기본 구현을 씁니다.

**왜 이게 나은가**: 세 언어의 해법은 전부 "연결 리스트에서 `list[i]` 를 쓰면
안 된다"를 *별도 장치*(마커/트레이트 부재/태그)로 알립니다. 위치 타입을
제네릭으로 빼면 **그 실수가 애초에 표현 불가능**합니다 — 연결 리스트의 위치는
노드라서 `list:Get(3)` 이 타입 에러입니다. 장치가 필요 없습니다.

### Luau 실측 결과 — 완전히 성립

`.claude/audit/list-index-abstraction/` (스파이크, 기대 진단 7건). 규모 증상 0건.

음성 대조군 5종이 전부 검출됩니다. 특히 **배열의 위치와 연결의 위치를 섞어
쓰면 잡힙니다**(`arrayList:Get(linkedList:FirstIndex())` → 타입 에러).

### ⚠️ 그런데 타입이 공짜인 것과 **쓰는 게** 공짜인 것은 다르다

원 구현에서 이 추상화가 비용 0 이었던 이유는 템플릿이 `Index = 정수` 경로와
`Index = 노드 포인터` 경로를 **정적으로 분리된 기계어 두 벌로** 뽑아줬기
때문입니다. 같은 `for` 루프 소스가 정수 증가로도, 포인터 역참조로도
인스턴스화됩니다.

**Luau 의 제네릭은 런타임에 지워집니다.** 그래서 "다음 위치를 얻는 연산"을
실제로 경유해 순회하면 정적 디스패치가 **간접 호출**로 바뀝니다. 이건 이미
실측된 숫자와 맞물립니다 — 콜백 순회와 `__iter` 순회가 `for i = 1, arr.n`
직접 인덱싱 대비 **2.5~2.8배** 느렸습니다
(`.claude/audit/arr-type-redesign/REPORT.md`).

**그래서 갈라 씁니다**:

- 위치 타입 파라미터는 **계약에만** 둡니다. 타입 수준 비용은 0 이고(실측),
  배열 위치와 연결 위치를 섞는 실수를 잡아주는 이득은 그대로 남습니다.
- **`Arr` 자신의 메소드는 프로토콜을 경유하지 않고 직접 인덱싱으로**
  구현합니다. 뜨거운 경로에 간접 호출을 넣지 않습니다.
- 프로토콜 경유 순회는 **두 번째 구현체가 실제로 생겼을 때**의 공용
  알고리즘에만 씁니다. 지금은 구현체가 `Arr` 하나뿐이라 공유의 이득 자체가
  검증되지 않습니다.

### 같이 따라오는 규약 — 위치를 저장하면 안 된다

이 설계의 원 구현이 남긴 규약: **사용자가 위치 값을 보관하는 것은 정의되지
않은 동작입니다.** 컨테이너가 바뀌면 배열의 인덱스는 밀리고 연결의 노드는
사라질 수 있는데, 그 차이가 구현마다 달라 공통 인터페이스가 보장할 수 없기
때문입니다. C++ 의 반복자 무효화 규약과 같은 이야기입니다.

**Luau 에서는 타입으로 못 막습니다.** 문서 규약으로 둘지, 세대 카운터로
런타임 검출할지 정해야 합니다. — **미결**

### 순회 중 삭제 — `RemoveThenNext`

같은 구현에 있던 프리미티브: 지우면서 위치를 다음으로 **갱신해 돌려줍니다.**
"순회 중 삭제" 라는 고전적 함정을 API 하나로 없앱니다. 지금 `Arr` 에는
대응물이 없고 `FilterInplace` 로 우회할 뿐입니다.

## 3. 조회기를 두 층으로 나눈다

세 언어 모두 **"for 루프용 단순 순회"** 와 **"위치를 들고 다니며 그 자리에서
변형하는 조회기"** 를 구분합니다.

- 단순 순회: 전진만, 값만 꺼냄. Luau 의 `__iter` 메타메소드와 제네릭 `for` 가
  정확히 이 자리입니다.
- 커서: 앞뒤 이동 + 현재 위치 조회 + 그 자리에 삽입/삭제/교체. Java 와 Rust 가
  각각 별도 타입으로 둡니다.

연결 리스트에서 커서가 결정적인 이유: `Get(i)` 를 반복하면 O(n²) 인데 커서로
누적 이동하면 O(n) 입니다.

**예전 과제에서도 같은 원칙이 독립적으로 나왔습니다** — 이진 탐색 트리에서
내부 노드는 변경 가능한 타입으로 두고 **바깥에는 읽기 전용 래퍼만** 내보내,
사용자가 트리 불변식을 깨지 못하게 했습니다. 그 근거도 적혀 있었습니다:
"인터페이스로 감춰도 구현을 알면 되돌려 캐스팅할 수 있으므로, 메모리를 더
쓰더라도 안전한 래퍼를 쓴다."

이건 `.claude/audit/arr-type-redesign/` 에서 찾은 **`ArrView<T>`** 와 같은
원리입니다 — 콜백에 전체 타입 대신 읽기 관점의 뷰를 주는 것. 서로 다른 이유
(저쪽은 불변식 보호, 이쪽은 타입 체이닝 유지)로 같은 모양에 도달했습니다.

## 4. Set 은 Map 의 특수화로 구현하되 상속하지 않는다

**[2026-09-22 사용자 확정 — 이대로 갑니다.]**

예전 과제에서 실제로 쓴 수단이 확인됐습니다. 해시 셋을 해시 맵으로부터
**private 상속**(밖에서는 보이지 않는 상속)으로 만들고, 주석이 의도를 직접
밝혀뒀습니다 — *"셋은 맵을 이용해 구현하지만 맵의 일종은 아니다."*
값 자리에는 필드가 하나도 없는 **빈 구조체**를 넣었습니다.

**얇다는 증거**: 셋의 모든 메소드가 한 줄짜리 위임 래퍼였고, 셋의 구현
파일은 **3줄**로 끝났습니다(두 헤더를 include 하는 접착 파일). 따로 구현할
것이 없었다는 뜻입니다.

```
has(key)  →  map.get(key) 가 값을 갖는가
add(key)  →  map.set(key, 빈값)
```

이름도 갈랐습니다: **셋은 `Add`/`Has`/`Remove`, 맵은 `Set`/`Get`.**

Luau 에는 private 상속이 없으니 **내부에 맵 인스턴스를 들고 얇은 래퍼만
노출**하면 같은 효과입니다. 코드 중복을 없애면서 API 표면은 완전히 분리됩니다.

### ⚠️ 이 선례가 증명하지 **않는** 것

그 과제에는 **합집합·교집합·차집합·부분집합이 아예 없었습니다.** 셋에 있던
연산은 `Add`/`Has`/`Remove`/`Count`/`Clear` 가 전부입니다. 그러니 이 선례는
"Set-on-Map 을 갔다"는 것까지만 증명하고, **"셋 전용 연산이 맵을 한 겹
거쳐도 괜찮았다"는 증명하지 못합니다** — 그 비용을 치를 코드가 존재한 적이
없습니다.

stl-luau 는 그 연산들을 만들 예정이므로, 합집합·교집합을 구현할 때가
**이 결정을 실측으로 다시 볼 지점**입니다. 두 셋의 원소를 순회하며 상대
셋에 `Has` 를 묻는 모양이 되는데, 그 `Has` 가 맵 래퍼를 한 겹 거칩니다.
느리면 그때 내부 맵의 테이블을 직접 읽는 특례 경로를 파면 됩니다 — 래퍼가
얇으니 그 특례도 얇습니다.

## 5. 예전 과제에서 가져갈 나머지

- **연산 이름을 ADT 별로 가른다**: 양 끝 추가/제거, 중간 삽입(밀어냄),
  덮어쓰기(길이 불변), 스택, 큐, 셋, 맵이 각각 다른 동사를 씁니다. 이미
  규칙표가 파일 상단 주석으로 정리돼 있었습니다.
- **용량 전략을 상수로 노출**: 최소 용량 / 증가율 / 축소 임계치를 이름 있는
  상수로 빼둡니다.
- **불변식을 파일 최상단에 선언**: 원형 큐에서 *"뒤 포인터는 반드시 빈 칸을
  가리킨다 → 따라서 앞뒤가 같으면 비어 있는 것으로 간주하고, 한 칸 남으면
  확장한다"* 처럼, "가득 참"과 "빔"이 같은 조건이 되는 고전적 버그를 미리
  문서화하고 피했습니다. 힙/덱을 만들기 전에 꼭 할 것.
- **순서 유지 삭제와 순서 무시 삭제를 이름으로 가른다** — 뒤 원소를 당기면
  O(n) 이고 마지막 것을 끌어오면 O(1) 인데, 둘은 다른 연산입니다.

## 6. 구간 규약 — 예전 구현이 실제로 쓴 것과, 그게 남긴 함정

같은 저자의 예전 문자열 구현은 구간을 **`(시작, 개수)`** 로 받고, 모든 구간
함수(`substr`/`insert`/`replace`/`erase`)가 **정규화 헬퍼 두 개를 공유**해서
규약이 파일 전체에서 일관됐습니다. 이 "정규화를 한 곳에 모은다" 는 습관은
그대로 가져갈 가치가 있습니다.

규칙은 이랬습니다:

- **음수 시작 = 끝에서부터**, 그래도 음수면 0 으로 클램프.
- **음수 개수 = 끝에서부터 몇 개를 남길 것인가** — `-1` 이면 끝까지,
  `-2` 면 마지막 하나를 빼고 끝까지. 파이썬 슬라이스의 음수 인덱스와 발상이
  비슷하지만 **인덱스가 아니라 개수 인자에 적용**된다는 점이 독특합니다.
- 끝 경계는 **배타(half-open)**.
- 범위를 벗어나도 예외를 던지지 않고 **조용히 클램프**.

### ⚠️ 거기서 실제로 생긴 버그 — "끝 바로 다음" 을 표현할 수 없었다

양수 시작이 범위를 넘으면 `length` 가 아니라 **`length - 1` 로 클램프**
됩니다. 그래서 "끝 바로 다음 위치" 가 표현 불가능하고, **`insert` 로 끝에
붙이는 것이 원리적으로 안 됩니다** — 마지막 글자 자리에 끼어듭니다.
실제 코드는 끝에 붙일 때 `insert` 대신 `append` 를 써서 이 함정을
우회하고 있었을 뿐, 고쳐진 적은 없습니다.

**교훈**: 삽입 위치의 유효 범위는 원소 위치의 범위보다 **하나 더 넓습니다**
(`1 .. n+1`). 이 둘을 같은 정규화 함수로 처리하면 반드시 이 버그가 납니다.
stl-luau 는 **조회용 클램프와 삽입용 클램프를 분리**해야 합니다.

### ⚠️ 실패 신호가 한 함수 안에서 갈렸다

탐색 함수가 "못 찾음" 에는 `-1` 을 돌려주는데, **시작 위치가 잘못되면
`length - 1`** 을 돌려줬습니다. 호출자가 반환값만 보고 찾았는지 판단할 수
없습니다. **한 함수는 실패 신호를 하나만 쓴다** — 반면교사로 기록합니다.

### stl-luau 의 선택은 달라야 한다

Lua 생태계는 `string.sub(s, i, j)` 가 **닫힌 구간** `[i, j]` 이고 **양쪽 다
음수 인덱스**를 허용합니다. 예전 구현의 `(시작, 개수)` + 배타 + "음수 개수"
를 그대로 가져오면 `string.sub`/`table.move` 와 어긋납니다. 가져올 것은
**규약이 아니라 "정규화를 한 곳에 모으고 모든 구간 함수가 공유한다" 는
구조**입니다.

## 7. 원소 타입이 비교에 참여하는 방식 — 주입이 맞았다

예전 과제는 **"차이 하나만 구현하면 비교 연산 여섯 개가 공짜로 나온다"**
는 믹스인을 썼습니다. 원소 클래스가 `diff(other) -> -1|0|1` 하나만 만들면
`<`, `<=`, `>`, `>=`, `==`, `!=` 가 전부 파생됩니다. stl-luau 의
`Comparator<T>` + `compareTo` 어댑터와 **같은 태도**입니다 — 비교자 하나만
넘기면 정렬·최대·최소가 전부 따라옵니다. 이 방향은 재확인됐습니다.

**그런데 그 구현의 경직성이 그대로 드러났습니다**: 비교가 기반 클래스에
고정돼 있어서, 파생 타입 다섯 개 중 **어느 것도 비교를 재정의하지 않았고**
파생 타입 고유 필드는 정렬·동등성에 **참여할 방법이 아예 없었습니다.**
기반 클래스의 두 필드만으로 영원히 정렬됩니다.

**그래서 stl-luau 가 비교자를 호출자에게서 주입받는 것이 옳습니다** — 같은
원소를 상황에 따라 다른 기준으로 정렬할 수 있어야 하고, 그건 타입에
비교를 박아넣는 설계로는 불가능합니다.

**대안과 그 대가**: Luau 에는 메타테이블 `__lt`/`__eq` 로 "원소 스스로
비교 가능" 하게 만드는 길도 있습니다. 채택하지 않습니다 —
(1) `__eq` 는 양쪽이 같은 메타테이블일 때만 불리는 제약이 있고,
(2) 사용자 타입에 메타메소드 구현을 **강제**하게 되어, "원소 타입에 아무
요구도 하지 않는다" 는 컨테이너 설계와 어긋나며,
(3) 위의 경직성 문제가 그대로 재발합니다.

## 8. 용량과 길이

- **성장은 최소 8 에서 시작해 2배씩**, 목표 길이를 넘을 때까지. 자동 축소는
  **없고** 축소는 명시적 호출로만 일어납니다. Luau 테이블은 자체 배열부가
  알아서 자라므로 수동 용량 관리는 필요 없지만, **크기를 미리 알면
  `table.create(n)` 으로 힌트를 준다**는 지금 관례는 같은 발상입니다.
- **길이는 명시 필드가 진실이고, 언어가 주는 길이 연산을 믿지 않습니다.**
  예전 문자열 구현도 길이를 별도 정수 필드로 들고, 널 종단 문자는 C API
  호환용 부가 정보로만 유지했습니다 — 주석이 *"내용에 널 문자가 없을 때만
  둘이 일치한다"* 고 못박아뒀습니다. stl-luau 의 *"`#` 대신 `self.n` 을
  신뢰한다"* 와 정확히 같은 교훈이고, 같은 저자가 두 번 같은 결론에
  도달했다는 교차 확인입니다.

### ⚠️ 이름이 대칭인데 비용이 비대칭이면 안 된다

예전 문자열 구현은 `append` 와 `prepend` 를 대칭 쌍으로 이름 붙였는데,
`append` 는 amortized O(1) 이고 `prepend` 는 **항상 전체를 민** O(n)
이었습니다. 이름만 보고는 알 수 없습니다.

stl-luau 는 *"API 가 편의를 위해 기본 경로를 느리게 만들지 않는다"* 를
이미 규칙으로 두고 있습니다(`conventions.md`). 여기에 **한 줄 덧붙입니다**:
이름이 짝처럼 생겼으면 비용도 짝이어야 하고, 아니라면 비용 차이가 문서에
드러나야 합니다. `PushBack`/`PushFront` 가 바로 이 자리입니다.

## 9. 어휘 — 선례가 있는 것과 없는 것

- **이미 쓰고 있고 선례와 일치**: `erase`, `replace`(위치+개수 기반).
  같은 저자가 두 프로젝트에서 같은 이름을 골랐다는 교차 확인입니다.
- **선례가 있는 미사용 후보**: `trim`, `leftPad`/`rightPad`, `prepend`,
  `reverse`, `shrinkToFit`, `isEmpty`.
- **선례가 없는 것**: **`split` 은 예전 구현에도 없습니다.** 분할 계열은
  참고할 선례 없이 처음부터 정해야 합니다 — `todos.md` 의 `rangefilter`/
  `rangefind`/`rangemap` 계열과 같은 처지입니다.

## 10. 최소 계약부터 — 안 쓴 것은 안 만든 것보다 나쁘다

예전 해시맵에는 *"키 순회·값 순회·열거를 구현할 것"* 이라는 TODO 가 끝까지
남아 있었고, **아무도 그걸 필요로 하지 않았습니다** — 리스트 쪽 순회
프로토콜이 이미 있어서 맵을 순회할 일이 없었기 때문입니다. 반대로
**`Count` 는 만들어 뒀는데 호출부가 단 한 곳도 없었습니다.**

같은 구현에 리해싱이 없어 **슬롯 수가 생성 시점 값으로 고정**돼 있었고
(호출부는 100 으로 하드코딩), 원소가 늘면 체인만 길어지는 함정을 그대로
안고 있었습니다. Luau 는 테이블 자체가 해시맵이라 이 계층이 아예 없지만,
*"성능 주장은 실측으로 뒷받침한다"* 는 원칙의 반면교사로 남깁니다.

**교훈**: 계약을 먼저 최소로 확정하고, 순회·집계는 **부르는 곳이 생겼을 때**
추가합니다. `.claude/arr-worklist.md` 의 54개도 같은 눈으로 한 번 더 볼
여지가 있습니다.

## 11. stl-luau 에 대한 함의 — 아직 결정 안 함

- `Map`/`Filter`/`Reduce` 처럼 순회만 있으면 되는 연산을 **`Arr` 전용 메소드에서
  떼어내 조회기 위의 공용 함수로** 올릴 수 있습니다. 그러면 나중에 연결
  리스트나 덱을 추가할 때 54개를 다시 구현하지 않고 다섯 개 프리미티브만
  주면 됩니다.
  **⚠️ 다만 이건 타입 실측을 다시 해야 합니다** —
  `.claude/audit/arr-type-redesign/` 의 제약(`Map` 반환이 `Arr<G>` 여야 하고,

  그대로인지 **아직 안 쟀습니다.**
- 인덱스 접근은 배열과 (링버퍼) 덱에만 두고, 연결 리스트에는 두지 않습니다.
