# 컨테이너 설계 노트 — 다른 표준 라이브러리에서 얻은 것

Java / Rust / C++ 표준 라이브러리와 예전 C++ 과제 구현을 읽고 정리한 것입니다.
**원문을 옮기지 않고 다시 썼습니다** — 참고 소스는 `*-ignoreme*` 로 무시되는
폴더에 있어 git 에 없고, 이 문서만으로 읽히게 쓰는 게 규칙입니다
(`.gitignore` 주석 참고).

## 1. ⭐ 인덱스 접근을 "리스트"의 필수 연산으로 두지 않는다

**세 언어가 전부 같은 결론에 도달했습니다.** 연결 리스트에서 `list[i]` 는
O(n) 인데, 인덱스 표기를 허용하면 사용자가 `for i = 1, n do list[i] end` 라고
써서 조용히 O(n²) 를 만듭니다. 표기가 비용을 속이는 것입니다.

| 언어 | 어떻게 막았나 | 강제 시점 |
|---|---|---|
| Java | `RandomAccess` 마커 인터페이스. 멤버가 하나도 없는 빈 인터페이스이고, 범용 알고리즘이 이걸 검사해 인덱스 루프와 반복자 루프를 갈라 씁니다. 배열 기반만 구현하고 연결 기반은 구현하지 않습니다. | 런타임 |
| Rust | 연결 리스트에 인덱스 연산(`Index` trait)을 **아예 구현하지 않습니다.** 대신 전용 커서 타입을 주고, 커서는 한 칸씩 앞뒤 이동만 됩니다. | 컴파일타임 |
| C++ | `std::list` 에는 `operator[]` 도 `at()` 도 **없습니다.** 대신 조회기에 능력 등급 태그를 달고, 범용 알고리즘이 그 태그로 자기를 분기합니다(임의 이동이 되면 포인터 산술, 아니면 한 칸씩 루프). | 컴파일타임 |

셋의 공통 원칙: **"느린 연산을 저렴해 보이는 표기로 감추지 않는다."**
그리고 인터페이스를 작게 유지하고, 파생 연산은 최소 원시 연산 위에 **한 번만**
얹습니다 — Java 는 `get(i)` 와 반복자를 서로의 구현 기반으로 교환하고, Rust 는
`next()` 하나 위에 수십 개 어댑터를 디폴트로 얹고, C++ 은 `++` 반복만으로
임의 이동을 흉내 냅니다.

## 2. ⭐⭐ 더 나은 네 번째 답 — 위치 타입 자체를 제네릭으로

세 언어의 해법은 전부 "인덱스를 줄지 말지"의 이분법입니다. 그런데 **위치를
가리키는 타입 자체를 타입 파라미터로 빼면** 이분법이 사라집니다.

```lua
export type ListCore<E, I> = {
	Get:        (self: ListCore<E, I>, idx: I) -> E?,
	FirstIndex: (self: ListCore<E, I>) -> I?,
	LastIndex:  (self: ListCore<E, I>) -> I?,
	NextIndex:  (self: ListCore<E, I>, idx: I) -> I?,
	PrevIndex:  (self: ListCore<E, I>, idx: I) -> I?,
}
```

| 구현 | 위치 타입 `I` |
|---|---|
| 배열 기반 | `number` |
| 연결 기반 | `Node<E>` — 노드 자체가 곧 위치 |

- 구현체는 **이 다섯 개만** 제공합니다.
- `IndexOf`/`Contains`/`Count` 같은 순회 알고리즘은 이 다섯 개만으로 쓰이므로
  소스에 **한 번만 존재하고** 두 구현이 공짜로 씁니다.
- **순회 방식이 양쪽에서 문자 그대로 같습니다** — 배열 쪽도 `i + 1` 이 아니라
  `NextIndex` 를 거칩니다. 그래서 알고리즘이 구현을 몰라도 됩니다.
- 배열 쪽만 "n번째 위치 얻기"를 O(1) 로 재정의하고, 나머지는 기본 구현을 씁니다.

**왜 이게 나은가**: 세 언어의 해법은 전부 "연결 리스트에서 `list[i]` 를 쓰면
안 된다"를 *별도 장치*(마커/트레이트 부재/태그)로 알립니다. 위치 타입을
제네릭으로 빼면 **그 실수가 애초에 표현 불가능**합니다 — 연결 리스트의 위치는
노드라서 `list:Get(3)` 이 타입 에러입니다. 장치가 필요 없습니다.

### Luau 실측 결과 — 완전히 성립

`.claude/audit/list-index-abstraction/` (스파이크, 기대 진단 7건). 규모 증상 0건.

음성 대조군 5종이 전부 검출됩니다. 특히 **배열의 위치와 연결의 위치를 섞어
쓰면 잡힙니다**(`arrayList:Get(linkedList:FirstIndex())` → 타입 에러).

### 같이 따라오는 규약 — 위치를 저장하면 안 된다

이 설계의 원 구현이 남긴 규약: **사용자가 위치 값을 보관하는 것은 정의되지
않은 동작입니다.** 컨테이너가 바뀌면 배열의 인덱스는 밀리고 연결의 노드는
사라질 수 있는데, 그 차이가 구현마다 달라 공통 인터페이스가 보장할 수 없기
때문입니다. C++ 의 반복자 무효화 규약과 같은 이야기입니다.

**Luau 에서는 타입으로 못 막습니다.** 문서 규약으로 둘지, 세대 카운터로
런타임 검출할지 정해야 합니다. — **미결**

### 순회 중 삭제 — `RemoveThenNext`

같은 구현에 있던 프리미티브: 지우면서 위치를 다음으로 **갱신해 돌려줍니다.**
"순회 중 삭제" 라는 고전적 함정을 API 하나로 없앱니다. 지금 `Arr` 에는
대응물이 없고 `FilterInplace` 로 우회할 뿐입니다.

## 3. 조회기를 두 층으로 나눈다

세 언어 모두 **"for 루프용 단순 순회"** 와 **"위치를 들고 다니며 그 자리에서
변형하는 조회기"** 를 구분합니다.

- 단순 순회: 전진만, 값만 꺼냄. Luau 의 `__iter` 메타메소드와 제네릭 `for` 가
  정확히 이 자리입니다.
- 커서: 앞뒤 이동 + 현재 위치 조회 + 그 자리에 삽입/삭제/교체. Java 와 Rust 가
  각각 별도 타입으로 둡니다.

연결 리스트에서 커서가 결정적인 이유: `Get(i)` 를 반복하면 O(n²) 인데 커서로
누적 이동하면 O(n) 입니다.

**예전 과제에서도 같은 원칙이 독립적으로 나왔습니다** — 이진 탐색 트리에서
내부 노드는 변경 가능한 타입으로 두고 **바깥에는 읽기 전용 래퍼만** 내보내,
사용자가 트리 불변식을 깨지 못하게 했습니다. 그 근거도 적혀 있었습니다:
"인터페이스로 감춰도 구현을 알면 되돌려 캐스팅할 수 있으므로, 메모리를 더
쓰더라도 안전한 래퍼를 쓴다."

이건 `.claude/audit/arr-type-redesign/` 에서 찾은 **`ArrView<T>`** 와 같은
원리입니다 — 콜백에 전체 타입 대신 읽기 관점의 뷰를 주는 것. 서로 다른 이유
(저쪽은 불변식 보호, 이쪽은 타입 체이닝 유지)로 같은 모양에 도달했습니다.

## 4. Set 은 Map 의 특수화로 구현하되 상속하지 않는다

예전 과제에서: 해시 셋을 해시 맵 위에 구현하되 **"is-a 관계는 성립시키지
않는다"** 를 명시했습니다. 값 자리에 빈 타입을 넣고, 바깥으로는 셋의 어휘만
노출합니다.

이름도 갈랐습니다: **셋은 `Add`/`Has`/`Remove`, 맵은 `Set`/`Get`.**

Luau 에는 private 상속이 없으니 **내부에 맵 인스턴스를 들고 얇은 래퍼만
노출**하면 같은 효과입니다. 코드 중복을 없애면서 API 표면은 완전히 분리됩니다.

## 5. 예전 과제에서 가져갈 나머지

- **연산 이름을 ADT 별로 가른다**: 양 끝 추가/제거, 중간 삽입(밀어냄),
  덮어쓰기(길이 불변), 스택, 큐, 셋, 맵이 각각 다른 동사를 씁니다. 이미
  규칙표가 파일 상단 주석으로 정리돼 있었습니다.
- **용량 전략을 상수로 노출**: 최소 용량 / 증가율 / 축소 임계치를 이름 있는
  상수로 빼둡니다.
- **불변식을 파일 최상단에 선언**: 원형 큐에서 *"뒤 포인터는 반드시 빈 칸을
  가리킨다 → 따라서 앞뒤가 같으면 비어 있는 것으로 간주하고, 한 칸 남으면
  확장한다"* 처럼, "가득 참"과 "빔"이 같은 조건이 되는 고전적 버그를 미리
  문서화하고 피했습니다. 힙/덱을 만들기 전에 꼭 할 것.
- **순서 유지 삭제와 순서 무시 삭제를 이름으로 가른다** — 뒤 원소를 당기면
  O(n) 이고 마지막 것을 끌어오면 O(1) 인데, 둘은 다른 연산입니다.

## 6. stl-luau 에 대한 함의 — 아직 결정 안 함

- `Map`/`Filter`/`Reduce` 처럼 순회만 있으면 되는 연산을 **`Arr` 전용 메소드에서
  떼어내 조회기 위의 공용 함수로** 올릴 수 있습니다. 그러면 나중에 연결
  리스트나 덱을 추가할 때 54개를 다시 구현하지 않고 다섯 개 프리미티브만
  주면 됩니다.
  **⚠️ 다만 이건 타입 실측을 다시 해야 합니다** —
  `.claude/audit/arr-type-redesign/` 의 제약(`Map` 반환이 `Arr<G>` 여야 하고,
  콜백이 `Arr<T>` 를 언급하면 체이닝이 죽음)이 자유 함수로 옮겼을 때도
  그대로인지 **아직 안 쟀습니다.**
- 인덱스 접근은 배열과 (링버퍼) 덱에만 두고, 연결 리스트에는 두지 않습니다.
