# 관례와 작업 방식

`CLAUDE.md`가 `@import`하므로 매 세션 로드됩니다 — 세션마다 필요하진 않은
상세는 `.claude/base/`나 개별 문서로.

## 언어 관례

- 사용자는 한국 유저입니다. 사용자가 보는 것(대화, plan, `.claude/` 문서,
  커밋 메시지 요약 등)은 한국어로. 코드 안 주석은 기존 파일들처럼 한국어로
  쓰는 게 이 저장소의 지배적인 스타일입니다(`src/Collections/Arr.luau` 참고) — 다만
  강제는 아니고, 기존 파일을 고칠 땐 그 파일의 기존 언어를 따르세요.
- 에러 메시지 문자열, 함수/변수 식별자는 영어.

## 코드 스타일

**[2026-09-22 전면 재작성 후 기준]** 확정 근거는 `.claude/base/rewrite-plan.md`
1-5 / 1-6 절. 아래와 다른 옛 코드는 더 이상 저장소에 없습니다.

- **네이밍**: 기준은 *"값을 만들거나 감싸는 것은 대문자, 판별 술어와 지역
  변수는 소문자."*

  | 무엇 | 케이싱 | 예 |
  |---|---|---|
  | 타입 | PascalCase | `Arr<T>`, `ArrView<T>`, `HashMapData<K, V>` |
  | 생성자 | PascalCase | `Arr.Of`, `TreeMap.New`, `Heap.FromList` |
  | 연산(네임스페이스 함수) | PascalCase | `Arr.PushBack(a, v)`, `Arr.SortInplace(a)` |
  | **종류** 술어(이 값이 그 컨테이너인가) | camelCase, 최상위 | `stl.isArr(v)`, `stl.isHeap(v)` |
  | 불리언을 돌려주는 연산 | PascalCase(네임스페이스 함수라서) | `Arr.IsSorted(a)`, `HashSet.IsSubsetOf(s, t)`, `Arr.Empty(a)`, `Trait.Implements(t, v)` |
  | 상수 | 대문자 | `VALUE`, `NEXT`, `KEY` |
  | 지역 변수 | camelCase | `arrLen`, `moveLen`, `outLen` |
  | `require` 받은 모듈 | PascalCase | `local Common = require("./Common")` |
  | 소스 파일 | PascalCase | `src/Collections/Arr.luau`, `src/Collections/HashSet.luau` |
  | 테스트 파일 | 소문자 + dot | `tests/spec.arr.luau` |

  camelCase 인 종류 술어는 **배럴 최상위의 `is…` 뿐**입니다 — 모듈 안에서 불리언을 돌려주는 함수는 다른 연산과 같이
  PascalCase 입니다(2026-10-13 이름 검토에서 규약 문장이 이걸 말하지 않는다고 둘이 짚음). **`Is` 접두**: 불리언 연산은 `Is…`(`IsSorted`·`IsSubsetOf`·`IsHeap`),
  형용사 하나짜리 `Empty`·`Equal` 만 접두 없이 둡니다(2026-10-13 이름 고르기 2차 — 외부자 둘은 "전부 `Is`", 내부자 둘은
  지금대로: 동률이라 유지. 배포 전에 다시 볼 후보). **`Common` 은 예외로 전부 camelCase**
  (`Common.raise`, `Common.listLength`, `Common.expectComparator`) — 라이브러리 안에서만 쓰는 모듈이고 공개 표면이 아닙니다.

- ⭐ **데이터는 엔티티, 함수는 서비스** (2026-10-01 사용자 결정, 질문 AB —
  예외 없음, `Fut` 포함). 컨테이너는 **메타테이블 없는 평범한 테이블**이고,
  모든 연산은 모듈의 **네임스페이스 함수**입니다(`Arr.Map(a, fn)`,
  `Fut.AndThen(f, fn)`). **콜론 메소드는 없습니다.** Luau 표준 라이브러리
  (`table`/`buffer`/`coroutine`)와 같은 모양입니다. 근거:
  - **속도**: 메타테이블이 있으면 `t[i]` 에 1.59배 세금 — 걷어내니 `Arr` 원소
    작업이 0.57~0.83배(perf 16절). fastcall 은 사용자 라이브러리에 안 먹지만
    인덱싱 세금은 먹습니다.
  - **일관성**: `Optional`(태그 유니온)은 메소드를 가질 수 없어(`spikes/45`)
    콜론으로는 전 모듈을 덮을 수 없었습니다.
  - **타입**: 함수가 타입 **바깥**에 있으니 전체형이 데이터부 그 자체
    (`Arr<T> = ArrData<T>`). 예전의 메소드 교집합·재귀 별칭 우회(`typeof`
    나열)·"계약 멤버 재선언 금지" 규칙이 전부 필요 없어졌습니다.
  - **확장**: `Arr<T>` 를 받는 함수는 누구나 같은 모양으로 더합니다(사용자:
    *"라이브러리에 묶여 무언가 더 넣기 어려워지는게 원천적으로 해결"*).
  - **쓰는 맛**: 체이닝은 없고 문장으로 나눠 씁니다 — *"quad 는 expr 공간에
    놓이는 연산들이라 원라이너가 필요했고, 여기는 속도가 더 생명"*. 생태계
    대조(외부자 검토)도 컨테이너·데이터 처리는 바깥 함수가 강하게 우세.

- **모듈 패턴**: 이름 붙은 top-level 함수들(첫 인자가 데이터) + **순수 테이블
  네임스페이스** `return { … }` + 판별용 **타입 토큰**(`__type`). ⭐ **트레이트**
  (2026-10-06 사용자 결정, 질문 AG — `papers/06`, `src/Trait.luau`):
  - ⭐ **트레이트 시스템은 2026-10-15 에 갈아 끼웠습니다**(질문 AY — 토론·판정이 모은 D3, 같은 날 **정의를 한 번만 넘기는 레코드 안**으로
    — 사용자 제안, `.claude/research/trait-udtf`. 정본 설명은 `src/Trait/init.luau` 머리, 설계 기록 `.claude/research/trait-v4`~`v10`·
    `trait-debate`·`luau-source`·`trait-udtf`). ⚠️ **이 시스템은 계속 바뀔 수 있습니다**(사용자: *"trait 시스템 자체는 계속 변화할 수
    있는걸로 둬야겠어. 타입 시스템이 변경됨에 따라서 영향을 받는지라"*) — 타입 모양이 새 솔버의 동작(**사용자 타입 함수 `Trait.View`**,
    명시적 타입 인자, 표 리터럴의 양방향 추론)에 기댑니다. 음성 대조군 `spikes/69`·`70` 이 그 동작의 경보입니다.
  - ⭐ **종류 = 닫힌 트레이트**(2026-10-15 질문 BB — 사용자: *"Arr 조차 Trait 이여야 하는거 아닌가 … struct Arr impl Arr {}"*, *"닫힌 경로는
    다른 곳에서 impl 될 일 없어 … 한번 구현되고 끝"*): 모듈 맨 위 `const Kind = Trait.Struct("Stl.Arr")`(토큰도 같이), 맨 끝 `Kind.Seal({ … })` —
    **그 표가 곧 종류의 정체**(`stl.Arr`). `ImplFor`·`ImplWhere` 가 없고 봉인하면 끝, 함수는 그 자리 그대로 직접 호출(찾을 일이 없음). 종류 자리에
    모듈을 넘깁니다: `Stack.ImplFor(stl.Arr, …)`, `Trait.Converter(stl.Stack, stl.Arr)`, 아래로 `Trait.Converter(stl.Arr)`, `Trait.Implements(stl.Arr, v)`,
    `Trait.TokenOf(stl.Arr)`. 바깥 종류도 같은 모양(`spec.traitrebuild` 9절). 모듈에 공개 `Token` 필드는 없습니다.
    ⭐ **두 장치의 경계**(사용자: *"어느 부분은 이거로 두고 어느 부분은 직접 적기로 두고 파편화 된 감"*): 닫힌 쪽(종류)의 타입 닻은 `__type:
    Token<"Stl.Arr">`, 열린 쪽(트레이트 — dyn)의 닻은 `__traits.X` 레코드 — 그래서 `__traits` 에 자기 종류를 적지 않습니다. 컨테이너 타입의
    `__traits` 는 **그 종류의 모듈이 정의하는 자리에서 직접 구현한 트레이트**(Java 의 `implements` — 같은 파일의 `ImplFor` 와 같은 사람이 적음)이고,
    **다른 곳에서 나중에 붙은 것**(바깥 등록, 덱 → 스택 같은 뭉텅이)은 `As`·`Trait.Converter`(어댑터)입니다. Rust 가 이 구분 없이 되는 건 컴파일러가
    모든 `impl` 을 전역으로 알아서 — 등록이 타입을 못 바꾸는 Luau 에선 Java 쪽 모델이 할 수 있는 것입니다.
  - **값에는 타입 토큰 하나**: 생성자가 `__type = TOKEN`(그 종류의 모듈이 `Trait.Struct("Stl.Arr")` 로 만든 얼린 공유 테이블 — 밖에서는
    `Trait.TokenOf(stl.Arr)`)을 붙입니다. **모든 생성·반환 경로**가 붙여야 합니다(`spec.contracts` 5절이 전수로 지킴). 토큰 **이름은 유일**합니다(라이브러리
    것은 `Stl.` 접두, 바깥 것은 자기 이름공간 — 같은 이름 두 번은 에러). 직렬화했다 되읽은 값은 `Trait.Restore(값)` 이 이름으로 이 사본의
    진짜 토큰을 되찾습니다. 토큰·트레이트는 **정의**라 버리지 않습니다(버리는 것은 정의되지 않은 동작 — 등록부가 강한 배열).
    키 문자열 `"__type"` 은 모듈마다 **리터럴로** 적습니다 — `Trait.TYPE_KEY` 를 받아 쓰면 상수 접기가 안 돼 생성이 7~11% 느렸습니다.
  - ⭐ **파일 구조**(2026-10-13 사용자 결정): `src/Trait/`(폴더)는 **시스템만**(토큰, 정의 `Trait`·`Fn`·`Default`, 조회 `ImplOf`·`Implements`·
    `ExpectImpl`·`Expose`). **트레이트 하나하나는 `src/Traits/<이름>.luau`** 에 — 정의(팩토리), 완성 표·등록 표 타입(`Full`·`Provided`), 마커,
    기본 구현, **종류를 모르는 코드의 진입점 서명**이 한 파일에 있습니다(*"인터페이스 파일처럼"*). 그 모듈이 **곧 트레이트 객체**입니다:
    `List.ImplFor(TOKEN, …)` 과 `List.IndexOf(값, x)` 가 같은 이름. 컨테이너는 `src/Collections/`, 컨테이너를 모르는 알고리즘(`BSearch`,
    곧 정렬들)은 `src/Algorithms/`. **확장할 수 있게만** 하고 조각마다 따로 떼어 쓸 수 있게까지는 만들지 않습니다. 진입점의 에러 머리는
    트레이트 이름(`List: IndexOf needs a List — …`).
  - ⭐ **트레이트 = 정의(팩토리) 한 번** — 정의가 이름 목록(런타임)이자 트레이트의 제네릭 타입이자 `X.Of`·`X.OfMut`·`X.ImplOf`·진입점의 타입입니다:
    ```lua
    -- 트레이트가 자기 연관 타입 레코드와 조건(마커)을 가짐(질문 BA)
    export type AssocRead<T> = { read Item: () -> T }
    export type Assoc<T> = { read Item: () -> T, read Mut: (T) -> T }
    export type ValueRead<T> = { read __type: Trait.Token<any>, read __traits: { read Deque: AssocRead<T> } } -- 배럴의 stl.DequeRead<T>
    export type Value<T> = { read __type: Trait.Token<any>, read __traits: { read Deque: Assoc<T> } }        -- 배럴의 stl.Deque<T>
    const DequeBase = Trait.Trait("Deque", function<Self, T>(of: (Self & ValueRead<T>) | AnyToken, ofMut: (Self & Value<T>) | AnyToken)
    	return table.freeze({
    		PushBack = Trait.FnMut<<(deque: Self, item: T) -> Self>>(), -- 필수·쓰기
    		Front = Trait.Fn<<(deque: Self) -> T?>>(),                 -- 필수·읽기
    		-- 기본 구현은 Trait.Default(빌더)·Trait.DefaultMut(빌더)
    	})
    end)
    export type Read<Self, T> = typeof(DequeBase.Of<<Self, T>>(nil :: any))        -- 읽기 보기(쓰기 칸 없음)
    export type Full<Self, T> = typeof(DequeBase.OfMut<<Self, T>>(nil :: any))     -- 완성 표
    export type Provided<Self, T> = typeof(DequeBase.ImplOf<<Self, T>>(nil :: any)) -- 등록 표(기본 구현 칸은 선택)
    ```
    - ⭐ **칸은 타입으로 레코드**(`{ required, mut, fn }` — `Fn`·`FnMut`·`Default`·`DefaultMut`)이고, 사용자 타입 함수
      **`Trait.View<정의, "read"|"full"|"impl">`** 이 정의 함수의 타입을 받아 세 보기(읽기 = 쓰기 칸을 뺌, 완성 = 칸마다 `fn`, 등록 = 기본 구현
      칸만 `fn?`)로 다시 짓습니다 — **제네릭 목록은 정의의 것 그대로**(`f:generics()`), 가변 꼬리는 뗌(`X.Of(d, 1)` 이 인자 수 에러). 정의가
      함수가 아님·표를 안 돌려줌·칸이 넷 중 하나가 아님·매개변수가 셋 이상은 정의 줄의 타입 에러(`'View' type function errored at runtime:
      Trait.Trait: …`, 보기 셋이라 세 번씩). 정의나 반환이 `any` 면 보기도 `any`(검사를 끄는 관용구 — 런타임만 보는 테스트가 씀).
    - ⭐ **읽기·쓰기는 칸에**(2026-10-15 질문 BA — 사용자: *"MarkerMut Marker 나누는거 너무 애매모호 … Mut/NonMut 을 한 곳에 모아둔게 문제"*,
      Rust 의 `&self`/`&mut self` 를 칸에): `X.Of(v)` 는 **읽기 보기**(정의의 첫 매개변수 조건 — 빌린 읽기 참조도 받음), `X.OfMut(v)` 는 **완성 표**
      (둘째 매개변수 조건 — 바꿀 수 있는 참조만, 둘째가 없으면 첫째). 런타임은 같은 표. 예전엔 읽기·쓰기를 트레이트 통째의 `of` 와 진입점마다의
      마커 두 곳에서 정해 어긋났습니다 — 빌린 참조가 `Collection.Of` 를 거쳐 `Clear` 를 얻었고(구멍), `Deque.Of` 는 아예 못 얻었음(과잉). `spikes/71`.
    - ⭐ **트레이트마다 자기 연관 타입 레코드, 컨테이너는 `__traits` 한 줄**(질문 BA — 사용자: *"Trait 를 아예 드러내는게 나아보이겠다"*):
      `read __traits: { read List: List.Assoc<T, number>, read Deque: Deque.Assoc<T>, read Collection: Collection.Assoc }`(빌린 읽기 타입은
      `AssocRead` 들 — `Collection` 은 안 적음). 레코드의 이름·위치·변성은 **그 트레이트 안의 일**이라 트레이트끼리 이름에 합의할 필요가 없고 뜻이
      부딪히지 않습니다(예전의 공용 `__generics: { Item, Index }` 는 전역 어휘였음). 공변 칸은 `() -> T`, 바꿀 수 있는 참조의 표시는 불변 팬텀
      `Mut`(`(T) -> T` 는 `() -> T` 의 서브타입이 아니라 칸 하나로는 두 쓰임을 못 덮음). 맵·셋의 조건(`of`)은 불변(조회도 키가 입력 — 질문 AM).
      ⭐ **리스트의 위치도 불변**(`read Index: (I) -> I` — 2026-10-16 리뷰 1라운드 T1: 위치는 `Get`·`NextIndex` 의 입력이라, 공변이던 때 `List.Get(연결덱, 123)`
      이 0건으로 라이브러리 줄에서 터졌음). 대가: 위치가 원소에 기대는 종류(연결 덱)는 빌린 읽기 참조를 넓은 원소로 못 받음(`spikes/65` 경계 줄).
      새 컨테이너·새 트레이트도 이 모양. 컨테이너 타입의 팬텀 줄이 63 → 14 였습니다.
    - ⚠️ **등록(런타임)은 타입을 못 바꿉니다**(사용자: *"Impl 자체가 타입을 변경 못 시키기 때문에 생긴다는 큰 제약을 돌고 돌고 돌았을 뿐"*) —
      바깥에서 등록·뭉텅이로 만족시킨 트레이트는 그 종류의 타입에 안 붙습니다. ⭐ **값은 트레이트, 타입은 데이터에 붙는 표식**(사용자):
      트레이트마다 값 타입 `stl.Stack<T>`(바꿀 수 있는 값 — 지금의 `X.Value`)·`stl.StackRead<T>`(읽기 — `X.ValueRead`)이 있고, 다른 종류를 그
      트레이트로 쓰려면 **중간자** `Trait.Converter` 에 그 쌍을 아는 쪽이 타입을 적어 **진짜로 바꿉니다**(사용자: *"<T>(Arr<T>) -> Stack<T> 를 주는

- ⭐ **읽기만 하는 함수의 첫 인자는 `ArrRead<T>`**(2026-10-06 사용자 결정, 질문 AC — `spikes/56`).

  원소로 쓰면 건전하지 않습니다. ⚠️ **둘 이상의 배열을 하나의 `T` 로 합치는 함수**(`Concat`,
  `MergeSorted`)도 `ArrData` — `ArrRead` 둘에서 `T` 를 풀면 솔버가 `number & string` 을 골라
  결과 원소를 아무 타입에나 넣을 수 있게 됐습니다(진단 0건, 실측). 입력을 소비하는 제자리
  변환(`CompactInplace`)은 `ArrConsumed<T>` — 원소는 공변이지만 **`n` 은 읽기·쓰기**라 `ArrRead` 는
  못 들어옵니다(읽기로 빌린 참조가 쓰기를 얻던 구멍, AC 리뷰). `ArrRead` 는 공개 타입입니다.
  **`CircularDeque` 도 같습니다**(2026-10-12 사용자 결정, 질문 AK — `spikes/60`): 읽기 함수는 `CircularDequeRead<T>`, 쓰기

  ⚠️ 콜백을 넘길 땐 **`f<<T>>` 나 파라미터 주석을 항상** — 둘 다 없는 맨 람다는 몸통이 파라미터를
  제약하지 않으면 결과 원소가 아무 타입에나 들어갑니다(luau 0.734 까지 진단 0건 — 새 솔버 결함, `spikes/57`. **0.742 에서
  고쳐짐**(2026-10-14) — 그래도 주석·`f<<T>>` 를 권합니다: 몸통이 산술이면 맨 람다는 여전히 에러).

- **함수의 첫 인자는 데이터부(`XxxData<T>`)로 받습니다** — 단 `Arr` 의 읽기 함수는 위 `ArrRead`. 원소가 유니온일 때
  (`Arr<number?>`)도 추론이 서는지는 `spikes/46` 이 지킵니다. 자기 자신을
  돌려줄 땐 `return self :: any`. (예전엔 전체형에 섞인 계약 조각 때문에 이게
  **필수**였습니다 — 지금은 전체형이 곧 데이터부라 같은 뜻입니다.)

- **계약은 함수 묶음입니다**(`List.Full<C, E, I>`·`List.Provided<C, E, I>` 등 — 정의 팩토리에서 얻음) — 트레이트에 등록되는 구현의
  모양입니다. 필드는 **`read`**(팩토리가 `table.freeze` 로 돌려줘서) — 그래야 제네릭 함수들을 모은 표가 그대로 구현체로
  들어갑니다(실측). 공용 알고리즘은 **구현을 손으로 받지 않습니다**:
  `List.IndexOf(a, x)`, `Map.Keys(m)` — 트레이트 마커에서 타입을 추론하니
  타입 인자도 필요 없습니다(예전 `Algorithm.Keys<<HashMap<…>, K, V>>(HashMap, m)`).
  ⚠️ 함수 묶음을 **직접** 받는 사용자 제네릭 함수(`put<C, V>(ops: MapFull<C, string, V>,
  …)`)는 여전히 타입 인자가 필요합니다 — 트레이트 마커를 받는 모양으로 쓰세요.
  ⭐ **키·위치·값을 입력으로 받는 제네릭은 불변 마커**(2026-10-12 사용자 결정, 질문 AM — `spikes/61`):
  `stl.MapRead`/`SetRead`/`ListRead`(2026-10-15 전엔 `MapMarker` …)는 `read`(공변)라 **꺼내기만 하는** 알고리즘용입니다(`Keys`·`Count`).
  마커와 함께 값·키·위치를 받아 넘기는 제네릭에 쓰면 그 타입이 조용히 넓어집니다 — `Set`/`Add` 하면
  `HashMap<string, number>` 에 문자열이 들어가고, 조회만 해도 `TreeMap<string, …>` 에 숫자 키가 넘어가
  비교자가 라이브러리 줄에서 터졌습니다(진단 0건 — AC 의 "공변으로 빌린 참조가 쓰기를 얻음" 과 같은
  메커니즘). 그런 제네릭은 **`stl.Map<K, V>`/`stl.Set<T>`/`stl.List<E, I>`**(전엔 `MapMarkerMut` …)를 받습니다 — 데이터 타입의 함수 타입
  팬텀(`read __mapMut: (K, V) -> (K, V)`, 리스트는 `(E, I) -> (E, I)`)을 요구해 불변이고, 읽기 마커의 서브타입이라 읽는 알고리즘에도
  그대로 넘어갑니다. `ArrRead`(빌린 참조)에는 그 팬텀이 없습니다. (2026-10-15 질문 BA 부터 팬텀은 트레이트 레코드의 `Mut` 칸
  — `read __traits: { read Map: Map.Assoc<K, V> }` — 이고, **트레이트 함수의 진입점은 칸의 읽기·쓰기로 마커가 저절로 정해집니다**. 이 규칙이
  남는 곳은 사용자가 마커를 받아 직접 짜는 제네릭과 `Trait.Expose` 의 알고리즘 진입점.) ⚠️ 읽기 마커로 쓰는 코드를 타입이 막지는 못합니다
  (구현은 `any` 를 거침) — 규약입니다.
  **경계**: 넓어지는 것은 **타입 변수로 받아 컨테이너에 넘기는** 키·위치·값입니다. `==` 비교만 하는 값
  (`List.IndexOf(list, item)` — 넓어져도 그냥 "없음")과, 위치를 타입 변수로 두지 않은 조회
  (`stl.ListRead<E, number>` + `idx: number`)는 읽기 마커로 건전하고 `ArrRead`(빌린 참조)도 받습니다.
  트레이트 파일의 진입점에 그런 함수(쓰기, 키를 넘기는 조회)를 더할 때도 `Mut` 마커로.
  ⭐ **원소 타입이 흘러들지 않아도, 컨테이너를 바꾸는 제네릭은 "바꿔도 되는 참조" 를 요구합니다**(2026-10-12,
  질문 AO — `spikes/63`): `Collection.Clear` 는 `stl.Collection`(레코드 `__traits.Collection` — 바꿀 수 있는 참조만 적음)을 받습니다. 토큰만
  요구했더니 읽기 전용으로 빌린 `ArrRead`·`CircularDequeRead` 가 진단 0건으로 지워졌습니다. 읽기만 하는 것(`Collection.Len`)은
  토큰만(`stl.CollectionRead`) — 빌린 참조도 받습니다.

- **제네릭이 안 풀릴 땐 명시적 타입 인자** `f<<T>>(...)` 를 씁니다 —
  `Arr.Of<<number>>()`, `HashMap.New<<string, number>>()`,
  `nested:Flat<<number>>()`. 캐스트(`:: Arr<number>`)는 차선입니다.
  캐스트는 "내 말을 믿어라" 이고 이건 "답을 알려준다" 입니다.
  ⭐ **콜백 파라미터 주석도 이걸로 없어집니다**(2026-10-02 정정, `spikes/54`):
  `Arr.Map<<number>>(a, function(v) return v * 2 end)`. 타입 인자 없이 맨 람다를
  넘기면 아직 에러라, 콜백을 넘길 땐 `<<T>>` 와 콜백 주석 중 하나가 필요합니다.
  자세한 것은 `base/typing-limits.md`.

- **`const` 바인딩**: 재대입 없는 바인딩은 `const`. ⚠️ **`const` 는 `local`
  을 대체하는 키워드입니다**(`const x = 1`). `local const x = 1` 이라고 쓰면
  `const` 라는 지역변수를 만들고 `x = 1` 은 **전역 대입**이 됩니다 — 타입
  주석이 없으면 문법 에러도 안 납니다.

- **삼항 `and/or` 금지.** `if-then-else` 표현식만. 단순 2항 `x or y` 는 허용.

- **`--!strict` 를 모든 파일 1행에.** 그 다음 `--[[ Module — 설명 ]]` 블록.
  예외는 없습니다(`--!nocheck` 이던 `Tuple`/`TypeUtil` 은 내렸습니다).

- **탭 들여쓰기.** 주석은 한국어, 식별자와 에러 메시지는 영어
  (`Common.raise("Arr: Range step must not be zero")` 형식 — 아래 "에러 규약").

- ⭐ **칸과 길이는 읽기만 공개합니다**(2026-10-15 질문 BB (나) ② — 사용자: *"read [number]: T 를 공개 해야할 까 … 맨 뒤에 집어넣으면
  길이가 깨지니까"*): `Arr<T>` 는 `read n`·`read [number]: T` — 읽기(`a[i]`, `a.n`)는 직접(함수를 거치면 2.7~5배 — perf 56절), **쓰기는 함수로만**
  (칸 하나는 `Arr.Set(a, i, v)` — 위치는 `At` 처럼 음수, NaN·`1..n` 밖은 에러, 끝에 더하기는 `PushBack`). 모듈 안쪽은 받자마자 안쪽 타입으로
  캐스트해 직접 씁니다(`const self = arr :: Raw<T>` — 비용 0, perf 56절). `CircularDeque` 는 칸이 **물리** 위치라 칸·`head`·`cap` 을 아예
  숨기고 `size` 는 읽기만. ⚠️ 대가: 리스트를 **읽고 쓰는** 타입(`{ T }`)을 받는 자리에 `Arr` 가 안 들어갑니다 — 라이브러리의 생성자 중 리스트를
  읽기만 하는 것(`FromList`·`FromRecords`·`Arr.FromTable`·`Fut.All`·`Common.denseList`)은 `{ read [number]: T }` 로 받게 바꿨고(2026-10-16 리뷰 T3 에 도구 열하나도 — `BSearch` 다섯·`FromSorted` 셋·`SortedArray.Locate`·`Append` 의 `other`·`CompleteArray.IsHeap`, 사전은 `HashMap.FromTable` 의 `{ read [K]: V }`), 내장 함수
  (`table.concat`·`table.sort`·`table.move`)에 바로 넘기는 사용자 코드는 `Arr.Join` 이나 캐스트(`spikes/73`). 새 함수가 리스트를 읽기만 하면
  `{ read [number]: T }` 로 받으세요.
- **배열 표현**: `{ n: number, [number]: T }` + 타입 토큰(`__type`).
  Lua 기본 `#` 대신 `self.n` 을 신뢰합니다 — 희소 배열과 꼬리 `nil` 문제를
  피하기 위함입니다. 1..n 사이에 구멍이 있을 수 있고, **각 함수가 구멍을
  어떻게 다루는지 주석에 적습니다.**
  ⭐ **구멍은 타입에 `T?` 로 드러냅니다**(2026-09-30 사용자 결정, 질문 T —
  Rust `MaybeUninit` 과 같은 결: 기본값이 없어 대신 채워줄 수 없으니 드러내는
  게 가장 명시적). 구멍이 생길 수 있는 생성자는 `Arr<T?>` 를 돌려주거나
  명시를 요구합니다(`Sized(n, fill)` 의 `fill` 필수, 구멍을 원하면
  `Arr.Sized<<number?>>(n, nil)`). 그래서 **콜백 계열**(`Map`/`Filter`/`Fold`/
  `Count`/`Find`/`Some`/`Every`/`Reduce` …)이 구멍을 **`nil` 그대로 넘기는
  것**이 건전하고, **집계·정렬**(`Sum`/`Prod`/`Max`/`Min`/`Sort`/`Join`)이
  구멍을 건너뛰는 것은 타입이 거짓말할 때(캐스트, `a[i] = nil`)를 위한
  **런타임 그물**입니다. `?` 를 떼는 길은 `Compact`/`FillHoles`(새 배열).
  ⚠️ 그래서 **콜백 타입의 다른 인자에 `T` 를 넣지 않습니다** — 셋째 인자가
  `ArrView<T>` 이던 때는 네임스페이스 호출에서 콜백 원소를 더 좁게 적은 것
  (`number?` 자리에 `v: number`)이 안 잡혔습니다. 지금은 **`ArrView<unknown>`**
  (질문 V → Z: `any` 로 뺐더니 `any` 가 콜백 반환을 타고 결과 타입으로
  샜습니다. `base/typing-limits.md`).

- ⭐ **`FromTable` 은 복사, `Adopt` 는 입양**(2026-10-13 사용자 확인, 질문 AU): `Arr.FromTable(t)`·`HashMap.FromTable(t)` 는
  넘긴 테이블을 **복사**하고, `Arr.Adopt(t)`·`HashMap.Adopt(data, size)`·`FlatMap.Adopt(…)` 는 **그대로 가집니다**(넘긴
  쪽이 뒤에서 건드리면 같이 바뀜). 예전에는 `Arr.FromTable` 이 입양이고 복사 판이 `CloneFromTable` 이라 같은 이름이 두
  모듈에서 소유권이 반대였습니다. `TreeMap.FromSorted` 는 어느 쪽도 아닙니다 — 전제(정렬됨)를 검사하지 않을 뿐, 목록을
  읽어 노드를 **새로 만듭니다**. 생성자를 더할 때 이름을 이 뜻대로.

  `Single` = `{ 값, 다음 }`, `Double` = `{ 값, 앞, 뒤 }`, `Binary` = `{ 값, 왼쪽, 오른쪽, 부모 }`, 트리부의 노드는 그 뒤에
  `5` = 키, `6` = 균형 정보(`Trees/Search`). **값은 모든 종류에서 1번 칸.**
  - 이름 필드를 두지 않습니다 — 하나라도 있으면 해시 부분이 따로 잡혀 트리 노드 만들기 2.3배·메모리 1.56배였습니다
    (perf 38절). ⚠️ 칸은 **생성자에 다 적으세요**(`{ value, prev, nil }`) — 나중에 대입하면 만들기가 3배(perf 34절).
  - **타입은 불투명 핸들**입니다(Luau 는 번호 칸마다 타입을 다르게 못 적음): `{ read __links: "double", read __value: T }`
    처럼 팬텀만. 종류마다 `NodeRead<T>`(읽기 — 컨테이너가 밖으로 내주는 위치)와 `Node<T>`(고칠 수 있음 — 불변 팬텀이
    더 있음). 덕분에 종류가 섞이지 않고(양방향 노드를 이진 도구에), **옵셔널 자리에서도 원소 타입을 지킵니다**
    (재귀 별칭이던 때는 새 솔버 결함으로 0건 — `spikes/65`·`66`).
  - 값은 함수로 읽습니다(`Node.Double.Value(node)`, 트리 노드는 `Search.Key`·`Search.Value`). **함수 호출은 해시
    필드보다 느립니다**(12.7 대 5.1ns — perf 38-2절) — 그래서 **라이브러리 안쪽은 그 종류의 상수와 같은 값을 지역
    상수로 다시 적어 직접 인덱싱**합니다(`const VALUE, PREV, NEXT = 1, 2, 3` — 모듈의 값을 받아 쓰면 접히지 않음).
    안쪽에서는 노드를 `any` 로 다루고, 불투명 타입은 공개 서명에만 씁니다.
  - ⭐ **노드를 따라가거나 찾는 도구는 "받은 핸들의 타입 그대로" 돌려주는 서명**으로 적습니다(리뷰 1라운드):
    `Next<N>(node: N & Kind): N?`, `Walk<N>(start: (N & Kind)?): () -> N?`, `Find<N, K>(root: (N & Keyed<K>)?, …): N?`
    (`Kind` = `{ read __links: "double" }` 같은 종류 팬텀). 고칠 수 있는 노드를 따라가면 고칠 수 있는 노드가,
    읽기 노드면 읽기 노드가, 레드블랙 노드면 레드블랙 노드가 나옵니다. `NodeRead<T>` 로 받아 `NodeRead<T>?` 를
    돌려주던 때는 ① 자기가 만든 사슬도 따라간 뒤에는 못 고쳤고 ② 트리 노드를 넘기면 값 타입이 `K | V` 나
    `unknown` 이 됐고 ③ 따라가 얻은 노드를 그 방식의 `Remove` 에 못 넘겼습니다. 값을 읽는 도구(`Value<T>(node:
    NodeRead<T>): T`)는 그대로입니다.

  - ⚠️ **알려진 경계**: 읽기 노드는 원소에 공변이라 `number` 덱의 위치가 `number?` 덱의 `InsertAfter`·`Remove` 에
    진단 0건으로 들어갑니다(`T → T?` 방향만 — `string` 대 `number` 는 막힘). 런타임은 "다른 컨테이너의 가운데

    노드가 아닌 값, 끝 쪽 칸이 `nil` 인데 머리·꼬리가 아닌 노드: 두 번 지우기·떼어 낸 노드가 걸림). 다른 컨테이너의

    내도 이어 돌게 합니다(`LinkedDeque.Iter`, `Node.Double.Walk`).

    코드)입니다.

    부르면 원리상 위치가 없어 줄을 볼 수 없습니다.
  - ⚠️ 테스트에서 줄 번호를 헬퍼 함수로 재지 마세요 — 그 헬퍼도 -O2 에서
    인라인됩니다(실제로 그랬음). `where = debug.info(1, "l") + 1` 을 그 자리에.
  - 반환 타입을 맞춰야 하는 자리는 `return Common.raise(...)` — Luau 는 `never`
    호출 뒤를 함수의 끝으로 보지 않습니다.

- **예외 안전성 — 계약은 정본에 적은 것뿐, 던진 뒤는 전부 관측** (2026-10-06 사용자 결정,
  질문 AD — quad 와 같은 틀). 콜백·비교자·순회자가 던진 뒤의 상태는 **약속하지 않습니다** —
  내용(반쯤 바뀐 값)도, 불변식(`n`·`size`·정렬 순서)도. 약속하면 나중에 바꿀 때 BREAKING 이
  되고, 지키려면 복사 비용이 듭니다(사용자: *"강하게 보장해야할 이유는 모르겠고"*).
  - **관측(지금 그렇다 — 바뀌어도 BREAKING 아님)**: 새 배열판은 입력을 안 바꿈, 버퍼에서
    정렬하고 되쓰는 판(`StableSort`/`SortBy`/`PartialSort` 의 Inplace)은 원본 그대로, 지금
    함수들은 `n`·`size` 를 맞게 둠, `Map(…, to)` 는 `to.n` 밖 칸에 쓰인 채 남을 수 있음, `Fut`
    는 리스너 하나가 던져도 나머지를 다 돌리고 첫 에러를 다시 던짐. 테스트가 이것들을 고정해도
    **관측을 고정한 것**입니다 — 바꿀 땐 테스트를 고치면 됩니다. 문서에는 "관측 — 계약
    아님" 으로 적습니다.
  - 계약(정본)으로 남는 것: 정상 반환의 의미(함수 주석), 라이브러리 자신의 에러는 메시지와
    사용자 줄(에러 규약).

- **비교의 통화가 둘입니다**: 정렬·최대·최소는 불리언 `LessThan`
  (`table.sort` 가 받는 모양), 정렬된 구조에서의 탐색은 3방향 `Comparator`.
  둘 사이는 `Common.lessFrom` / `Common.compareFrom` 으로 건넙니다 — 비용이
  눈에 보이도록 자동 변환은 없습니다.

- **`table.move`/`table.create` 로 벌크 처리**, 가변인자 다수는 `table.pack`
  대신 `select` 루프. 근거는 아래 성능 절.

- **포매터는 stylua 입니다**(`stylua.toml`, `mise.toml` 에 2.5.2 고정).
  `./scripts/check.sh` 가 `--check` 로 게이트를 걸고, 어긋나면
  `stylua src tests` 로 맞추면 됩니다. 바이너리가 없는 환경에서는 건너뜁니다.
  **네임스페이스 `return { … }` 만 `-- stylua: ignore` 로 빼뒀습니다** —
  한 줄에 여럿 늘어놓는 편이 읽기에 낫기 때문입니다. 새 모듈도 같게 하세요
  (지시자는 **주석 전체가 정확히 `-- stylua: ignore`** 여야 먹습니다).
  ⚠️ **`(` 로 시작하는 문장을 쓰지 마세요** — `;(f :: T)(x)` 처럼요. 앞 문장이
  **`const` 선언이면 stylua 2.5.2 가 모호함을 가르는 `;` 를 지워** 파싱 에러가
  납니다(실측, 평범한 `local` 뒤에서는 앞줄 끝으로 옮겨 보존함). 지역 변수로
  받아 부르세요: `const f = x :: T; f(1)`. 에러가 나니 조용한 버그는 아니지만
  포맷 한 번에 멀쩡하던 파일이 깨집니다.

## ⭐ `type function` 은 주의해서 씁니다 (2026-09-22 사용자 확정, 10-14 "주의" 로 정정)

*"타입 함수는 문제가 너무 많기 때문에, 가급적 사용을 피할거야."* quad 이

⚠️ **금지 규약이 아니라 주의입니다**(2026-10-14 사용자: *"타입 함수를 적대시 하는건 아닌데. 부작용이 많아서 주의하고
있는거야. 규약은 아니고. 테스트가 끔찍히 어려워지고 버그/예외가 많아서 그랬어. 써도 되긴 한데. 무슨 일을 내나

⭐ **지금 src 의 사용자 타입 함수는 둘 — `Trait.View`·`Trait.Entries`**(위 트레이트 절).
- `View`(2026-10-15, 질문 AY — 트레이트 정의를 한 번만 넘기는 레코드 안): 들이기 전에 잰 부작용 — 다시 지은 제네릭이 적용한 자리의 스코프를
  받고 기본값·바운드를 잃음(지금 정의엔 없음), 제네릭 소비자·제네릭 재정의는 그대로 검사됨(`spikes/70`), 쓰는 쪽 에러 문구는 D3 와 같음.

  그 타입이 구현하는 트레이트가 메시지에 나옴), **원인을 모르는 우회 하나**(진입점마다 제네릭을 새로 만들어 바꿔 끼움 — 안 하면
  `Expected 'E', got 'number'`, `research/trait-ofmut`). 배터리 `spikes/55`·`60`·`61`·`64`·`65`·`71`·`72` 가 지킴.
새 타입 함수를 더하면 같은 식으로 재서 보여 드립니다.
게이트의 에러 규약은 최상위 `type function … end` 몸통을 건너뜁니다(거기의 `error` 는 타입 에러를 내는 길). `src/` 는 여전히
**전부 `--!strict`** 이고 예외가 없습니다. 예전에 쓰던 `Tuple`/`TypeUtil` 은 내린 채입니다.

세 함정(2026-09-22 기록):

1. `type function` 안에서 같은 파일의 바깥 로컬을 참조하면 **컴파일 실패**
2. `error()` 대신 `print()` + `types.never` 를 써야 진단이 노출됨 — ⚠️ **0.742·0.740 에선 아님**: `Trait.View` 의 `error("…")` 는

3. ⭐ 어떤 타입이 `type function` 을 **한 번 통과하면**(그냥 `return t` 라도)
   그 뒤 제네릭 `self` 메소드 체이닝이 **조용히 깨짐**

셋째가 결정적이었습니다 — 그때는 **체이닝이 공개 표면의 핵심**이었습니다
(`arr:Map():Filter():Sort()`). (2026-10-01 에 콜론 메소드를 없애 체이닝 자체가
사라졌지만, 나머지 두 함정과 제네릭 함수 전반의 위험은 그대로라 방침은
유지합니다.)

내려둔 실험 코드와 그 경위는 `.claude/research/type-function-experiment/`,
